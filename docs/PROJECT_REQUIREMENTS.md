## 2. 产品目标

Pinjie Mall 面向零售商家及其消费者，提供微信小程序商城、运营管理后台和独立 FastAPI 服务。项目长期目标包含标准电商交易闭环和合规的两级分销佣金能力。

当前阶段按四个里程碑建设 Backend 商城业务、数据库模型及公开契约，沿用已有 Admin 基础能力。小程序工程和消费者界面不在当前阶段实施。`apps/web` 永久冻结，不能作为产品交付、测试、发布或部署目标。

## 3. 目标用户与场景

| 用户 | 主要需求 |
| --- | --- |
| 消费者 | 后续通过微信小程序浏览商品、下单、支付、查看订单和参与分销 |
| 运营人员 | 通过 Admin 管理商品、订单、用户、分销规则、资产和系统设置 |
| Backend 开发者 | 在清晰领域边界、事务、迁移、安全和契约约束下实现商城能力 |
| 小程序开发者 | 后续消费稳定的 Backend 契约实现用户体验 |
| 项目维护者 | 独立维护代码、文档、发布配置和生产追溯链 |

核心使用场景是微信小程序电商：商品、库存、购物车、订单、支付和分销由 Backend 提供服务，Admin 支持运营和风控，用户通过小程序完成 C 端交互。

## 4. 产品原则

| 编号 | 需求 | 验收条件 |
| --- | --- | --- |
| BASE-GEN-001 | 项目采用单一 Monorepo 管理 Backend、Admin 和共享包 | 应用边界清楚，共享代码只经 `packages/` 公开入口协作 |
| BASE-GEN-002 | 项目独立维护和运行 | 运行、发布、镜像、凭据和配置不依赖其他仓库或本机绝对路径 |
| BASE-GEN-003 | 需求、阶段、实现、计划和交付历史分层维护 | PRD、索引、源码、计划和 Changelog 各自记录唯一事实 |
| BASE-GEN-004 | 跨端能力使用单一全栈计划 | 同一计划说明 Backend、Admin、小程序、契约、数据和部署影响 |
| BASE-GEN-005 | 模块边界可机械验证 | 跨领域内部导入、跨应用源码引用和循环依赖由门禁拒绝 |
| BASE-GEN-006 | 临时兼容必须受控 | 兼容窗口有期限、负责人、观测、回滚和删除测试 |

## 5. Backend 与 Admin

| 编号 | 需求 | 验收条件 |
| --- | --- | --- |
| BASE-BE-001 | 提供可配置、可健康检查的 FastAPI 服务 | 本地可运行，健康检查不依赖具体业务数据 |
| BASE-BE-002 | 提供统一响应、错误和请求追踪 | 公开 API 使用稳定响应契约，不泄露敏感信息 |
| BASE-BE-003 | 提供认证、用户、管理员、RBAC、资产和系统设置基础能力 | 认证、授权和审计在服务端生效 |
| BASE-BE-004 | 商城领域按数据所有权实现 | 商品、库存、购物车、订单、支付和分销分别定义不变量、事务和契约 |
| BASE-ADMIN-001 | 提供可扩展的 Ant Design Pro 管理后台 | 具备路由、布局、认证、权限和统一错误处理 |
| BASE-ADMIN-002 | 管理页面覆盖主要操作状态 | 覆盖加载、空数据、失败、无权限和成功反馈 |
| BASE-ADMIN-003 | 运营能力与服务端权限一致 | 商品、订单和分销运营页面只使用生成契约和服务端权限 |

## 7. 数据、契约与质量

| 编号 | 需求 | 验收条件 |
| --- | --- | --- |
| BASE-API-001 | 根 `openapi.json` 是唯一 OpenAPI 契约 | 契约由 Backend 导出，禁止手工维护副本 |
| BASE-API-002 | API Client 由契约生成 | `packages/api-client/src/` 不手工修改，Admin 和后续小程序消费者使用业务数据 |
| BASE-DB-001 | PostgreSQL 是关系数据权威来源 | 结构通过 Alembic 演进，环境和数据所有权隔离 |
| BASE-DB-002 | Redis 不保存唯一业务事实 | 缓存、限流、会话和锁具备命名空间、TTL 和失败语义 |
| BASE-OPS-001 | 本地只运行 Backend 8000 与 Admin 3001 | Web 端口，包括 3000，禁止监听和暴露 |
| BASE-OPS-002 | Backend 与 Admin 使用不可变镜像交付 | 生产 Compose 不声明 Web 服务，镜像使用完整 digest |
| BASE-OPS-003 | CI、发布和部署分离 | 发布和部署需要独立授权，失败关闭且可追溯 |
| BASE-QUAL-001 | 未实现和未验证状态如实记录 | 不以文档、Mock 或静态检查伪造业务已交付 |

## 8. 商城后端四阶段需求

本轮仅建设 Backend、数据库模型、迁移文件和生成契约。管理端 API 属于后端范围，Admin 页面与小程序工程不在本轮范围。阶段描述为目标，完成事实以源码、验证记录和 Changelog 为准。

### 8.1 商品基础

| 编号 | 需求 | 验收条件 |
| --- | --- | --- |
| BASE-COM-001 | 商品分类与商品资料 | 分类最多三级且无环；商品具有实物/虚拟类型、草稿/上架/下架状态，分类和商品生命周期受引用保护 |
| BASE-COM-002 | 稳定 SKU 与基础售价 | 每商品至少一个 SKU；无规格商品使用默认 SKU；SKU 编码唯一且 ID 稳定，修改规格或售价不删除重建；价格为非负精确人民币金额 |
| BASE-COM-003 | 商品图片复用资产 | 仅绑定经服务端确认的图片资产；仍被商品引用的资产不能删除；商品公开信息不泄露成本及内部管理字段 |
| BASE-COM-004 | 独立库存与人工调整 | SKU 对应唯一库存账户；可用与占用数量非负；调整具有幂等标识、版本、原因及不可变流水，不能通过商品编辑绕过库存操作 |
| BASE-COM-005 | 收货地址 | 用户只访问本人地址；最多二十条，至多一个默认地址；默认地址删除后有确定的替补规则；订单使用独立地址快照 |
| BASE-COM-006 | 运费模板 | 按件或克计费，支持省份规则、默认地区、包邮门槛及排除地区；收费单位明确、续费向上取整，缺失或无效模板拒绝结算 |

实物商品的可售 SKU 必须有可计量重量；虚拟商品不收物流运费，虚拟交付与订单履约在交易阶段定义。上架前校验商品、有效 SKU、分类及运费配置。基础售价先支持统一标价，会员价格能力按第四阶段细化，不预留可以悄悄改变成交金额的占位分支。

### 8.2 交易

| 编号 | 需求 | 验收条件 |
| --- | --- | --- |
| BASE-COM-101 | 购物车与结算预览 | 数量有界，校验 SKU 归属、可售性和当前库存；服务端重新计价，预览不创建订单 |
| BASE-COM-102 | 原子下单与幂等 | 同一业务请求重复提交只创建一个订单；订单、明细和库存占用保持原子一致；同键不同内容明确冲突 |
| BASE-COM-103 | 订单快照 | 固化名称、规格、成交价格、数量、地址、运费和适用规则版本；修改商品或地址不能改变历史订单 |
| BASE-COM-104 | 库存占用释放 | 下单占用、支付确认与取消释放具有明确状态及流水；并发不得超卖或重复释放，超时任务可恢复 |
| BASE-COM-105 | 订单状态机 | 非法转换被拒绝；重复操作幂等；取消与支付并发依据权威事实处理；所有状态变化可追溯 |

待付款订单自创建起 30 分钟到期，超时取消并原子释放占用库存。实物与虚拟商品必须分开下单；实物必须选择本人地址，虚拟订单不接受收货地址。同一运费模板按该组商品合并件数或克数、使用该组商品金额判断包邮，不同模板运费相加。预览返回报价指纹，下单重新计算并核对指纹，价格或快照资料变化时要求重新预览。任何前端提交的总价、优惠或佣金均不能作为扣款依据。

### 8.3 支付、履约与售后

| 编号 | 需求 | 验收条件 |
| --- | --- | --- |
| BASE-COM-201 | 外部支付闭环 | 微信/支付宝作为长期渠道目标；实际启用渠道具备下单、查单、关单、可信回调和恢复，未实现渠道明确不可用 |
| BASE-COM-202 | 支付可信确认 | 验签后核对商户、应用、订单、金额和币种；重复通知不重复记账；网络超时记录结果未知并查询确认 |
| BASE-COM-203 | 履约 | 发货、收货、自动确认有权威状态保护；管理批量写固定顺序锁定、全有或全无；物流轨迹对接单独确认 |
| BASE-COM-204 | 部分退款与退货 | 申请金额完整传到资金执行；累计退款不超过实付；退货数量、运费退还、入库及佣金追回按已确定政策联动 |
| BASE-COM-205 | 评价与财务核对 | 评价校验已购订单明细和重复发布；财务核对区分渠道事实、人工处理和未决差异，不以人工标记伪造渠道确认 |

外部写操作必须持久化意图、定义幂等及结果确认，不在长期数据库事务内等待外部资金操作。支付与售后成功以权威确认事实为准。

M3 采用以下明确初始政策：微信和支付宝渠道未配置时，支付意图保留不可用事实并明确返回不可用状态，不产生伪造付款成功；支付和退款成功只由渠道验签、商户与应用、订单、金额、币种均核对通过后的内部确认入口写入。实物订单付款后等待发货，管理员发货后用户可确认收货，发货满七日由持久化扫描自动确认；虚拟订单付款后等待管理员完成交付。退款按用户选择的订单明细数量和对应商品金额申请，不自动退运费、不自动入库；管理员审核后由渠道退款事实确认成功。用户只能对已交付的本人订单明细发布一次公开评价。对账导入仅记录渠道账单与系统支付事实的匹配或差异，不能改变订单、支付或退款状态。

### 8.4 会员与两级分销

| 编号 | 需求 | 验收条件 |
| --- | --- | --- |
| BASE-COM-301 | 会员及价格规则 | 等级、资格和价格优先级明确；展示、结算和订单快照使用同一套计价结果 |
| BASE-COM-302 | 两级推荐 | 防止自邀与循环；返佣最多两级；关系变更不重写历史订单的归属快照 |
| BASE-COM-303 | 佣金生命周期 | 规则、受益人、基数和舍入可追溯；冻结、结算、撤销及退款追回幂等，规则调整不追改已确定佣金 |
| BASE-COM-304 | 双轨钱包 | 账户权利、消费/提现资格和转移边界必须在实施前明确；余额不得仅存 Redis，冻结须有业务归属和明细 |
| BASE-COM-305 | 提现 | 申请、审核、资金执行、拒绝解冻及结果未知有明确流程；人工确认与渠道实际打款分开记录，不伪造自动打款 |

账户与资金口径尚未批准时不开放相关资金接口。具体未决问题只记录在活动计划中。

### 8.5 共同验收边界

1. 复用既有认证、权限、审计、资产、异常和响应体系，领域仅写入自身数据。
2. 金额使用 Decimal、明确精度与舍入，时间统一 UTC，业务主键由统一 UUID v7 入口生成。
3. 并发写依赖数据库约束、固定锁顺序或条件更新；幂等必须核对请求内容并保存业务结果。
4. 新表通过新增 Alembic revision 演进，不搬运参考仓库迁移历史，不自动执行共享数据库变更。
5. 每阶段同步唯一 OpenAPI 及生成客户端。小程序身份接入须独立适配既有用户体系，不复活 Web 服务。
6. 本地完成区分轻量检查、动态专项测试、真实渠道联调和生产验收；未执行项不得记为通过。

## 9. 非目标

1. C 端 Web、Web 服务、Web 镜像和任何 Web 端口。
2. 当前阶段的小程序工程、界面或小程序端自动化验证。
3. 本轮的 Admin 新增页面，以及未列入四阶段的促销、优惠券、秒杀和拼团实现。
4. 默认生产数据、管理员凭据、真实域名、证书、平台密钥和生产镜像 digest。
5. 未经单独计划和授权的外部支付、物流、对象存储、消息和营销集成。

非目标不改变长期商城方向。业务实现进入后续全栈计划，并在实施时补充领域不变量、接口消费者、风险和验证。

## 10. 完成验收

当前阶段按活动计划中的里程碑验收：完成对应后端能力、适用轻量门禁、契约同步和文档收尾。未实施阶段、小程序、真实依赖测试和外部渠道联调如实记录；本地实现完成不等于完整交易验收或生产可用。长期商城验收还需小程序、真实交易链路、并发与故障恢复及生产可靠性验证。

## 11. 需求追踪规则

1. 新计划关联一个或多个适用 `BASE-*` 编号；无法对应时写明原因。
2. 改变产品目标或验收边界时，同一任务更新本文件、计划和相关权威文档。
3. 技术实现变化但产品需求不变时，只更新计划、架构或运维文档。
4. 需求完成后，在计划记录验证证据，并在 `CHANGELOG.md` 记录交付事实。
