## 2. 产品目标

Pinjie Mall 面向零售商家及其消费者，提供微信小程序商城、运营管理后台和独立 FastAPI 服务。项目长期目标包含标准电商交易闭环和最多三级分销佣金能力，返佣总额受每订单行佣金来源预算约束。

本基线自 2026-09-21 采用统一平台运费、会员/批发统一计价、零元内部成交、整单含原运费退款及三级预算分佣。既有 M1 至 M4 和 Admin A0 至 A4 的历史交付按当时政策保留；当前代码仍使用商品运费模板、部分退款、正额成交与固定两级分佣，须经后续全栈计划迁移，不能将本次设计更新视为已实现。

当前阶段在 Backend 四个里程碑基础上建设 Admin 电商运营页面与配套接口，覆盖商品、订单履约、售后支付查询、会员分销与财务审核。小程序工程和消费者界面不在当前阶段实施。`apps/web` 永久冻结，不能作为产品交付、测试、发布或部署目标。

## 3. 目标用户与场景

| 用户 | 主要需求 |
| --- | --- |
| 消费者 | 后续通过微信小程序浏览商品、下单、支付、查看订单和参与分销 |
| 运营人员 | 通过 Admin 管理商品、订单、用户、分销规则、资产和系统设置 |
| Backend 开发者 | 在清晰领域边界、事务、迁移、安全和契约约束下实现商城能力 |
| 小程序开发者 | 后续消费稳定的 Backend 契约实现用户体验 |
| 项目维护者 | 独立维护代码、文档、发布配置和生产追溯链 |

核心使用场景是微信小程序电商：商品、库存、购物车、订单、支付和分销由 Backend 提供服务，Admin 支持运营和风控，用户通过小程序完成 C 端交互。

## 5. Backend 与 Admin

| 编号 | 需求 | 验收条件 |
| --- | --- | --- |
| BASE-BE-001 | 提供可配置、可健康检查的 FastAPI 服务 | 本地可运行，健康检查不依赖具体业务数据 |
| BASE-BE-002 | 提供统一响应、错误和请求追踪 | 公开 API 使用稳定响应契约，不泄露敏感信息 |
| BASE-BE-003 | 提供认证、用户、管理员、RBAC、资产和系统设置基础能力 | 认证、授权和审计在服务端生效 |
| BASE-BE-004 | 商城领域按数据所有权实现 | 商品、库存、购物车、订单、支付和分销分别定义不变量、事务和契约 |
| BASE-ADMIN-001 | 提供可扩展的 Ant Design Pro 管理后台 | 具备路由、布局、认证、权限和统一错误处理 |
| BASE-ADMIN-002 | 管理页面覆盖主要操作状态 | 覆盖加载、空数据、失败、无权限和成功反馈 |
| BASE-ADMIN-003 | 运营能力与服务端权限一致 | 商品、订单和分销运营页面只使用生成契约和服务端权限 |
| BASE-ADMIN-004 | 提供商品运营闭环 | 分类、品牌、规格属性、平台运费、商品、稳定 SKU、统一价格、图片、库存调整及流水、上下架可操作，查询在服务端过滤，普通列表具有合法批量能力 |
| BASE-ADMIN-005 | 提供交易履约与售后工作台 | 可查询订单快照与履约、发货及虚拟交付、审核退款、查询支付与对账；审核和渠道成功分别展示 |
| BASE-ADMIN-006 | 提供会员分销财务查询与审核 | 可查询会员、推荐、佣金、双轨钱包和提现，按既有规则审核提现；不提供余额改写、关系重绑或伪造打款 |

库存变动、钱包流水及支付事件属于不可变业务历史，Admin 只读展示，不提供人工删除或批量写入；随关联业务长期保留，清理须经过独立保留策略与授权。普通商品、订单、退款、会员、佣金、钱包账户和提现列表仍按生命周期提供批量操作或受权限保护的选中记录导出，不能因没有删除接口而归类为日志。

## 8. 商城后端四阶段需求

本节定义商城后端四阶段能力。对应历史建设范围包括 Backend、数据库模型、迁移文件和生成契约；当前 Admin 专项消费并补充管理端 API，小程序工程仍不在当前范围。阶段描述为目标，完成事实以源码、验证记录和 Changelog 为准。

### 8.1 商品基础

| 编号 | 需求 | 验收条件 |
| --- | --- | --- |
| BASE-COM-001 | 商品分类与商品资料 | 分类最多三级且无环；商品具有实物/虚拟类型、草稿/上架/下架状态，分类和商品生命周期受引用保护 |
| BASE-COM-002 | 稳定 SKU 与统一计价 | 无规格使用默认 SKU，多规格以当前实际组合识别；同货品 ID 稳定，规格转换保留旧引用；支持基础/成本/市场价、批发阶梯与会员规则，成交价格为非负精确人民币金额 |
| BASE-COM-003 | 商品图片复用资产 | 仅绑定经服务端确认的图片资产；仍被商品引用的资产不能删除；商品公开信息不泄露成本及内部管理字段 |
| BASE-COM-004 | 独立库存与人工调整 | SKU 对应唯一库存账户；可用与占用数量非负；调整具有幂等标识、版本、原因及不可变流水，不能通过商品编辑绕过库存操作 |
| BASE-COM-005 | 收货地址 | 用户只访问本人地址；最多二十条，至多一个默认地址；默认地址删除后有确定的替补规则；订单使用独立地址快照 |
| BASE-COM-006 | 平台统一运费 | 按优惠后整单商品金额和省级地区计算包邮门槛或固定费用；地区覆盖默认，虚拟零运费；配置缺失或错误拒绝结算，不读取商品旧模板 |

目标运费不使用重量计价，SKU 重量为选填资料；虚拟商品不收物流运费。上架前校验商品、有效 SKU、分类链、属性关系和图片，报价时校验明确的运费配置。品牌、公共属性、分类模板、商品采用版本及候选关系由数据库字典统一定义，历史规格不可被公共字典改名破坏。旧运费模板仅在完成受控迁移后退出新单计算。

### 8.2 交易

| 编号 | 需求 | 验收条件 |
| --- | --- | --- |
| BASE-COM-101 | 购物车与结算预览 | 数量有界，校验 SKU 归属、可售性和当前库存；服务端重新计价，预览不创建订单 |
| BASE-COM-102 | 原子下单与幂等 | 同一业务请求重复提交只创建一个订单；订单、明细和库存占用保持原子一致；同键不同内容明确冲突 |
| BASE-COM-103 | 订单快照 | 固化名称、规格、成交价格、数量、地址、运费和适用规则版本；修改商品或地址不能改变历史订单 |
| BASE-COM-104 | 库存与累计限购 | 下单同时预占 SKU 库存及用户商品额度，成交确认、取消释放有事实记录；不限购期间仍累计，成交退款不恢复终身累计；并发不得超卖或超限，超时任务可恢复 |
| BASE-COM-105 | 订单状态机 | 非法转换被拒绝；重复操作幂等；取消与支付并发依据权威事实处理；所有状态变化可追溯 |

待付款订单自创建起 30 分钟到期。没有成功或未知支付阻断时，超时取消并原子释放库存和限购预占；未知先查单，晚到真实收款保留事实并补偿退款。实物与虚拟商品必须分开下单；实物选择本人地址，虚拟无地址。按整单优惠后商品金额与省级配置计算一次运费。预览返回报价指纹，下单重算，价格或快照资料变化要求重新确认。前端提交金额不能作为扣款依据。

总应付为零的订单通过唯一内部确认号成交，复用库存、限购、履约和分佣决策，不生成虚假零元渠道支付；商品零价但运费非零仍走真实渠道。单行及总金额写入前校验精度、有限性与溢出。订单主状态仅待付款、已付款、已取消；接单、履约、退款分别建模，页面综合展示。

### 8.3 支付、履约与售后

| 编号 | 需求 | 验收条件 |
| --- | --- | --- |
| BASE-COM-201 | 外部支付闭环 | 微信/支付宝作为长期渠道目标；实际启用渠道具备下单、查单、关单、可信回调和恢复，未实现渠道明确不可用 |
| BASE-COM-202 | 支付可信确认 | 验签后核对商户、应用、订单、金额和币种；重复通知不重复记账；网络超时记录结果未知并查询确认 |
| BASE-COM-203 | 履约 | 发货、收货、自动确认有权威状态保护；管理批量写固定顺序锁定、全有或全无；物流轨迹对接单独确认 |
| BASE-COM-204 | 未发货/未交付整单退款 | 本期仅已成交且未发货实物、未交付虚拟商品可申请；完整覆盖原明细，退原商品实付及原运费；审核、渠道执行与补偿分开；累计退款不超原支付，原 SKU 全量回补及追佣幂等；发货/交付后售后留待专项 |
| BASE-COM-205 | 评价与财务核对 | 评价校验已购订单明细和重复发布；财务核对区分渠道事实、人工处理和未决差异，不以人工标记伪造渠道确认 |

外部写操作必须持久化意图、定义幂等及结果确认，不在长期数据库事务内等待外部资金操作。支付与售后成功以权威确认事实为准。

目标政策：未配置渠道保留 unavailable，不伪造付款成功；支付/退款只由完整核验的可信事实确认。真实收款及恢复任务先持久化，再原子完成一次业务成交；重复收款、取消后收款分别建立异常退款，不能重复发货或发佣。实物接单后发货，用户确认或发货满七日自动确认；虚拟订单由管理员完成交付。整单退款包含零价明细与原运费；本期只允许未发货/未交付申请，未接单自动审核，已接单人工审核，资金成功后可靠追佣、原 SKU 全量回补与限购标记。已发货未签收同样不开放本期售后，发货/交付后的范围、退货验收与期限留待专项；历史售后按原权益迁移，不能抹去。用户只对已交付本人明细评价一次。对账覆盖收款、退款与提现，人工处置不得伪造渠道成功。具体事务及约束见数据库字典第 5、8 章。

### 8.4 会员与三级预算分销

| 编号 | 需求 | 验收条件 |
| --- | --- | --- |
| BASE-COM-301 | 会员及价格规则 | 等级、资格和价格优先级明确；展示、结算和订单快照使用同一套计价结果 |
| BASE-COM-302 | 三级推荐 | 防止自邀与循环，推荐关系仅首次绑定；返佣最多三级且按真实距离不补位；历史归属快照不重写 |
| BASE-COM-303 | 佣金生命周期 | 规则、受益人、基数和舍入可追溯；冻结、结算、撤销及退款追回幂等，规则调整不追改已确定佣金 |
| BASE-COM-304 | 双轨钱包 | 账户权利、消费/提现资格和转移边界必须在实施前明确；余额不得仅存 Redis，冻结须有业务归属和明细 |
| BASE-COM-305 | 提现 | 申请、审核、资金执行、拒绝解冻及结果未知有明确流程；人工确认与渠道实际打款分开记录，不伪造自动打款 |

目标政策：会员等级可为空，未持有等级与持有停用等级分别记录。有效等级依 SKU 一口价、商品一口价优先；无一口价则用同 SKU 批发价乘最近命中的会员折扣，分类仅折扣/排除，禁止折扣层层相乘。基础、数量和等级变化在同一服务端报价链中处理，先舍入单价再乘数量。

分佣政策发布后冻结内容，下单保存买家等级和行来源预算 S，首次可信成交固定推荐链及受益人状态。来源按 SKU 等级专属、SKU 通用、商品等级专属、商品通用、平台默认选择；disabled 终止回退且该行全部停发。最多三级按矩阵计算候选额，一级缺矩阵可按资格兜底，明确零值不兜底。按一级到三级依次分配剩余 S，超额截断，三层实发总和不得超过 S；全局总开关关闭覆盖所有路径。默认交付七日后结算；整单退款撤销冻结权益或追回已结算额，不足形成欠款，新佣金及提现释放先还欠款。

双轨钱包固定为佣金钱包与消费钱包：佣金钱包只接收已结算佣金，可提现，不能用于购物；消费钱包只能用于后续购物抵扣，不能提现；两者禁止互转。提现申请冻结佣金钱包可用余额，审核拒绝必须解冻；审核通过与实际渠道打款结果分开记录，未接入渠道时不得伪造打款成功。具体未决问题只记录在活动计划中。

### 8.5 共同验收边界

1. 复用既有认证、权限、审计、资产、异常和响应体系，领域仅写入自身数据。
2. 金额使用 Decimal、明确精度与舍入，时间统一 UTC，业务主键由统一 UUID v7 入口生成。
3. 并发写依赖数据库约束、固定锁顺序或条件更新；幂等必须核对请求内容并保存业务结果。
4. 新表通过新增 Alembic revision 演进，不搬运参考仓库迁移历史，不自动执行共享数据库变更。
5. 每阶段同步唯一 OpenAPI 及生成客户端。小程序身份接入须独立适配既有用户体系，不复活 Web 服务。
6. 本地完成区分轻量检查、动态专项测试、真实渠道联调和生产验收；未执行项不得记为通过。

## 9. 非目标

1. C 端 Web、Web 服务、Web 镜像和任何 Web 端口。
2. 当前阶段的小程序工程、界面或小程序端自动化验证。
3. 未列入当前专项的促销、优惠券、秒杀和拼团实现。
4. 默认生产数据、管理员凭据、真实域名、证书、平台密钥和生产镜像 digest。
5. 未经单独计划和授权的外部支付、物流、对象存储、消息和营销集成。

非目标不改变长期商城方向。业务实现进入后续全栈计划，并在实施时补充领域不变量、接口消费者、风险和验证。

## 10. 完成验收

当前阶段按活动计划中的里程碑验收：完成对应后端能力、适用轻量门禁、契约同步和文档收尾。未实施阶段、小程序、真实依赖测试和外部渠道联调如实记录；本地实现完成不等于完整交易验收或生产可用。长期商城验收还需小程序、真实交易链路、并发与故障恢复及生产可靠性验证。

## 11. 需求追踪规则

1. 新计划关联一个或多个适用 `BASE-*` 编号；无法对应时写明原因。
2. 改变产品目标或验收边界时，同一任务更新本文件、计划和相关权威文档。
3. 技术实现变化但产品需求不变时，只更新计划、架构或运维文档。
4. 需求完成后，在计划记录验证证据，并在 `CHANGELOG.md` 记录交付事实。
