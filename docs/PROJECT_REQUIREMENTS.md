# Pinjie Fullstack Base 产品需求基线

> 文档状态：生效
> 适用范围：`pinjie-fullstack-base` 及其派生仓库
> 最后更新：2026-09-07

## 1. 文档定位

本文件是 `pinjie-fullstack-base` 的产品需求权威来源，定义母版解决的问题、目标使用者、适用场景、目标能力、非目标、派生规则和验收边界。

本文件描述“母版最终需要具备什么”，不记录当前完成度。相关事实按以下来源维护：

| 信息 | 权威来源 |
| --- | --- |
| 项目身份、当前阶段、活动计划和权威入口 | `PROJECT_INDEX.md` |
| 详细实现状态 | 实际源码、配置、迁移、生成契约和对应架构文档 |
| 全部实施计划永久登记 | `plans/INDEX.md` |
| 已交付能力和版本变化 | `CHANGELOG.md` |
| 技术选型及其理由 | `docs/adr/` |
| 工程结构和实现边界 | `docs/architecture/` 和各级 `AGENTS.md` |
| 具体实施方案和验证结果 | `plans/*.md` |
| CMS、电商等业务扩展设计 | `docs/blueprints/` 和派生仓库文档 |

PRD 与当前实现不一致时，以本文件判断目标范围，以实际源码、配置、迁移、生成契约和对应架构文档判断详细实现状态，并通过新的全栈计划处理差距。`PROJECT_INDEX.md` 只负责项目身份、当前阶段、活动计划和权威入口，不得仅修改根索引或 Changelog 来改变产品需求或伪造实现状态。

## 2. 产品背景

常见全栈业务项目在启动阶段会重复处理后端工程分层、认证与用户基础、管理端和用户端骨架、接口类型生成、本地环境、数据库迁移、质量门禁和容器部署。这些工作跨越 Python 与 JavaScript 工具链，容易出现以下问题：

1. Backend、Admin 和 Web 各自开发，接口和类型逐渐漂移。
2. 新项目重复搭建工程基础，质量和安全边界不一致。
3. 通用基础设施与具体业务混在一起，难以复用和升级。
4. 项目缺少明确的母版基线，派生后无法追溯继承与扩展范围。
5. 开发、测试和部署约定分散，新成员或 AI 需要反复拼接上下文。

本产品通过一个可运行、可验证、可派生的全栈 Monorepo 母版，提供跨业务通用基础，并为具体业务保留清晰扩展边界。

## 3. 目标用户

| 用户 | 主要需求 |
| --- | --- |
| 母版与项目维护者 | 持续维护商城全栈能力、规则、契约和质量基线 |
| 派生项目负责人 | 使用稳定基线推进电商与多级分销业务落地 |
| Backend 开发者 | 在统一分层、事务、迁移和安全边界内扩展电商与分销领域能力 |
| Admin 开发者 | 基于统一契约和管理端组件体系实现商品、订单与分销运营流程 |
| 小程序端开发者 | 后续基于统一后端契约实现微信小程序 C 端体验（前阶段暂不开发） |
| 项目协作者和 AI | 通过索引、PRD、计划和文档快速确认目标、现状与执行范围 |

本产品不直接面向派生项目的最终业务用户。最终业务用户的需求由派生仓库 PRD 负责定义。

## 4. 核心使用场景

1. 微信小程序电商商城：基于 FastAPI 后端与 Ant Design Pro 管理后台，提供完整的商品、购物车、订单、支付和分销裂变体系，C 端通过微信小程序呈现。
2. 从母版创建一个独立 CMS 项目，继承认证、用户、管理端、用户端、契约生成和部署基线，再增加内容、栏目、媒体、审核和发布能力。
3. 从母版创建电商项目，保留通用能力，通过业务蓝图和新的全栈计划增加商品、库存、订单、支付等领域。
4. 创建企业站或博客，保留 SSR、SEO 和可访问性能力，并按实际需求裁剪 Admin 与业务模块。
5. 创建内部管理平台，以 Backend 和 Admin 为主，明确不涉及 C 端 Web，同时继续使用统一契约和质量门禁。
6. 母版升级时，通过母版不可变 Tag 和对应完整 Commit SHA 判断派生项目基线，并评估可安全同步的通用能力。

## 5. 适用与不适用范围

### 5.1 默认适用

- 需要 FastAPI 后端、PostgreSQL 数据库和 React 管理后台的业务系统。
- 面向微信小程序终端的电商与分销项目。
- 需要独立 Backend、Admin，同时要求接口类型一致的项目。
- 需要认证、用户、管理、系统等通用基础的 CMS、博客、企业站、管理平台和电商项目。
- 需要 Windows 本地开发、GitHub Actions、Docker 和 1Panel 部署基线的项目。
- 需要长期维护规则、需求、计划、ADR、文档索引和变更记录的项目。

### 5.2 默认不适用

- 任何形态的 C 端 Web 站点及其服务端口（本项目完全面向微信小程序端）。
- 只有少量静态页面且不需要后端和数据库的纯静态站点。
- 以原生移动端、桌面客户端、实时游戏或嵌入式设备为主要交付物的项目。
- 强依赖 Django、Nuxt、Java、.NET 等其他核心技术栈，且无意采用本母版架构的项目。
- 以机器学习训练、高性能计算或流式数据处理为核心的系统。
- 必须采用完全 Serverless 且不运行长期 FastAPI、PostgreSQL 或 Redis 服务的项目。

不适用并不表示技术上无法改造。改造幅度足以改变母版核心边界时，应创建独立架构基线，不能继续宣称完整继承本母版。

## 6. 产品原则

| 编号 | 需求 | 验收条件 |
| --- | --- | --- |
| BASE-GEN-001 | 母版必须以一个全栈 Monorepo 管理 Backend、Admin、Web 和共享包 | 三个应用边界清楚，共享只通过 `packages/` 的公开包发生 |
| BASE-GEN-002 | 母版必须只包含跨业务可复用能力 | 具体 CMS、电商、博客业务只存在于蓝图或派生仓库 |
| BASE-GEN-003 | 母版必须支持独立派生和运行 | 派生仓库运行时不依赖母版本机目录或其他参考项目绝对路径 |
| BASE-GEN-004 | 目标能力、阶段导航、详细实现、实施过程和交付历史必须分开维护 | PRD、根项目索引、实际文件与架构文档、计划和 Changelog 各自拥有明确职责 |
| BASE-GEN-005 | 跨栈功能必须作为一项完整能力规划和验收 | 同一功能使用一份全栈计划覆盖涉及的应用、契约、数据和部署范围 |
| BASE-GEN-006 | 母版及派生项目必须能够追溯基线 | 派生项目同时记录母版不可变 Tag、完整 40 位 Commit SHA、派生类型、阶段和业务范围 |
| BASE-GEN-007 | 母版必须采用可机械验证的模块化边界 | 应用、领域和 Feature 只通过公开入口协作，越层、跨域内部引用和循环依赖由自动门禁拒绝 |
| BASE-GEN-008 | 临时兼容只能用于受控迁移 | 兼容窗口具备范围、负责人、删除日期、观测指标、回滚条件和删除测试，禁止永久或隐式兼容 |

## 7. Backend 目标需求

| 编号 | 需求 | 验收条件 |
| --- | --- | --- |
| BASE-BE-001 | 提供可配置、可启动和可健康检查的 FastAPI 应用 | 本地环境可以启动应用，健康检查不依赖具体业务数据 |
| BASE-BE-002 | 提供统一的成功响应、业务异常和请求追踪机制 | 公开 API 使用统一响应契约，顶层 `message` 使用中文，错误包含可定位的请求标识且不泄露敏感信息 |
| BASE-BE-003 | 提供认证与会话基础能力 | 支持派生项目实现登录、可关闭的公开注册、身份校验、当前用户读取和登录失效处理；用户与管理员新密码统一为 6 至 64 个字符，不使用默认生产密钥 |
| BASE-BE-004 | 提供用户账户基础能力 | 支持 Admin 独立创建用户、用户资料（含受控头像绑定）、账户状态、统一软删除与长期可恢复回收站；恢复后保持停用，具体业务画像由派生项目扩展 |
| BASE-BE-005 | 提供管理身份和 RBAC 基础 | 支持管理员身份、角色、权限和受保护管理接口，复杂 ABAC 或组织模型不进入母版默认范围 |
| BASE-BE-006 | 提供系统级公共能力入口 | 健康、配置、审计、限流和缓存等能力通过公共基础设施或 system 领域统一承载 |
| BASE-BE-007 | 数据访问必须具有明确分层和事务边界 | Router、Service、Repository、Model 和 Schema 职责可由规则与测试验证，事务由 Service 控制 |
| BASE-BE-008 | 外部输入和外部系统调用必须安全失败 | 输入在边界校验，外部请求具有超时、有限重试和幂等边界，不静默吞错 |
| BASE-BE-009 | 每个领域必须拥有自己的写模型和内部实现 | 跨领域写流程只通过公开 Application Service、Port、DTO 或领域事件编排，其他领域不得直接访问 Repository、Model 或内部 Service |
| BASE-BE-010 | Admin 管理端点必须声明资源权限 | 每个新增管理端点在 Router 显式声明准确 `PermissionCode`；缺少目录项时先更新源码权限目录并通过受控同步写入目标环境，禁止只校验管理员登录态 |
| BASE-BE-011 | 提供强类型运行时系统设置 | 站点资料与公开注册使用数据库权威配置、固定 Schema、revision 并发保护和审计；注册配置失败时保持关闭，配置媒体与文件资产隔离 |

## 8. Admin 目标需求

| 编号 | 需求 | 验收条件 |
| --- | --- | --- |
| BASE-ADMIN-001 | 提供可扩展的 B 端管理应用骨架 | 应用具有路由、布局、导航、认证入口和统一错误处理能力 |
| BASE-ADMIN-002 | 提供管理员登录与权限入口 | 未认证和无权限状态可识别，受保护页面不能仅依赖界面隐藏控制访问 |
| BASE-ADMIN-003 | 提供用户、管理员、角色、权限和系统管理的扩展位置 | 用户管理包含受独立权限控制的创建、正常列表、回收站和单条及批量恢复；通用管理能力边界清楚，具体业务运营页面由派生项目增加 |
| BASE-ADMIN-004 | 管理界面必须覆盖完整操作状态 | 表格、表单和操作流程覆盖加载、空数据、失败、无权限和成功；所有删除、移入回收站和移除操作，无论软硬删除、单条或批量、列表或 LOGO 与头像等非列表入口，均使用统一警告弹窗明确目标、影响及恢复方式；确认后才执行，提交防重并禁止关闭，失败保留目标、草稿和选择并明确反馈，已有确认不重复叠加 |
| BASE-ADMIN-005 | 管理端必须适合高频工作操作 | 界面紧凑、可扫描，支持筛选、比较、重复操作、长文本和窄屏溢出处理 |
| BASE-ADMIN-006 | 页面只通过共享 API Client 消费后端契约 | 不在页面复制 OpenAPI DTO，不绕过统一 HTTP、认证和错误处理入口 |
| BASE-ADMIN-007 | 数据列表必须提供与生命周期一致的批量操作 | 除登录安全事件、审计事件、请求元数据及产品明确登记的不可变历史记录外，列表按权限提供批量选择和至少一种有效批量操作；软删除实体批量软删除，硬删除实体批量硬删除，未定义删除生命周期的实体提供状态等合法批量操作 |
| BASE-ADMIN-008 | 提供固定、强类型的系统设置界面 | 站点资料与公开注册使用对应 Ant Design 组件，按精确读写权限显示只读或编辑状态，revision 冲突保留草稿并要求明确刷新 |

## 9. 客户端形态与小程序端规划（Web 目标需求废弃）

本项目为微信小程序商城项目，应用层完全不需要 Web 端，所有 `BASE-WEB-*` 需求在本项目中废弃停用，完全禁止开发 Web 端及暴露 WEB 端口。

C 端交互由后续小程序端承接，并确立以下阶段目标与约束：

| 编号 | 需求 | 验收条件 |
| --- | --- | --- |
| BASE-MP-001 | C 端统一采用微信小程序端 | C 端用户通过微信小程序访问商城，不采用 Web 方案；前阶段先不开发，由后续专项阶段实施 |
| BASE-MP-002 | 前阶段优先完成后端与管理端 | 后端领域模型、SPU/SKU、订单、支付、分销佣金与管理后台优先就绪，为后续小程序端提供完整稳定接口支持 |
| BASE-MP-003 | Web 端全面停用并排除出交付目标 | apps/web 目录冻结停用，禁止分配开发资源，禁止在本地或生产启动 Web 端服务与监听端口 |

## 10. API 与共享包目标需求

| 编号 | 需求 | 验收条件 |
| --- | --- | --- |
| BASE-API-001 | 根 `openapi.json` 必须是唯一 OpenAPI 契约 | 契约由 Backend 导出，面向开发者的标题、分组、接口摘要、字段说明和响应说明使用中文，路径、参数、字段与程序标识保留英文；禁止手工编辑和维护应用内副本 |
| BASE-API-002 | `packages/api-client/src/` 必须由根契约生成 | 生成过程可重复，Admin 和 Web 使用同一份类型和请求能力 |
| BASE-API-003 | 契约变化必须按固定顺序同步 | Backend 实现、OpenAPI 导出、API Client 生成、前端适配和跨栈验证在同一计划内完成 |
| BASE-API-004 | 共享包必须保持业务中立 | 只承载明确跨应用复用的客户端、Lint 和 TypeScript 配置，不承载单一派生项目业务实现 |
| BASE-API-005 | 公开契约变更必须识别并审查破坏性影响 | 移除字段、改变类型或语义、改变方法或路径、收紧约束及改变错误契约必须在同一全栈计划中完成消费者迁移或明确的受控兼容窗口 |

## 11. Database 目标需求

| 编号 | 需求 | 验收条件 |
| --- | --- | --- |
| BASE-DB-001 | PostgreSQL 必须作为关系数据权威来源 | 本地、测试和生产数据库明确隔离，不使用内存数据库替代关键行为验证 |
| BASE-DB-002 | 数据库结构必须通过 Alembic 演进 | Model 变化具有对应迁移，能够验证空库升级和重复升级 |
| BASE-DB-003 | 异步数据访问必须避免隐式查询和失控事务 | 关联加载、事务提交和查询边界符合 Backend 规则并有测试覆盖 |
| BASE-DB-004 | 派生业务的数据不变量必须由派生项目定义 | 母版不预设商品、内容、订单等业务表和约束 |
| BASE-DB-005 | 数据结构变化必须保护数据所有权和可恢复性 | 迁移包含升级验证、数据校验和失败恢复边界；不可逆变更必须具备已验证备份和专项确认 |

## 12. 本地开发、质量与部署目标需求

| 编号 | 需求 | 验收条件 |
| --- | --- | --- |
| BASE-OPS-001 | 提供 Windows 可复现的本地开发流程 | 使用 uv、pnpm、本机 PostgreSQL 和 Docker Desktop Redis，本地仅运行 Backend（8000）与 Admin（3001），完全禁止启动 Web 端服务与端口 |
| BASE-OPS-002 | 依赖必须由唯一锁文件管理 | 根目录只维护一份 `pnpm-lock.yaml`，Backend 只维护 `apps/backend/uv.lock` |
| BASE-OPS-003 | 每个应用必须具备可执行的质量能力和轻量自动门禁 | Backend 自动执行静态、类型、导入和契约检查，Admin 自动执行 Lint 和类型检查；Web 端已停用；构建与测试能力只在用户明确授权后运行 |
| BASE-OPS-004 | 跨栈契约变化必须保持机器契约一致 | OpenAPI 导出、API Client 生成、Breaking Change 和受影响前端类型检查进入同一计划；构建与测试结果仅在明确授权后补充 |
| BASE-OPS-005 | 应用必须具备容器化生产交付路径 | Backend、Admin 和 Web 可构建独立镜像，生产配置不打包真实密钥 |
| BASE-OPS-006 | 部署流程必须支持安全升级和失败恢复 | 数据迁移、镜像版本、健康检查、回滚和备份边界有可执行文档 |
| BASE-OPS-007 | CI 和发布必须分离 | Push 与 Pull Request 只执行轻量静态、契约、治理和安全检查；镜像发布与部署分别授权，发布所需制品构建不代表测试通过 |
| BASE-OPS-008 | CI 必须以 Fail Closed 方式处理已配置的自动门禁 | 空骨架、部分实现和完整应用状态可区分；轻量静态门禁、生成漂移、契约破坏和安全检查失败时必须停止，未获授权的构建与测试如实记录为未执行 |
| BASE-OPS-009 | 发布物和生产部署必须不可变且可验证 | 构建绑定完整 Commit SHA，镜像提供 SBOM 和构建来源证明，生产部署固定镜像 digest，禁止使用 `latest` 或缺失版本回退 |
| BASE-OPS-010 | 母版必须区分单机可恢复和多实例高可用部署 | 当前部署等级、适用边界、健康检查、回滚、备份恢复及故障转移要求有明确文档，单机部署不得宣称高可用 |
| BASE-OPS-011 | 派生项目必须按业务风险定义可靠性目标 | 生产前明确关键用户链路的 SLI、SLO、错误预算、RTO 和 RPO，并通过容量测试和恢复演练验证 |

## 13. 安全与质量要求

| 编号 | 需求 | 验收条件 |
| --- | --- | --- |
| BASE-SEC-001 | 密钥、令牌、密码和生产数据不得进入仓库 | 真实 `.env` 被忽略，`.env.example` 只含公开模板值 |
| BASE-SEC-002 | 认证、授权和输入校验必须在服务端生效 | 客户端状态和界面隐藏不能替代服务端权限判断 |
| BASE-SEC-003 | 日志和错误不得泄露敏感信息 | 凭据、完整令牌、密码和敏感个人数据不进入日志或响应 |
| BASE-SEC-004 | 高风险操作必须具备明确保护和回滚边界 | 数据删除、迁移、生产变更和发布需要目标核对及独立授权 |
| BASE-SEC-005 | 软件开发和供应链必须采用分层安全门禁 | 仓库定义漏洞报告、代码所有权和高风险评审；秘密、代码、依赖、容器和构建来源在对应阶段接受可重复检查 |
| BASE-SEC-006 | 认证、授权和高风险操作必须可审计 | 权限默认拒绝，资源授权在服务端结合资源状态执行，审计记录可关联请求和发布版本且不保存凭据或完整敏感载荷 |
| BASE-QUAL-001 | 母版不得通过假数据或静默降级伪装能力完成 | 未实现、失败、跳过和替代验证必须明确记录 |
| BASE-QUAL-002 | 已有功能、配置和 UI 行为必须在修改中得到保护 | 未经明确授权不得精简、替换或弱化既有能力 |
| BASE-QUAL-003 | 文本和配置资产必须具有稳定格式 | 源码、配置和文档使用 UTF-8 无 BOM并保留末尾换行 |
| BASE-QUAL-004 | 失败和故障隔离必须具有显式契约 | 禁止吞错、假成功、弱默认值和静默降级；允许的超时、有限重试、熔断、背压和只读状态必须可观测并具有恢复条件 |

## 14. 文档与治理目标需求

| 编号 | 需求 | 验收条件 |
| --- | --- | --- |
| BASE-DOC-001 | 项目必须维护全项目索引 | 能够定位项目身份、当前阶段、活动计划和权威入口 |
| BASE-DOC-002 | 项目必须维护产品需求基线 | 目标用户、适用场景、能力、非目标和验收要求集中且可追踪 |
| BASE-DOC-003 | 重大技术决策必须使用 ADR | ADR 记录选择理由和代价，PRD 不复制长篇技术比较 |
| BASE-DOC-004 | 实现类工作必须通过全栈计划追踪 | 计划关联需求编号，覆盖涉及与不涉及范围、风险、验证和用户确认 |
| BASE-DOC-005 | 项目自身计划及永久登记必须保留 | 母版永久保留全部计划；独立派生仓库只在初始化阶段允许用户人工一次性清理母版继承计划并重建索引，AI 不执行删除；初始化结束后永久保护派生项目全部计划 |
| BASE-DOC-006 | 当前文档和交付历史必须可导航并保持单一来源 | `docs/README.md` 登记全部专题项目文档，治理入口和历史载体保留稳定路径，`CHANGELOG.md` 记录已交付变化；GitHub Wiki 保持关闭且不维护文档副本 |

## 15. 明确非目标

以下内容不进入母版默认实现：

1. 商品、库存、购物车、订单、支付、促销和评价等电商领域。
2. 内容、栏目、媒体、审核、发布和版本等 CMS 领域。
3. 短信、微信、邮件营销、站内信和第三方消息推送等具体集成。
4. 特定支付渠道、物流渠道、搜索服务、对象存储或地图服务集成。
5. 超出通用 RBAC 的 ABAC、复杂组织树、多租户计费和数据权限模型。
6. 面向某个品牌的视觉、营销首页、文案和业务流程。
7. 生产数据、默认管理员凭据、真实域名、证书和平台密钥。
8. 为兼容任意框架而维护 Django、Nuxt、Vue、Java 或 .NET 的平行实现。

这些能力进入对应业务蓝图、派生仓库 PRD、ADR 和全栈计划。母版可以提供扩展位置，但不能提前写入单一业务假设。

## 16. 派生项目规则

1. 派生项目必须成为独立仓库，不建立指向母版绝对路径的运行时依赖。
2. 派生后立即在 `PROJECT_INDEX.md` 同时记录派生类型、母版不可变 Tag、完整 40 位 Commit SHA、阶段和业务范围。
3. 派生项目应更新 `docs/PROJECT_REQUIREMENTS.md`，增加自身目标用户、业务需求、非目标和验收标准，并明确哪些 `BASE-*` 需求继承、调整或不适用。
4. 安全、质量、契约和计划保护要求不得静默削弱。确需调整时，必须通过 ADR、全栈计划和用户确认记录原因。
5. 母版仓库中的计划原文及其在 `plans/INDEX.md` 中的登记记录永久保留。
6. 独立业务仓库只在派生初始化阶段允许用户人工一次性删除从母版继承的计划原文；AI 不得执行删除、移动或重命名。
7. 派生初始化必须保留 `plans/README.md`、`plans/INDEX.md` 和派生项目已经产生的计划。人工清理后按实际文件重建计划索引，不保留失效登记。
8. 派生初始化计划结束后，现存及后续新增的派生项目计划继续永久保留；母版计划通过母版仓库和派生仓库 Git 历史追溯。
9. 具体业务代码进入派生仓库，通用且经验证的能力可通过独立计划评估是否回馈母版。

## 17. 母版完成验收

母版达到“可用于稳定派生”的条件时，必须同时满足：

1. 本 PRD 中适用于母版的需求均有实现或明确的已确认豁免。
2. Backend、Admin 和 Web 可以按照本地开发文档独立启动，并具备各自轻量自动门禁及可按需执行的构建与测试能力。
3. Backend 契约能够导出并生成 API Client，两个前端可以消费同一契约。
4. 数据库可以从空库执行 Alembic 升级，测试环境具有防误连保护。
5. 三个应用具有可验证的容器构建和健康检查路径。
6. 认证、用户、管理员、RBAC 和 system 通用能力具有跨栈验收证据。
7. 桌面和移动端关键页面完成可访问性、文字、遮挡和横向溢出检查。
8. README、PRD、全项目索引、ADR、架构、运维、计划和 Changelog 与代码事实一致。
9. 根 `pnpm-lock.yaml` 和 `apps/backend/uv.lock` 已生成并能够复现依赖。
10. 真实密钥、生产数据、缓存和构建产物未进入版本控制。
11. CI 能够区分空骨架、部分实现和完整应用，轻量静态门禁与契约检查失败时停止，生成契约不存在未提交漂移，未获授权的重型验证明确记录为未执行。
12. 生产候选镜像绑定完整 Commit SHA、SBOM、构建来源证明和 digest，发布、部署与回滚记录能够关联同一不可变版本。
13. 模块依赖、安全供应链、备份恢复和部署等级均有可执行门禁或演练证据；尚未适用的项目明确记录状态，不能伪装成通过。

当前是否达到上述条件，必须综合实际源码、配置、迁移、生成契约、对应架构文档、计划验证结果和 `CHANGELOG.md` 判断；`PROJECT_INDEX.md` 用于定位当前阶段和活动计划，`plans/INDEX.md` 用于定位全部计划记录，两者不能单独证明能力已经实现。

## 18. 需求追踪规则

1. 新计划必须包含“关联需求”，引用一个或多个 `BASE-*` 编号；治理前置或无法对应需求时明确填写“无”及原因。
2. 新增、修改或取消产品能力时，必须先更新本 PRD 或在同一计划中列明 PRD 变更，并取得用户确认。
3. 技术实现变化但产品需求不变时，只更新计划、架构文档或 ADR，不机械修改 PRD。
4. 需求完成后，在计划中记录验证证据，并在 `CHANGELOG.md` 记录已交付能力。
5. 根项目索引只记录项目身份、当前阶段、活动计划和权威入口，不复制需求正文或详细实现状态。

## 19. 术语

| 术语 | 含义 |
| --- | --- |
| 母版 | 提供跨业务通用全栈能力、可用于创建独立项目的本仓库 |
| 派生项目 | 基于母版不可变 Tag 和对应完整 Commit SHA 创建，并加入具体业务能力的独立仓库 |
| 目标能力 | 本 PRD 规定母版最终需要达到的能力，不代表当前已完成 |
| 当前阶段 | 当前仓库所处的高层阶段和活动工作摘要，由 `PROJECT_INDEX.md` 维护 |
| 详细实现状态 | 当前仓库已经存在的具体能力和运行机制，以实际源码、配置、迁移、生成契约和对应架构文档为证据 |
| 全栈计划 | 面向整个 Monorepo，统一评估 Backend、Admin、Web 和跨栈范围的实施计划 |
| 权威来源 | 某类信息唯一允许维护完整事实的文件或生成链路 |
| Fail Closed | 前置条件、验证或依赖不满足时明确失败并阻止继续，不返回假成功或自动选择弱化路径 |
| 受控迁移窗口 | 为滚动升级临时保留的新旧契约重叠期，具有明确范围、期限、观测、回滚和删除条件 |
| 不可变发布物 | 内容由完整 Commit SHA 和镜像 digest 唯一确定，已发布内容不能在保持同一标识时被替换 |
| 单机可恢复模式 | 允许短时中断，通过不可变版本、备份、恢复验证和回滚控制风险的部署等级，不等同于高可用 |
