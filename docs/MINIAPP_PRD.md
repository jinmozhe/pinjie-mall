## 2. 产品目标、用户与成功标准

### 2.1 产品目标

1. 消费者只通过微信小程序完成商品浏览、身份建立、购物车、结算、支付、订单与售后操作。
2. 复用现有用户、商品、库存、交易、履约和分销领域，确保客户端、运营后台与渠道事实一致。
3. 弱网、重复提交、账号切换、通知延迟与进程退出后，用户仍能查询真实结果并继续处理。
4. 以可运营、可退款、可恢复和可追溯作为真实收款条件，不以页面完成或支付弹窗调起作为完成标准。

### 2.2 用户角色与使用场景

| 用户 | 核心场景 | 成功结果 |
| --- | --- | --- |
| 未登录访客 | 浏览分类、商品详情和公开评价 | 不强制登录即可查看公开商品；私有数据不被加载 |
| 登录消费者 | 管理地址、加购、结算、付款和查单 | 订单与付款结果可查，价格与服务端报价一致，无重复订单 |
| 已购消费者 | 查看发货、确认收货、申请退款和评价 | 仅操作本人且符合资格的订单，失败与处理中状态可解释 |
| 会员与推荐人 | 查看会员资料、推荐关系、佣金和钱包 | 只展示有权访问的真实记录，资金权利与后端一致 |
| 运营人员 | 上架、库存管理、发货、售后审核和异常核对 | 在 Admin 中完成必要操作，不依赖手工修改数据库 |

### 2.3 成功指标与证据

上线验收记录关键旅程的成功、拒绝、冲突和恢复用例，不能只给出首页截图或构建成功。产品观测覆盖商品详情到结算、结算到订单、订单到可信付款的转化，以及登录恢复失败、未知支付未决时长、订单超时积压、退款处理积压和重复业务事实数量。

转化指标只统计同一环境、时间窗口和明确事件口径，不预设未经业务数据支持的增长目标。重复订单、重复收款确认、重复佣金入账与跨账号数据泄露的验收容忍值为零。服务可靠性沿用[可观测性与可靠性基线](architecture/observability-reliability.md)，具体发布阈值和告警责任进入上线计划。

## 3. 范围、交付分组与非目标

### 3.1 建议交付分组

| 分组 | 范围 | 对外开放条件 |
| --- | --- | --- |
| E0 工程可行性验证 | Taro 工程、依赖解析、商品展示、SKU 弹层、请求与 Query、分包 | 只验证工程与组件；样例数据不计作真实业务验收 |
| R1 首个可交易版本 | 微信身份、商品分类与列表、详情、购物车、地址、结算、本人订单、微信支付、履约、退款、评价、资料与隐私入口 | 对应 Backend、Admin、迁移、渠道、恢复任务及真机验收均完成 |
| R2 会员分销体验 | 会员开通、推荐绑定与分享、佣金查询、双轨钱包、具备资金执行条件的提现 | 资格、资金闭环、审核和异常恢复已验证；未接通真实打款时不开放新的真实提现申请 |

R1 与 R2 表达开发顺序，不取消产品基线中的任何长期能力。已有推荐关系的佣金联动必须进入 R1 支付、履约和退款验证，不能因 R2 页面后做而跳过。

实物和虚拟商品继续遵守既有不同结算与履约语义。实际开放的商品类目、终端和支付方式必须在上线专项中按微信规则核对准入；未取得准入的组合不能进入真实支付，不得伪装成其他商品类型绕过限制。

### 3.2 本版非目标

- C 端 Web、H5、其他小程序平台和原生 App；不恢复 `apps/web`，不启动或暴露 3000 端口。
- 新建 Node 后端、云数据库、另一套会员体系，或重写现有商城领域。
- 优惠券、秒杀、拼团、复杂促销、游客购物车合并、实时物流轨迹、智能推荐、聊天客服和订阅消息运营。
- 会员折扣、消费钱包充值或支付抵扣、两类钱包互转；当前会员等级不改变成交价。
- 在微信小程序首版开放支付宝支付；后端长期渠道目标保留。
- 预设 Skyline、多套编译链、多套请求 SDK、整仓测试框架迁移或为每个基础控件增加无业务价值的包装。

用户帮助和售后联系信息属于 R1 必需的服务入口，不因此引入独立客服系统。业务扩展必须关联新计划和适用基线，不能仅凭 UI 示例自动加入范围。

## 4. 当前接入基础与事实边界

以下是 2026-09-17 的源码与契约快照，后续实施必须按最新实际文件重新核对。

| 范围 | 当前事实 | 对小程序的影响 |
| --- | --- | --- |
| Miniapp | 目录存在，尚无应用工程 | 需要独立初始化和完整治理接入 |
| 工程工具 | pnpm workspace、Turborepo、Node 24 基线、根锁文件、依赖观察期与安装脚本白名单 | 新应用沿用现有治理，不绕过 peer 冲突或全局强制统一 React |
| Admin | Umi Max、Ant Design、React 19、TanStack Query；通用基础页面已存在 | 保持组件体系；商城运营页面仍需建设 |
| 类型消费 | API Client 生成 Axios SDK 和类型；Admin 实际使用生成类型加应用内 fetch 管道 | Miniapp 可复用类型，独立使用 Taro 传输，不直接导入 Admin 源码 |
| 用户与会话 | 消费者认证读 Web Cookie；用户要求用户名和密码摘要；会话仅允许 browser_cookie | 微信首次建号、凭据能力和会话 Profile 需要专门设计与迁移 |
| 商城领域 | 商品、地址、购物车、报价、订单、履约、退款、评价、会员分销已有本地实现 | 可复用领域，仍须适配身份与补充页面所需查询 |
| 外部资金 | 支付创建返回 unavailable；没有真实支付回调适配器；真实退款和提现打款未接通 | 页面接入不能证明收款或资金退出可用 |
| 运维与数据 | 存在迁移文件和显式扫描命令，历史交付记录未包含实际迁移及完整动态验证 | 上线前独立验证数据库、权限和任务运行，不能假定命令已被调度 |

## 5. 信息架构与关键旅程

### 5.1 页面与入口

建议主导航为“首页、分类、购物车、我的”。这是产品信息架构，不预先固化目录实现；TabBar 入口与主包、分包约束在工程阶段验证。

| 页面组 | 入口与内容 | 登录要求 |
| --- | --- | --- |
| 首页与分类 | 商城基础信息、公开分类、分页商品列表；首版不依赖营销装修系统 | 无 |
| 商品详情 | 图片、名称、规格、价格、售卖状态、商品类型、公开评价和购买入口 | 浏览无；加购或购买时登录 |
| 购物车 | 本人条目、选择、数量、失效原因、结算入口 | 有 |
| 结算与地址 | 明细、本人地址、配送资格、运费、总额、报价变化提示 | 有 |
| 订单与支付结果 | 本人列表、详情、付款结果、取消、履约和售后入口 | 有 |
| 售后与评价 | 可申请条目、申请结果、进度、评价资格与提交反馈 | 有 |
| 我的与设置 | 资料、地址、订单、账户安全、退出、注销、隐私与帮助入口 | 公共说明无；账户内容有 |
| 会员分销 | 档案、推荐关系、分享、佣金、钱包与提现记录 | 有，并执行服务端资格校验 |

### 5.2 关键用户旅程

1. 浏览商品，选择有效规格和数量；触发加购或购买时完成身份建立，恢复原商品与选择意图，不自动提交写操作。
2. 从购物车或立即购买进入结算，按商品类型选择地址，获取服务端报价；用户确认后提交同一业务请求。
3. 订单创建后发起支付；无论平台返回成功、取消或失败，用户均可返回订单查询后端权威状态。
4. 查看实物物流单号或虚拟交付信息；符合条件时确认收货、提交评价或按明细申请退款。
5. 进入会员页面主动开通或查看档案；确认推荐绑定后按资格查看佣金、钱包和提现处理结果。

页面返回、应用前后台切换与登录恢复分别保存必要的非敏感交互状态。过期价格、地址与订单状态必须重新读取，不能恢复为可直接成交的旧报价。

## 6. 功能需求

### 6.1 身份、资料与隐私

| 编号 | 需求与验收条件 | 分组 | 基线 |
| --- | --- | --- | --- |
| MP-AUTH-001 | 使用微信一次性 code 经 Backend 建立可信身份，映射现有 user_id；不接受客户端声明的 OpenID、昵称或手机号作为合并账户依据 | R1 | BASE-BE-003、BASE-MP-001 |
| MP-AUTH-002 | 公开浏览不强制登录；私有动作失败或取消登录后保持未登录，原页面可继续使用；完成登录只恢复操作上下文，不自动下单或绑定推荐人 | R1 | BASE-BE-003 |
| MP-AUTH-003 | 凭据过期采用单次并发恢复；恢复失败明确反馈，网络故障不伪装成退出；主动退出成功后停止自动恢复，直到用户再次发起登录 | R1 | BASE-BE-002、BASE-BE-003 |
| MP-AUTH-004 | 停用、撤销和合法账号切换后取消旧请求、清除私有缓存并阻止旧响应回填；账户只能访问本人地址、订单、售后及资金数据 | R1 | BASE-BE-003 |
| MP-AUTH-005 | 本人资料、头像、账户安全和注销适配微信账户的凭据能力；不要求无密码账户输入不存在的密码，也不设置公共默认密码绕过模型 | R1 | BASE-BE-003 |
| MP-PRIV-001 | 提供隐私说明与必要授权说明，按实际动作请求所需权限；拒绝非必要权限不阻断公开浏览；注销说明明确历史交易保留边界，不宣称立即物理删除全部数据 | R1 | BASE-BE-003、BASE-QUAL-001 |

身份专项启动时，必须在活动计划中确定首次建号与现有注册开关的关系、已有账户可验证绑定流程、会话与存储策略、退出与冷启动恢复规则。当前用户名、密码摘要和 Session 约束是迁移影响，不能只新增登录路由后继续复用浏览器会话。

### 6.2 商品、规格与购物车

| 编号 | 需求与验收条件 | 分组 | 基线 |
| --- | --- | --- | --- |
| MP-CAT-001 | 首页和分类分页展示公开可见商品；切换分类重置对应分页，空分类、无商品、加载失败可区分；分类过滤由服务端提供，不能只过滤当前页冒充完整结果 | R1 | BASE-COM-001 |
| MP-CAT-002 | 详情呈现商品图片、类型、规格、价格及不可售原因；缺失、下架和无库存具有明确反馈，不暴露成本和内部管理字段 | R1 | BASE-COM-002、BASE-COM-003 |
| MP-CAT-003 | SKU 选择基于已加载数据推导可选组合，无规格商品使用默认 SKU；选择变更同步数量和展示价格，提交后仍接受服务端可售与库存校验 | R1 | BASE-COM-002、BASE-COM-004 |
| MP-CART-001 | 登录购物车以服务端为权威，支持加入、选择、数量修改和删除；无效条目单独提示，禁止用缓存总额作为成交金额 | R1 | BASE-COM-101 |
| MP-CART-002 | 条目更新携带 revision，冲突时重新读取并提示用户确认；加购等写请求超时不得盲目重放造成重复数量 | R1 | BASE-COM-101、BASE-QUAL-001 |

分类导航属于首版范围；关键词搜索与多种排序不因输入框示例自动纳入首版。当前购物车响应主要包含 SKU 标识、数量、选择和版本，页面还需要商品展示信息及不可售原因，应通过明确查询视图或有界批量查询补齐，避免每条购物车触发一组无界请求。

### 6.3 地址、报价与下单

| 编号 | 需求与验收条件 | 分组 | 基线 |
| --- | --- | --- | --- |
| MP-ADDR-001 | 本人地址支持新增、编辑、默认设置、选择和删除；遵守现有数量及默认地址约束；无地址、地址失效和配送区域不支持均提供可操作反馈 | R1 | BASE-COM-005、BASE-COM-006 |
| MP-CHK-001 | 结算统一使用服务端预览，展示商品小计、运费和应付总额；实物使用本人地址，虚拟商品不索取配送地址；不同商品类型不能混合提交 | R1 | BASE-COM-101、BASE-COM-103 |
| MP-CHK-002 | 地址、数量或其他影响报价的输入改变后重新预览；提交使用 quote_fingerprint，报价冲突返回确认步骤；零应付及超出金额边界的订单按服务端规则拒绝 | R1 | BASE-COM-101、BASE-COM-102 |
| MP-CHK-003 | 同一次提交保持业务 request_id 与内容不变；超时显示结果确认中，通过已定义的查询或安全同键重放恢复，不新建请求号重复下单 | R1 | BASE-COM-102、BASE-COM-105 |

金额以契约规定的十进制字符串消费和展示，不使用前端浮点计算决定运费、优惠、支付或佣金。业务幂等号与响应中的请求追踪标识分别管理。结算草稿只保存恢复意图所需信息，不把完整地址和付款敏感数据默认持久化。

### 6.4 订单、支付与履约

| 编号 | 需求与验收条件 | 分组 | 基线 |
| --- | --- | --- | --- |
| MP-ORD-001 | 提供本人订单分页、状态筛选和详情；状态组合由后端明确提供或由已定义契约映射，不能用当前页数据伪造全量数量与筛选结果 | R1 | BASE-COM-103、BASE-COM-105 |
| MP-ORD-002 | 订单详情展示历史快照、应付及支付事实、履约和售后入口；待付款取消与支付并发按服务端结果处理；倒计时只作提示，客户端到零不能自行取消订单 | R1 | BASE-COM-103、BASE-COM-104、BASE-COM-105 |
| MP-PAY-001 | Backend 持久化支付意图并返回微信调起参数；小程序只调用平台支付，不生成金额、商户签名或保存商户秘密；未启用渠道明确不可用 | R1 | BASE-COM-201 |
| MP-PAY-002 | 平台支付返回后查询商城后端；成功、取消、失败和超时均不能直接决定订单资金状态；结果未知可继续查询和人工求助，不诱导重复支付 | R1 | BASE-COM-202 |
| MP-PAY-003 | 通知验签、查单、关单、重复通知、迟到通知和退款补偿形成可恢复链路；可信付款与本地取消冲突不能通过丢弃通知或前端改状态解决 | R1 | BASE-COM-104、BASE-COM-201、BASE-COM-202 |
| MP-FUL-001 | 实物订单展示发货事实、承运人和运单号，确认收货校验当前版本；虚拟订单展示已授权的交付信息，未交付不显示已完成 | R1 | BASE-COM-203 |

## 7. 通用交互与异常恢复

### 7.1 状态与交互要求

所有数据页面提供加载、空数据、失败、无权访问与成功状态。刷新失败保留可识别的旧展示并说明未更新，涉及交易确认时必须取得有效权威数据。禁止用空列表代替请求失败。

提交操作防止重复点击，显示执行状态；删除地址、购物车条目、取消订单、确认收货和注销等动作明确后果，提交失败保留用户输入及目标。敏感操作不因页面恢复而自动执行。设计统一品牌色、价格色、状态色、字体、间距、安全区和反馈文案，适配小屏、长文本、键盘弹起与底部操作区，不套用后台表格布局。

| 编号 | 场景 | 预期行为 | 基线 |
| --- | --- | --- | --- |
| MP-UX-001 | 页面首次加载、无数据、请求失败 | 三种状态明确区分，失败提供重试且不伪造业务结果 | BASE-BE-002、BASE-QUAL-001 |
| MP-UX-002 | 写操作进行中、超时或被拒绝 | 禁止重复提交；超时保留原业务意图，按该接口的确认策略恢复 | BASE-COM-102、BASE-COM-202 |
| MP-UX-003 | 前后台切换、返回页面、网络恢复 | 定向刷新相关数据；隐藏页面停止无意义轮询；离线不执行交易写队列 | BASE-QUAL-001 |
| MP-UX-004 | 小屏、长文案、键盘和安全区 | 关键按钮可见可操作，不遮挡输入和金额，不只用颜色传达状态 | BASE-MP-001 |

### 7.2 关键异常矩阵

| 场景 | 用户可见结果 | 恢复与验收 |
| --- | --- | --- |
| 明确凭据失效 | 正在恢复登录或需重新登录 | 同时发起的请求共享恢复任务，限定重放，恢复接口不递归 |
| 429、503、断网 | 限流或服务暂不可用 | 保留错误类别、重试提示与追踪标识，不直接清除登录状态 |
| SKU 失效或库存不足 | 指明受影响商品，停止成交 | 刷新商品或结算，不自动替换规格或减少购买数量 |
| 购物车版本冲突 | 条目已更新，请重新确认 | 读取最新 revision，不静默覆盖其他设备修改 |
| 报价变化 | 展示新报价并要求确认 | 不携带旧 fingerprint 继续提交，不静默提高扣款金额 |
| 下单返回丢失 | 订单结果确认中 | 复用原 request_id 恢复；契约未提供确认方式时不得上线该流程 |
| 支付取消或平台报错 | 返回订单，按后端状态显示 | 取消支付弹窗不自动取消商城订单 |
| 付款成功但通知延迟 | 支付结果确认中 | 有限查询、后台主动查单与运营升级，不要求再次付款 |
| 已取消订单收到可信付款 | 异常资金处理中 | 持久化渠道事实、查询与核对，不得直接将已释放库存订单改为已支付；按已审定补偿路径退款或转人工处理 |
| 退款结果未知 | 退款处理中，可查询 | 保留申请和资金占用，渠道核实前不显示到账或重新申请相同额度 |
| 退出后旧请求返回 | 保持未登录或新账号界面 | 旧请求无法写入新账号缓存，后台也拒绝越权访问 |
| 分享参数失效或目标已下架 | 明确失效提示 | 可返回商城，不自动创建推荐关系或伪造商品 |

“人工处理”必须具备责任人、告警、处理记录和最终资金确认，不能作为永久搁置未知结果的兜底状态。

### 9.3 工程设计与技术约束入口

目录树、Feature 内聚、公开入口、商品详情到加购的完整调用链，以及状态、请求、认证和平台能力的协作统一维护在[小程序目录与应用架构](architecture/miniapp-architecture.md)。该文档承接本 PRD 的工程设计，避免产品需求中复制一套不断变化的文件结构。
