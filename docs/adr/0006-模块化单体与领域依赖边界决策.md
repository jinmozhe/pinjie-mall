# ADR 0006: 模块化单体与领域依赖边界决策

- 状态：已确认
- 日期：2026-08-13
- 决策者：大仙
- 当前机制：[模块与依赖边界](../architecture/module-boundaries.md)

## 背景

母版需要承载认证、用户、管理和系统等跨业务通用能力，并允许派生项目增加独立业务领域。当前团队、流量和部署边界尚未形成，直接拆分微服务会引入网络故障、分布式事务、部署编排和跨服务追踪成本。只使用目录约定又无法阻止跨领域访问 Model、Repository 和内部 Service，长期会破坏数据所有权。

## 决策

Backend 采用模块化单体。每个领域拥有自己的协议入口、应用服务、领域规则、持久化适配和数据表，通过公开 Application Service、Port、DTO 或领域事件与其他领域协作。

依赖规则如下：

1. Router 只能调用应用服务，禁止直接访问 Repository、Model 或数据库 Session。
2. Repository 只实现持久化，不包含权限或业务决策，不控制事务提交。
3. 领域不得导入其他领域的 Repository、Model 和内部 Service。
4. 跨领域写流程进入 `app/services/` 编排层，领域只能写入自己拥有的数据表。
5. 普通写模型禁止跨领域 JOIN；报表、搜索和只读聚合通过明确的 Query Service 或 Read Model 实现。
6. Web 和 Admin 保持独立应用；Feature 只能通过公共入口协作，不得导入其他 Feature 内部文件。
7. 依赖规则必须由静态门禁或架构测试验证，不能只依赖人工评审。

完整规则见 [模块与依赖边界](../architecture/module-boundaries.md)。

## 备选方案

### 直接采用微服务

拒绝。当前没有独立团队、独立扩缩容和独立发布证据，分布式成本高于收益。

### 自由分层单体

拒绝。缺少领域所有权和自动依赖门禁，容易形成共享数据库与跨域内部调用。

### 每个领域独立数据库

暂不采用。母版默认使用同一 PostgreSQL 实例和数据库，通过表所有权和代码边界隔离。未来服务拆分时再评估物理数据库隔离。

## 后果

### 收益

- 领域规则、数据和测试保持高内聚。
- 单进程事务和本地调用保持简单。
- 依赖违规可以在合并前被机械拒绝。
- 未来具备真实拆分需求时，公开 Port 和数据所有权提供清晰边界。

### 代价

- 需要维护公开接口和架构测试。
- 跨领域报表必须使用明确的只读模型，不能随意 JOIN 内部表。
- 共享基础设施必须保持业务中立，不能成为绕过领域边界的公共杂物层。

## 服务拆分准入

只有同时具备独立团队或所有者、独立发布节奏、独立扩缩容需求、明确数据所有权、可接受跨服务一致性模型和完整可观测能力时，才允许通过新 ADR 评估拆分。目录数量或代码行数不能单独作为拆分依据。
