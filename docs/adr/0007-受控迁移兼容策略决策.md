# ADR 0007: 受控迁移兼容策略决策

- 状态：已确认
- 日期：2026-08-13
- 决策者：大仙
- 当前机制：[错误模型与契约边界](../architecture/error-model.md)

## 背景

项目要求禁止兼容层，目标是避免长期双轨、自动猜测协议和历史包袱。数据库、API 和事件契约在滚动发布期间仍可能需要短期新旧版本重叠。完全禁止任何兼容窗口会迫使所有消费者锁步发布或停机切换，与高可用目标冲突。

## 决策

禁止永久兼容、隐式兼容、自动猜测版本和无期限双字段或双写。允许经过计划或 ADR 批准的短期 Expand、Migrate、Contract 迁移窗口。

临时兼容必须登记：

- 负责人和受影响消费者。
- 开始日期、删除日期和最长允许期限。
- 新旧契约、数据或行为的准确范围。
- 使用量、错误率或迁移完成度等观测指标。
- 回滚条件、数据校验方法和删除测试。
- 清理任务及完成证据。

任何缺少上述信息的兼容代码不得合并。删除日期到期时，继续保留必须重新取得用户确认并更新原计划，不能默认延期。

## Breaking Change 定义

以下变化默认视为破坏性变更：

- 删除字段、端点、事件或公开导出。
- 改变字段类型、空值语义、单位、枚举含义或默认行为。
- 改变 HTTP 方法、路径、认证要求或错误契约。
- 收紧调用方可见的校验和权限约束。
- 改变数据库列语义、唯一性或历史数据解释方式。

跨栈破坏性变更必须在同一计划中完成 Backend、OpenAPI、API Client、Admin、Web 和数据库影响评估。尚未完成迁移的消费者不得依靠未登记的兼容分支继续运行。

已获批准的破坏性契约变化可通过有期限的精确 CI 例外登记，操作、字段与清理规则见 [GitHub Actions 工作流说明](../operations/github-actions-workflows.md#8-受控-openapi-例外)。例外只处理静态门禁的已审查诊断，不替代消费者迁移、发布顺序、回滚或本 ADR 的兼容窗口要求。

## 备选方案

### 零兼容窗口

仅适用于可接受停机且所有消费者能够原子切换的场景，不作为母版默认规则。

### 永久多版本 API

拒绝作为默认方案。只有未来出现独立发布的外部消费者，并且有明确版本生命周期、所有者和退役策略时，才通过新 ADR 评估。

## 后果

- 滚动发布可以在受控期限内安全完成。
- 每项兼容都有删除责任和可核验证据。
- 发布计划需要额外记录迁移顺序和观测指标。
- 紧急延期不能静默发生，会显式占用维护成本并接受评审。
