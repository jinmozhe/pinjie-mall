# ADR 0010: 浏览器认证、会话、RBAC 与审计决策

- 状态：已确认并实施
- 日期：2026-08-15
- 决策者：大仙
- 当前机制：[认证、授权与审计边界](../architecture/authentication-authorization.md)

## 背景

母版需要同时支撑 C 端账户和 B 端管理控制台，并为未来小程序、原生 App、微信公众号及微信内网页保留扩展位置。浏览器、公开客户端和服务端调用的凭据暴露面不同，不能用一种传输方式覆盖所有客户端。

两个参考后端都提供了 JWT、Refresh、用户、管理员、RBAC、登录日志和审计能力，但存在共享 Token 边界、权限 JSONB、动态菜单、Refresh 明文风险、中间件按 URL 推断审计语义以及安全记录失败后放行等问题。本仓库需要保留成熟功能面，同时满足默认拒绝、数据库权威、失败关闭和跨端隔离要求。

## 决策

### 客户端认证 Profile

1. 阶段 C 只开放 Browser Cookie Profile。Web 与 Admin 的 Access、Refresh 和 CSRF 凭据通过同域 Cookie 工作，登录响应不返回 Token 字段。
2. Access 与 Refresh Cookie 使用 `HttpOnly`，生产使用 `Secure`，`SameSite=Lax`，不设置 `Domain`。CSRF Cookie 允许浏览器读取，但只保存与 Session 绑定的随机值。
3. Token 不进入 `localStorage`、`sessionStorage`、Zustand、URL、页面源码或日志。
4. 未来小程序和原生 App 使用独立 Public Client Bearer Profile。该 Profile 必须有独立端点、Session 类型、客户端证明、存储、轮换、撤销和测试契约，不能复用浏览器登录响应临时返回 JSON Token。

### JWT 与主体隔离

1. 使用 PyJWT 和固定 `HS256` 算法 allowlist。C 端与 B 端分别使用 `WEB_JWT_SECRET`、`ADMIN_JWT_SECRET` 以及 `pinjie-web`、`pinjie-admin` audience。
2. C 端 Access 有效期 15 分钟，B 端 10 分钟，允许最多 30 秒时钟偏差。
3. 必需 Claims 为 `iss`、`aud`、`sub`、`sid`、`jti`、`iat`、`nbf`、`exp`、`token_type` 和 `credential_version`。JWT 不保存角色、权限、邮箱或其他个人资料。
4. 验签完成后仍必须校验 PostgreSQL Session、主体状态和凭据版本。JWT 自身有效不能代替服务端会话状态。

### 密码、Session 与 Refresh

1. 密码使用 Argon2id。Hash 和 Verify 进入线程池，并受进程内有界并发控制，避免阻塞异步事件循环。
2. PostgreSQL 是 Session 和 Refresh Token 的权威来源。Redis 只保存短期 Session 缓存、限流、互斥和请求元数据 Stream。
3. Refresh Token 使用 48 字节随机值，数据库只保存 HMAC-SHA256 摘要。闲置期限为 7 天，会话绝对期限为 30 天。
4. Refresh 通过 PostgreSQL 行锁单次消费并旋转。已消费 Token 再次出现时撤销整个 Session Family并记录高严重度登录安全事件。
5. 用户或管理员的密码、状态、角色、超级管理员标记变化时递增 `credential_version` 并撤销相关会话，确保收权立即生效。

### CSRF 与来源校验

1. Cookie 身份的 `POST`、`PUT`、`PATCH` 和 `DELETE` 同时校验精确 Origin allowlist 与 `X-CSRF-Token`。
2. CSRF Token 与 Session 绑定，Cookie 保存原值，PostgreSQL 保存 HMAC 摘要，比较使用常量时间函数。
3. 登录和注册没有既有 Session，仍执行 Origin 校验，并结合 SameSite Cookie 和 Redis 限流降低登录 CSRF 与撞库风险。

### RBAC 与管理操作确认

1. 权限目录由源码中的类型化 `PermissionCode` 和 `PERMISSION_CATALOG` 维护，通过显式 CLI 同步数据库。运行时不自动创建、删除或猜测权限。
2. 角色、权限、管理员与关联关系使用规范化表和外键。阶段 C 不建立动态菜单表，Admin 导航由前端路由目录按服务端权限过滤。
3. Dependency 校验端点权限，Service 在事务内结合目标状态执行最终资源授权。前端隐藏按钮不承担安全控制。
4. 管理操作不使用密码二次确认 Token。超级管理员不绕过 Session、CSRF、最后超级管理员保护和审计；Admin 删除与移除操作使用统一标准警告弹窗确认操作者意图，适用范围与提交保护遵守 [Admin 工程实施标准](../architecture/admin-engineering-standard.md)。

### 安全事件、审计与请求日志

1. 登录安全事件是认证结果的一部分，写入失败时登录或刷新失败关闭。
2. 高风险业务先建立类型化审计意图，成功变更与审计完成在同一数据库事务内提交。拒绝和异常通过独立终结器写入 `denied` 或 `failed`；无法终结时保留 `started` 并输出 critical 信号。
3. 普通访问日志使用结构化输出，不承担审计职责。
4. 可选请求持久化只支持 `metadata` 模式，通过 Redis Stream、Consumer Group、pending reclaim、DLQ 和 PostgreSQL `request_id` 唯一约束工作。正常请求不保存请求体；错误 JSON 请求仅在非敏感路由捕获，敏感字段递归替换为 `***`，最多保存 4096 个字符并附加截断标记。登录和改密等敏感路由、响应体、Cookie、Authorization 和 Token 永不进入请求日志。

## 备选方案

### 所有客户端统一 Bearer Token

该方案实现表面统一，但会迫使浏览器 JavaScript 持有 Token，扩大 XSS 后果，并把小程序与网页的安全边界混在同一契约中，因此不采用。

### C/B 共享 Secret 或 Session 表

共享可以减少配置和表数量，却会扩大单个密钥泄露、audience 校验缺陷和管理端攻击的影响范围，因此不采用。

### 权限 JSONB 与数据库动态菜单

JSONB 和动态菜单适合部分强配置化系统，但会弱化权限外键、索引、重命名一致性和源码路由审查。母版阶段使用规范化 RBAC 与代码导航，复杂菜单进入派生项目计划。

### 中间件统一推断业务审计

中间件无法可靠理解资源状态、业务动作和事务结果。它只负责请求上下文与访问元数据，业务审计由 Router 声明意图并由 Service 完成。

## 影响

- Backend 必须配置四个互不相同且至少 32 字节的 JWT/HMAC Secret；生产缺失时拒绝启动。
- Web 与 Admin 必须使用同域 `/api/v1`，并由公共 HTTP 层处理 CSRF、Refresh 并发和会话失效。
- 权限目录变化需要运行 `scripts.sync_permissions --check`，经授权后再 `--apply`。
- 请求元数据 Worker 只在 `REQUEST_LOG_MODE=metadata` 时启动；功能关闭时不运行空闲消费者。
- 短信、微信、邮箱登录、找回密码、MFA、ABAC、多租户和 Public Client Bearer Profile 仍是后续派生能力。

## 验证

阶段 C 已通过以下自动化边界：

- 独立 PostgreSQL 18.4 `_test` 数据库与 Redis 8.10.0 集成测试。
- JWT Claims、C/B 隔离、Cookie、CSRF、Refresh Rotation、重放、限流、收权和审计失败路径。
- Admin 与 Web 单元和组件测试、生产构建、真实 Chromium 桌面与移动跨栈 E2E、axe、键盘焦点和无 Token 持久化检查。
- Backend、Admin 和 Web Linux 容器镜像本地构建。

完整端点、数据模型和测试矩阵保存在关联计划；当前运行机制以[认证、授权与审计边界](../architecture/authentication-authorization.md)为准。
