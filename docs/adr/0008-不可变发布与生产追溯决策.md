# ADR 0008: 不可变发布与生产追溯决策

- 状态：已确认
- 日期：2026-08-13
- 决策者：大仙
- 当前操作：[发布与回滚手册](../operations/release-and-rollback.md)

## 背景

现有发布工作流在 `main` 推送后直接构建和部署，并使用 `latest` 标签。相同标签可以指向不同内容，生产环境无法仅凭标签确认实际代码，也难以证明镜像由哪次受检构建产生。CI、镜像发布和部署混在同一工作流还会扩大令牌和生产密钥的权限范围。

## 决策

采用不可变发布和职责分离：

1. CI 只验证代码、契约、迁移、构建和安全门禁，不发布或部署。
2. 镜像发布使用独立人工触发工作流，输入完整 40 位 Commit SHA，并验证检出的提交完全一致。
3. 镜像标签至少包含 `sha-<commit>`，同时记录镜像 digest、SBOM 和构建来源证明。
4. 当前生产由单维护者在 1Panel 人工更新编排，固定三个应用的完整镜像 digest，禁止使用 `latest`、分支标签或缺失版本回退。旧 GHCR `Deploy Production` 工作流不参与当前 TCR 部署路径。
5. 当前人工部署保留执行者、时间、输入版本和结果记录，同一环境只允许一个发布或回滚操作。仓库中保留的生产工作流继续受 GitHub Environment 和并发锁保护，但不作为当前人工部署入口。
6. Git Tag、GitHub Release、镜像发布、生产部署和回滚继续作为独立授权动作。
7. 正式母版版本默认评估 SemVer。采用 CalVer 或其他方案必须新增 ADR，不能由构建脚本自行决定。
8. GitHub 继续作为权威代码仓库和验证平台。人工源码交接入口校验完整 Commit SHA 和四个轻量 Push Run，并提供默认 `strict`、可显式选择 `fast` 的验证模式。`strict` 必须核对同 SHA Full Validation Artifact；`fast` 必须由操作人员明确选择、填写单行原因并留下 Workflow Summary，且不能表述为完整验证通过。两种模式都继续校验默认分支祖先、应用完整状态和模块边界，只以非强制快进方式把提交交接到 CNB `main`，不在 GitHub Runner 构建或上传生产镜像层。
9. CNB 社区版在腾讯侧使用 `backend-image`、`web-image` 和 `admin-image` 三条独立 Pipeline，按真实 Docker 构建输入选择需要构建的应用。每条 Pipeline 独立执行 Trivy、CycloneDX SBOM、BuildKit provenance、单镜像结构化发布清单和 TCR 写后 digest 复核。TCR 个人版是当前唯一生产镜像源，不能宣称具备企业版 SLA、服务端不可变和完整操作审计能力。
10. 每条 CNB Pipeline 使用默认 Buildx `docker` 驱动，以 `candidate-<CNB Build ID>` 唯一候选标签向对应 TCR 仓库推送镜像，同时保存并核对内容 digest；候选标签只用于本次发布门禁，禁止部署。单镜像通过扫描和证据检查后，才检查并创建该仓库的 `sha-<完整 Commit SHA>` 标签。候选标签已存在或已有 SHA 标签指向不同 digest 时失败，禁止覆盖。
11. CNB 构建工具镜像和扫描器固定 digest，TCR 发布凭证只从受限密钥仓库导入。GitHub 的 CNB 写入 Token、CNB 的 TCR 固定密码和生产只读凭证分别保存，不跨系统复用。
12. CNB 从 `CNB_COMMIT` 读取 Git committer time，设置为 `SOURCE_DATE_EPOCH`，并写入 OCI `revision`、`created` 和 `source` 标签。这样 1Panel 能显示可解释的镜像创建时间，同一 Commit 重建仍使用相同时间；不同 Commit 的 COPY 层可能因时间变化减少缓存命中，按应用独立构建控制该成本。
13. 同一 Commit 影响多个应用时，全部预期 Pipeline 的单镜像证据必须成功且 Commit SHA 完全一致。只影响一个应用时允许独立发布该端，未改动端保留既有已验证 Commit 与 digest；人工核对来源、镜像 digest、扫描结果及跨端契约和数据库兼容性后进入独立授权的部署，不要求最终三端候选验收工作流。
14. `.cnb/web_trigger.yml` 只在 `main` 分支提供受控三端全量构建按钮，用于首次运行、变更文件超过平台统计上限、Git 对比不可用或影响范围存疑的情况。人工入口复用三个固定应用 Pipeline，不接受任意镜像名、分支或 Commit 输入。
15. 已验证的 GitHub GHCR/TCR 双仓发布 Commit `8f341586dfe5d6a22894fe1410959d4ef7599202`、旧 `pinjie-cnb-tcr-release-v1` 附件和既有镜像保留为迁移回滚基线。新发布使用 `pinjie-cnb-tcr-image-v1` 单镜像证据；新发布不再要求 GHCR 与 TCR 同步或 digest 相等，旧工作流设计继续由 Git 历史保留，不再作为并行发布入口。

## 当前人工部署决策

单端发布证据继续使用 `pinjie-cnb-tcr-image-v1`。默认严格交接继续要求同 SHA Full Validation，新版 v2 明确验证 Admin Nginx dist 与 Web standalone。GitHub main 到 CNB main 使用统一串行组，并保存真实交接模式、理由及验证 Run 的 Artifact。

2026-09-06 确认：当前项目采用单维护者、1Panel 人工部署，取消候选镜像验收和自动变量预检的流程要求。额外维护 GitHub 只读凭据、请求 JSON、隔离测试环境和部署组合清单，会增加当前操作成本；按实际场景使用 CNB/TCR 人工核验、固定 digest、回滚记录和上线复验。此决策不限制派生项目根据自己的风险重新评估验证需求。

维护者核验 CNB 单镜像证据与 TCR 完整 digest 后，同步服务器根 `.env` 和 1Panel 编排变量，再保存编排并检查实际运行版本、健康及关键业务。生产镜像构建和服务器拉取继续处于 CNB、TCR、腾讯云链路，部署不重建镜像。Full Validation 和人工上线检查不能证明最终 TCR 镜像组合已通过独立自动 E2E，这部分覆盖不再作为当前部署前置条件。

具体操作与发布记录以[端到端人工发布手册](../operations/github-cnb-tcr-1panel-release-runbook.md)为准。现存候选验收工作流与工具不纳入当前流程，本次文档调整不删除或禁用其代码。生产、回滚、证明文件和 OCI 引用链必须受到保留保护，真实删除继续独立授权。

## 追溯链

```text
需求编号
-> 实施计划
-> ADR 或威胁模型
-> Pull Request 与评审
-> Commit SHA
-> CI 运行与结果
-> SBOM 和构建来源证明
-> 镜像 digest
-> Alembic Revision
-> 1Panel 人工部署记录
-> release.version
-> request_id、trace_id 和 audit_id
```

普通开发提交继续以 Git 历史为权威来源，不把每个 SHA 重复写入项目文档。只有发布、部署、回滚、安全审计和派生基线等跨系统记录保存完整 SHA 或不可变 Tag。

## 部署等级

- 单机可恢复模式：允许短时中断，通过不可变版本、备份、恢复验证和快速回滚控制风险。
- 多实例高可用模式：增加多实例、负载均衡、数据层高可用、故障转移和滚动发布。

当前 Compose 属于单机可恢复模式，不能宣称高可用。

## 备选方案

### 继续使用 `latest`

拒绝。标签可变，无法作为生产证据或可靠回滚目标。

### 仅使用 Git Tag

拒绝作为部署唯一标识。Tag 指向源代码，不唯一描述镜像构建环境和最终 OCI 内容；生产仍需固定 digest。

### `main` 推送自动部署

拒绝作为母版默认方案。生产部署必须经过独立授权、环境保护和不可变版本确认。

## 后果

- 任意生产版本都能追溯到源代码和构建证据。
- 回滚可以重用已验证 digest，无需重新构建旧代码。
- GitHub 只传输 Git 对象，镜像层在腾讯侧构建并推送 TCR，避免 GitHub Runner 到 TCR 的跨境大文件上传瓶颈。
- 发布和部署步骤继续使用明确输入与独立授权，CNB 社区版额度耗尽或共享节点异常会显式阻断发布。
- 需要维护镜像保留策略、部署记录和环境保护配置。
