# Admin 工程实施标准

## 目标与权威关系

本文定义 `apps/admin` 在 Ant Design Pro v6/Umi Max 体系内的具体实施方式，适用于页面、Feature、请求、状态、组件和依赖变更。长期强制红线以 `apps/admin/AGENTS.md` 为准，采用 Umi Max 的技术取舍以 [ADR 0011](../adr/0011-Admin采用AntDesignProV6与UmiMax决策.md) 为准；认证授权、模块边界和测试语义继续分别以 [认证授权架构](authentication-authorization.md)、[模块边界](module-boundaries.md)和[测试策略](testing-strategy.md)为准。

本标准不固定 Umi 内部依赖的精确版本，也不要求所有页面使用同一种 ProComponents 高阶组件。

## 框架与项目边界

| 能力 | 权威所有者 | 实施要求 |
| --- | --- | --- |
| 路由、布局、运行时生命周期 | Umi Max | 使用 `config/routes.ts`、`src/app.tsx` 和 `@umijs/max` 公共入口 |
| 客户端 Access | Umi Max + 项目权限映射 | 用于路由、菜单和控件显隐，不代替服务端授权 |
| UI 与主题 | Ant Design、ProComponents | 优先使用兼容组件，按交互和性能选择抽象层级 |
| OpenAPI 类型 | `@pinjie/api-client` | 由根契约生成，禁止复制 DTO 或生成第二套契约 |
| HTTP 传输 | `src/lib/api/http.ts` | 唯一处理 Cookie、CSRF、Refresh 和错误的传输层 |
| 领域 API | `src/lib/api/admin.ts` 或 Feature 公开适配层 | 封装端点和领域语义，不在页面拼接底层请求 |
| 服务端状态 | TanStack Query | 管理请求生命周期、缓存、失效和刷新 |
| 最终授权与审计 | Backend | 客户端隐藏、禁用和确认不能替代服务端判定 |

Umi 管理的 React Router、Bundler、Babel、esbuild 和运行时内部依赖不得由应用直接接管。需要扩展时先使用 Umi 配置或插件公共契约；需要升级时采用 Umi 官方支持的兼容组合，不能把某个内部主版本写成永久项目规则。

## 目录与 Feature

- `config/routes.ts` 是路由和菜单结构入口，路由组件指向对应 Feature 的页面导出。
- `src/app.tsx` 负责 Query Provider、`getInitialState`、Layout 和运行时级错误边界等全局装配。
- `src/access.ts` 从 initialState 派生客户端访问能力，不发明服务端没有的权限。
- `src/features/<feature>/` 内聚路由页面、局部组件、Hook、测试和领域适配；当前路由页面命名为 `*Page.tsx`。
- `src/components/` 只放跨页面复用的管理端组件，`src/lib/` 只放无业务页面所有权的基础设施。
- Feature 之间只通过公开入口或共享基础设施协作，禁止导入其他 Feature 内部实现。

新增页面时，先登记配置式路由和所需 Access，再在对应 Feature 内完成页面编排。不得另建独立 React Router、第二套 Layout 或绕过 `app.tsx` 的应用入口。

## Access 与服务端授权

`src/access.ts` 的职责是改善管理端体验：控制菜单、路由和按钮是否可见或可操作。它不能证明请求有权执行，也不能阻止绕过浏览器直接调用 API。

所有受保护操作必须由 Backend RBAC 最终判定，并继续使用 CSRF、资源状态校验、事务和服务端审计。Admin 不提供管理操作的密码二次确认 Token；客户端标准警告弹窗负责在删除、移入回收站和移除前明确用户意图，不承担服务端授权。权限加载失败时不得猜测或放宽权限，应进入明确失败、无权限或重新登录状态。

## 数据、请求与状态

请求链保持单向：

```text
Page / Feature -> domain API -> http.ts -> Backend
                         |           |
                         |           +-- Cookie、CSRF、单飞 Refresh、错误解包
                         +-- @pinjie/api-client 生成 DTO
```

- 页面和组件不直接调用原始 `fetch`，不自行刷新 Token，不重复解析统一响应结构。
- `@pinjie/api-client` 当前提供生成 DTO；领域 API 通过项目 HTTP 管道调用端点。未来若启用生成 SDK，必须证明不会形成第二套传输、安全或 DTO 来源，并纳入全栈计划。
- TanStack Query 保存服务端数据和请求状态。Mutation 成功后按领域键精确失效或更新缓存，失败必须显示可操作错误。
- 组件本地状态用于弹窗、表单、选择和短期草稿。只有真正跨页面且不属于服务端事实的状态才评估 Store。
- Token、Cookie 内容、Refresh 状态和其他敏感凭据不得进入 `localStorage`、Store 或客户端可读持久化存储。

## UI 组件选择

| 场景 | 优先选择 | 允许调整的条件 |
| --- | --- | --- |
| 标准查询、分页、排序和列配置 CRUD | `ProTable` | 特殊虚拟化、复杂单元格交互或性能证据可改用 Ant Design Table |
| 标准新增或编辑表单 | `ModalForm` 或 `DrawerForm` | 多阶段流程、跨步骤草稿、复杂焦点或独立路由可使用 Form 与页面编排 |
| 简单详情和键值信息 | ProDescriptions 或 Ant Design Descriptions | 大量自定义布局时使用语义化组合组件 |
| 基础反馈、导航和输入 | Ant Design 组件 | 仅在现有组件无法满足明确契约时增加项目组件 |

ProComponents 是提高标准管理场景效率的首选，不是形式上的强制。选择较低层组件时必须保持统一的加载、空数据、失败、无权限、成功反馈、分页和可访问性行为，不能借此复制基础控件或破坏设计一致性。

标准列表使用 `ProTable` 时，空数据展示以 `ProTable` 内建空态为唯一来源。页面外层 `QueryState` 只负责加载、失败和重试，不传 `empty`，也不额外渲染 Ant Design `Empty`，避免同一请求产生两个“暂无数据”。未使用 `ProTable` 的列表、抽屉和面板继续由 `QueryState empty` 或 Ant Design `Empty` 提供空态。

管理端保持紧凑、可扫描和适合重复操作。所有 Ant Design `Table` 或 `ProTable` 表格的表头和单元格统一设置 `white-space: nowrap`，优先通过 `onHeaderCell`、`onCell` 或 Admin 公共表格样式实现，避免空数据或列宽自适应时出现换行；长文本通过列宽、Tooltip 或明确的溢出处理解决。存在操作列时沿用现有 `width: "1%"` 和按钮布局，并保持表头、单元格及按钮容器单行。标准桌面列表保持弹性宽度，不在全局 `.ant-table-container` 上覆盖 `overflow`；真实宽表和窄屏横向溢出由具体 `Table` 或 `ProTable` 的 `scroll.x` 管理，避免重复滚动容器和异常纵向滚动条。危险操作必须有清晰文案、Loading 和失败恢复；删除与移除按下节统一二次确认。图标按钮使用 Ant Design Icons，并为不熟悉的图标提供 Tooltip。

桌面展开态由 Umi Max ProLayout 统一使用 `256px` 侧栏，PageContainer 保持流式内容区，不设置固定最大宽度。`1440px` 及以上视口使用 `40px` 页面水平内边距，较窄桌面回落为 `24px`，移动端回落为 `16px`；标题区与正文使用同一水平边界。移动端侧栏折叠和抽屉继续使用 ProLayout 官方响应式行为，页面不得产生 document 级横向溢出。

## 页面容器与间距

- 标准管理列表页复用 `src/components/PageFrame.tsx`，统一接入 `workspace-page` 与 `workspace-panel`。当前接口要求传入 description；页面没有说明需求时，不为满足展示形式增加空区块或间距占位，需要调整可选性时在后续实现中同步组件类型与调用方。
- 特殊页面直接使用 PageContainer 时，必须接入与公共容器等价的标题、内容边界和响应式间距；引入同一个 Ant Design 组件不代表已应用项目样式。
- 内边距由明确的一层容器负责。PageFrame 内的 ProTable 使用 `src/styles.css` 现有规则去除内部 ProCard 的重复边框、阴影和内边距，避免多层 Card 叠加留白。手机端公共面板内边距为 16px。
- 排查留白时按页面、面板、表格逐层检查 padding、margin、宽度及实际命中的类名，先修正公共样式的接入，避免用负 margin、固定页面宽度或隐藏溢出掩盖问题。
- 有数据的宽表接入 `responsive-data-table` 和对应 `scroll.x`，空表按下节取消固定滚动宽度并恢复自适应；真实溢出只在表格自身范围内滚动，工具栏保持在可用内容宽度内。公共样式调整需核对已有消费者，业务专用布局使用 Feature 类名限定范围。

## 列宽与长内容

- 按内容选择列宽：排序、布尔状态等短字段使用合理固定宽度；说明等长文本列优先承担剩余空间。保留适合当前列表的弹性内容列，避免所有列机械等宽或长文本无限撑宽。
- 固定宽度应容纳表头、内边距、开关及其加载状态；长名称或说明使用省略和可访问的完整内容入口，不通过表头换行或压缩字号补偿列宽不足。
- 操作列继续遵守既有宽度与单行按钮约定；内容列调整不顺带改变操作列、勾选列或业务操作。某个列表的具体像素宽度不提升为全局默认值。
- 分别核对空数据、有数据、长文本及无操作权限时的列布局；空表沿用公共空态并核对实际布局，不能以空表正常推断有数据时也不会溢出。

### 空数据时的横向滚动策略

适用于全部 Ant Design `Table` 和 `ProTable`，包括普通列表、只读日志、回收站以及抽屉或弹窗中的表格。

**根因说明**：Admin 表格统一对表头和单元格设置 `white-space: nowrap`，列头内容始终具有固定水平宽度。若空数据时取消 `scroll.x`（例如写成 `rows.length ? { x: "max-content" } : undefined`），Ant Design 的 `ant-table-content` 内部 `<table>` 元素会按列头 `nowrap` 宽度撑开，而外层 CSS 又设置了 `overflow-x: auto`，导致空数据状态下反而出现横向滚动条。

**统一规则**：

1. `ProTable` 和 `Table` 统一设置 `scroll={{ x: "max-content" }}`，无论数据行数多少，始终保持一致。**禁止**根据 `rows.length` 或其他条件动态切换 `scroll.x` 与 `undefined`。
2. `ResourceTable` 公共组件已按此规则固定，所有通过 `ResourceTable` 渲染的列表页无需额外处理。
3. 新增不经由 `ResourceTable` 的独立 `Table` 或 `ProTable` 时，必须直接在组件 `scroll` prop 上设置 `{ x: "max-content" }`，不得省略。
4. 空数据的视觉空态由 `ProTable` 内建 Empty 负责，外层 `QueryState` 只处理加载和失败，详见"UI 组件选择"节。
5. 窄屏下列头实际内容超出可用宽度时，允许表格内部按真实内容横向滚动；禁止产生 document 级横向溢出，禁止用 `overflow-x: hidden` 隐藏问题。

验收时分别核对桌面和窄屏下的空数据、有数据宽表、筛选无结果及空与非空双向切换，确认空态居中、无多余横向滚动条且有数据时宽表滚动能力正常。

## 列表标题与工具栏

按 `apps/admin/AGENTS.md` 的列表规则，`ProTable` 通过 `headerTitle` 设置表格上方工具栏左侧的具体列表名称，例如“用户列表”“角色列表”“审计事件列表”；页面标题或 Tab 名称不能代替该标题。右侧使用内建工具按钮，显式配置如下（`query` 指当前列表的 TanStack Query 查询）：

```tsx
headerTitle="用户列表"
options={{
  reload: () => void query.refetch(),
  density: true,
  setting: true,
  fullScreen: true,
}}
```

刷新重新请求当前分页和查询条件下的数据，沿用页面的加载与错误反馈；密度、列设置和全屏必须实际可用。自定义业务操作与这些工具并存，不通过 `options={false}`、隐藏工具栏或样式覆盖移除必需入口。普通数据列表与只读日志列表均适用。

搜索、筛选和重置按实际查询需求配置，开发前结合预计数据量判断；预计数据较多且需求不明确时，先向用户确认是否需要及具体条件。无需查询表单时可设置 `search={false}`；已有自定义查询控件时避免重复生成同类表单。需要重置时同步恢复输入值、实际查询条件与分页，并按既有选择规则清空选择，不能只清空界面输入。

### 紧凑筛选与响应式布局

- 少量高频筛选优先并入现有表格工具栏，保持筛选、搜索的操作顺序；复杂查询继续使用适合的查询区。不要仅为少量下拉框增加独立大卡片或固定高度的空白区域。
- 筛选、搜索和按钮沿用表格所在 Ant Design 主题的字体、字号及控件尺寸。清空筛选等简单辅助动作可使用纯图标按钮，同时提供 Tooltip 和准确的可访问名称；不据此把新增、删除等所有动作改为图标。
- 下拉框根据内容和可用空间设置宽度边界，长选项由组件省略；搜索框桌面宽度按页面需要确定，窄屏下允许伸缩或占满一行。某页的搜索宽度、下拉框最小宽度或断点不作为所有列表的硬性值。
- 增加控件时同时核对 ProTable 外层工具栏、内部 actions 容器和业务控件组的布局。外层支持换行不代表内部 actions 已支持换行；需要时在 `toolBarRender` 中组合业务容器，并沿用公共响应式类或限定范围的样式。
- 按实际可用宽度安排换行，可使用容器查询处理侧栏展开后的窄内容区。Flex 或 Grid 子项需要可收缩时设置 `min-width: 0`，同类下拉框可等分剩余宽度，固定按钮保留触达尺寸。
- 标题、刷新设置、筛选和搜索在窄屏有明确分组与顺序，避免重叠或挤出页面；不强制所有列表使用相同行数。无新增权限、回收站或其他按钮缺席时，剩余控件自然填充空间，不保留空列占位。

### 查询一致性

- 搜索字段、匹配方式、大小写、首尾空白、特殊字符及筛选组合语义以产品需求和服务端实现为准，输入提示与可访问名称必须准确。新增匹配字段不擅自移除既有字段；用户明确调整范围时，同步服务端条件、提示、回归源码和需求文档。
- 全部有效筛选条件进入请求参数与 TanStack Query key；服务端先过滤再计算总数和分页。刷新及翻页保留条件，改变条件回到第一页并清空不可见勾选。
- 筛选选项覆盖加载、失败和重试状态，不把加载失败当作无选项；读取与写入权限独立，具备读取权限的用户仍可使用查询。
- 明确区分“清空筛选”和“重置全部查询”的范围，例如只清下拉筛选时保留关键词；按钮名称、禁用条件和实际清除范围保持一致。

验收时按实际影响检查标题、工具栏左右布局、刷新请求及加载和失败反馈、权限、空数据、筛选无结果、窄屏和长标题；搜索与筛选已启用时同时检查提交、重置、分页和选择状态。静态检查不能代替浏览器验收，动态验证按项目授权规则执行并如实记录未执行项。

## 列表分类与批量操作

新增列表或调整列表操作能力时先按数据语义分类；局部样式、文案和缺陷修复保留既有能力，不自动扩大为批量功能建设：

| 列表类型 | 选择与批量操作 | 删除语义 | 当前示例 |
| --- | --- | --- | --- |
| 普通数据列表 | 按写权限显示受控选择列，并提供至少一种有效批量操作 | 复用实体既有软删除或硬删除；没有删除生命周期时提供启停等合法操作 | 用户、管理员、角色、文件资产 |
| 只读日志列表 | 不显示选择列，不提供人工删除或批量写操作 | 只允许服务端保留策略和受控清理流程 | 登录安全事件、审计事件、请求元数据 |

普通数据列表使用 Backend 专用批量端点传递当前页明确选中的 ID，不跨页隐式全选，也不循环调用单条写接口。每次查询、筛选、重置或翻页时清空选择；请求成功后提示实际完成数量、清空选择并刷新数据，请求失败时保留选择并展示统一错误。没有相应批量写权限时隐藏选择列和批量操作区。

### 布尔状态与列内开关

- 对具有明确开关语义且允许直接保存的布尔字段，例如启用与停用，新增或调整交互时优先使用 Ant Design Switch。同一业务中语义相同的字段保持一致；多状态流程、身份变更或需要业务表单的操作按原流程实现，不机械替换所有既有 Tag 或按钮。
- `checked` 绑定当前服务端状态，提供包含对象与动作的可访问名称，并通过文字或 Tooltip 说明含义。逐行显示加载状态，防止同一目标重复切换，同时禁用与该目标冲突的编辑、删除及批量操作；无冲突的其他行不应无故锁定。
- 成功后更新缓存并刷新受影响查询，失败保留或恢复原状态并明确提示，不能只切换前端外观。列内开关与已打开表单存在同目标写入冲突时，沿用项目互斥控制。
- 使用准确的资源写权限和生命周期条件控制可操作性；无权限、回收站或受保护对象按业务约定使用禁用开关或只读状态标记。客户端限制不能替代 Backend 授权、CSRF、事务和审计。
- 优先复用已有状态或批量启停接口提交目标 ID 与动作，避免为状态切换回传密码、备注等无关字段；只能使用完整更新接口时遵守原契约并保留全部非目标字段。涉及敏感信息时沿用原有缓存和日志保护，不为开关交互增加敏感数据副本。

现有用户、管理员和角色列表的状态 Tag 沿用已交付交互；本节规定后续新增或明确调整状态交互时的实现方式，不代表当前项目已完成 Switch 源码迁移。

### 删除生命周期

软删除实体的单条和批量删除沿用状态失效、凭据版本提升、会话撤销和长期可恢复生命周期，在明确确认后提交。用户软删除进入回收站，回收站只提供受 `users:restore` 权限控制的单条与批量恢复；不可恢复记录禁用选择与恢复入口，恢复后显示为停用账户。新增列表如果确需归入只读日志例外，必须先在产品需求中登记其不可变历史属性和保留策略，普通业务记录不能仅因暂时缺少批量 API 而归入例外。

### 删除与移除确认

所有删除、移入回收站、永久删除、移除以及同类清除已保存资源或关联的入口均遵守下列要求，覆盖软硬删除、单条和批量、列表及 LOGO、头像等非列表控件：

1. 统一使用 `src/components/StandardConfirmModal.tsx`，传入标题、说明、加载状态、执行回调及可选业务表单。固定“确定”和“取消”，已有合规弹窗就地复用，不叠加第三次确认或密码输入。
2. 打开弹窗只记录待确认目标，不修改数据、清空草稿或发起删除请求。文案包含具体对象或数量、操作影响及恢复方式；硬删除说明不可恢复，软删除说明回收站及关联影响，草稿移除说明保存后生效。
3. 执行回调返回完整操作 Promise。公共组件在任何异步校验前设置同步防重锁，结合 Loading 禁止重复确认及取消、关闭按钮、遮罩和 Esc。页面不得通过表单回车、其他入口或提前结束 Promise 绕过确认与锁；延后保存的头像移除还需保护保存请求。
4. 失败保留弹窗、目标、输入和批量选择，使用统一错误格式显示反馈并允许明确重试；成功后才关闭弹窗，批量成功后清空选择并刷新数据。不得乐观清除后无提示回退，或吞掉错误后显示成功。
5. 打开确认时固定目标 ID 集合；涉及 revision 时固定版本，冲突后取消、加载最新配置并重新确认，不能自动换成新版本继续删除。提交期间阻止同一资源的冲突写入。
6. 适用回归用例覆盖打开和取消零写入、单条与批量确认、连续点击只提交一次、提交中不能关闭、失败保留及重试、成功清理和无权限入口。只按当前授权执行测试与浏览器验证，静态检查不等同交互验收。

启停、恢复、密码重置、会话撤销、身份调整、角色分配、权限修改、筛选重置及取消选择等非删除操作保持原交互。角色权限树清空属于待保存的权限勾选，沿用权限配置保存流程；不能通过将实际资源删除改名为“清空”规避确认。

## 依赖治理

| 依赖层级 | 示例 | 准入与升级规则 |
| --- | --- | --- |
| Umi 内部核心 | React Router、Bundler、Babel、esbuild | 不直接声明或接管；随 Umi 官方兼容组合和锁文件解析 |
| 官方兼容栈 | `@umijs/max`、React、Ant Design、ProComponents、官方插件 | 按兼容矩阵升级，形成计划并完成 Admin 与适用跨栈回归 |
| 业务中立外围能力 | 查询、验证、可访问性或通用工具 | 有明确跨业务复用需求、无现有能力重复且通过供应链评审后引入 |
| 具体业务依赖 | 图表、富文本、Excel、地图、支付或行业 SDK | 默认由真实业务计划引入，不进入当前商城基线 |

所有新解析继续受根 `pnpm-lock.yaml`、七天冷却、安装脚本白名单和供应链门禁约束。范围化安全 override 必须记录依赖链、受影响范围、兼容依据和回归结果；无兼容修复版本的 Medium 或 Low 风险按 `SECURITY.md` 建立限时风险接受。不得通过强制升级框架内部主版本、关闭审计或永久 override 换取表面无告警。

当前 Umi `4.7.5` 的 Vite bundler 固定依赖存在 High 漏洞的 Vite 4，而 Admin 实际使用默认 Webpack。根 `.pnpmfile.cjs` 精确移除未使用的 Vite bundler，`patchedDependencies` 同时关闭 Vite 入口并修复 Webpack server 忽略 host 的监听行为，`scripts/ci/check-umi-vite-security.mjs` 拒绝版本漂移和补丁缺失。补丁负责人为仓库维护者，复核日期为 2026-09-21；上游稳定版提供安全组合后必须通过新计划删除临时补丁。

## 验证要求

变更按风险运行最小充分检查。Admin 源码或依赖变化默认只执行：

```powershell
pnpm --filter @pinjie/admin typecheck
pnpm --filter @pinjie/admin lint
```

Vitest、production build、浏览器冒烟和真实跨栈 E2E 只有在用户对当前任务明确授权后才执行，并分别记录结果。路由、插件、认证、请求或依赖变化不能自行扩大授权范围。规则和架构变化执行：

```powershell
pnpm lint:md
pnpm check:workspace
pnpm check:boundaries
pnpm check:governance
```

Mock、局部组件测试和浏览器冒烟不得表述为真实跨栈验证。Umi 启动、缓存和 Windows 进程排障见 [Admin 本地运行与验证排障手册](../operations/admin-local-development-and-validation-troubleshooting.md)。
