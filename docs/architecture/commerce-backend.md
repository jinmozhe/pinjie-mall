# 商城后端领域与实施设计

## 1. 定位

本文描述四阶段后端当前机制，运行验证事实仍以对应计划为准。业务验收唯一来源为[产品需求基线](../PROJECT_REQUIREMENTS.md)，建设记录见[四阶段计划](../../plans/2026-09-17_商城后端四阶段建设计划.md)，后续审查与修复见[边界审查修复计划](../../plans/2026-09-17_商城M1至M4边界审查修复计划.md)。

目标迁移边界：2026-09-21 起，后续开发以[终极全域数据库字典](database-schema-guide.md)及更新后的产品基线为目标，采用平台统一运费、零元内部成交、整单含原运费退款和三级预算分佣。下文商品运费模板、正额限制、部分退款及固定两级佣金均为现行实现，尚未迁移；不能据目标文档宣称新行为已实现，也不能以本页旧机制覆盖新需求。

## 2. 所有权与依赖

| 领域 | 拥有数据 | 对外职责 |
| --- | --- | --- |
| products | 分类、商品、稳定 SKU、商品图片关联 | 商品管理、可售状态与商品快照 |
| inventory | SKU 库存账户、人工流水、占用及占用事件 | 初始化、调整、占用确认释放 |
| addresses | 用户收货地址 | 本人管理、默认地址和快照 |
| shipping | 运费模板、地区规则 | 模板管理、校验与运费报价 |
| cart | 购物车条目 | 购物意图，不保存权威成交金额 |
| orders | 订单、订单明细、状态历史 | 状态转换、快照与交易身份 |
| lifecycle | 支付意图、履约、退款、评价、对账及对应事件 | 支付售后事实和状态查询 |
| distribution | 会员推荐、佣金、双轨账户、追回关联、钱包流水、提现 | 最多两级分佣与资金权利 |

Model 沿用项目 db/models 路径，路径集中不授予跨领域写权限。各领域公开入口输出 DTO 或提供明确命令。购物车、订单和支付售后的跨领域编排分别位于 `app/services/cart.py`、`app/services/orders.py`、`app/services/payment_lifecycle.py`；商品可售快照、地址快照、运费模板、库存变更和订单查询通过所属领域的公开 Service 协作。生命周期仓储不读取或写入订单表，订单仓储不读取商品、地址、模板或库存表。

## 3. M1 数据与接口设计

### 商品

- 分类为父子树，最多三级；结构写入使用数据库事务内固定锁，防止并发改父级构造环。
- SPU 保存名称、说明、类型、分类、运费模板及草稿/上架/下架状态。
- 每个 SPU 拥有稳定 SKU；无规格商品也使用默认 SKU。编码唯一，规格使用 JSONB，价格使用 Numeric，重量单位为克。
- 更新 SKU 以 ID 定位并校验商品归属，不全量删除重建。SKU 停用表达不可售，历史标识保留。
- 商品图片关联统一资产 ID，绑定时锁定并验证图片资产，资产删除时检查引用。仍被引用时明确拒绝删除。
- 商品公开 DTO 与管理 DTO 分开，不输出成本、内部备注或权限信息。

### 库存

- 库存账户以 SKU 唯一，available 与 reserved 均非负，revision 用于拒绝陈旧写入。
- 人工调整只修改 available；每次调整保存 request_id、SKU、变动数量、前后数量、原因和操作者。
- 人工调整校验可用与占用库存合计不超过数据库整数容量，保证后续释放占用不会溢出。
- 同一请求号只能代表同一内容；重复相同请求返回已完成结果，不重复调整。相同请求号不同内容返回冲突。
- 下单占用、支付确认和取消释放进入 M2，M1 不开放伪造订单状态的库存端点。
- SKU 创建及库存初始化通过同一应用事务完成；商品编辑不直接更新库存表。

### 地址

- 地址写入以用户为粒度串行，写入前核对当前用户有效状态。
- 地址保存收件人、手机、行政区编码与名称、详细地址和默认标记。
- 数据库使用条件唯一索引限制每用户至多一个默认地址；删除默认地址后按创建时间和 ID 选择替补。
- 本阶段复用现有用户认证依赖，不宣称小程序登录已完成。未来 Public Client Profile 适配相同用户 ID。

### 运费

- 模板包含名称、计费方式、状态、版本、包邮门槛和排除省份。
- 地区规则包含省份列表、首单位/首费、续单位/续费。默认规则唯一，显式省份不能重复归属。
- 按件计费使用整数件数，按重计费使用整数克；金额保留两位，单位进位使用 Decimal 的 ROUND_CEILING。
- M1 拒绝停用模板的新绑定、上架和报价，模板编辑按行锁与 revision 校验；M1 不开放模板删除接口，数据库引用采用 RESTRICT。
- 运费超过 Numeric(15,2) 上限时明确拒绝。后续结算须重新校验模板状态与规则版本；未来若开放删除，须补齐锁定和引用检查。

### 接口形态

管理 API 使用 /api/v1/admin 下的 products、inventory、shipping 等领域路径；消费者 API 按 products、addresses 等领域组织。具体机器契约只由后端导出至根 openapi.json，不维护另一份字段契约。列表有界分页，写操作使用明确请求 Schema，版本冲突不静默覆盖。

## 4. 应用事务与安全

管理写操作经过管理员会话、精确 PermissionCode、CSRF、事务内权威校验和 AuditCoordinator。外层编排拥有事务，领域内部命令与 Repository 不提交；Repository 返回权威数据，应用服务决定授权。Admin 提供分类和运费模板批量启停、商品批量上下架及同一商品内 SKU 批量启停，限制 1 至 100 个唯一目标、核对 revision、固定顺序锁定并全有或全无。SKU 批量命令核对共享商品版本。

商品、库存、地址和运费按领域定义稳定错误码，统一 AppException 和 ResponseModel。未知错误明确传播，数据库约束冲突只在能识别业务约束时映射为业务冲突。

## 5. M2 至 M4 的衔接边界

1. 商品和地址提供快照 DTO；订单拥有快照，不保留对可变商品资料的强依赖。
2. 成交价格只由服务端计价；未来会员折扣必须同时进入预览和最终下单，快照保存生效规则版本。
3. 库存占用以订单业务标识幂等；任务必须有持久扫描依据、领取和重试边界，不能只依赖进程内计时器。
4. 外部资金调用采用持久意图、事务外调用、结果确认与短事务落库。超时保留结果未知。
5. 部分退款以退款单独立跟踪金额与数量，支付执行必须收到申请金额；订单、库存和佣金根据确认结果编排。
6. 两级分佣保存受益人与规则快照，退款追佣覆盖冻结、已结算和已提现场景；资金政策明确后再实现。
7. 双轨账户不采用一个共享冻结余额混合表达所有权利；具体账户和转移规则以获确认的需求为准。
8. 微信身份接入复用用户基础与审计，独立扩展适合小程序的会话 Profile，不复制参考仓库整套认证。

## 6. M2 交易实际边界

交易阶段新增购物车、结算预览、订单、订单明细、状态事件和库存占用数据。购物车只保存用户意图，写入时校验当前 SKU、商品及分类祖先可售和可用库存，不占用库存也不保存成交价格。更新条目必须提交当前 `revision`，陈旧写入返回冲突。消费者写用例在事务内重新锁定读取用户有效状态，拒绝认证后被停用或软删除的账户。

预览和创建订单共用服务端计价：同一 SKU 先合并数量，实物和虚拟商品拒绝混单；实物订单必须使用本人地址，虚拟订单没有地址快照。同一运费模板聚合件数或重量与组内商品金额后计费，不同模板运费相加。报价指纹覆盖商品、价格、规格、地址及运费规则快照；下单在事务内重新计算，指纹不一致明确拒绝。

订单按用户和请求号幂等，保存规范请求摘要；重放直接核对已保存的规范明细、地址标识和报价指纹，不依赖当前商品资料或猜测摘要版本。创建时依次锁定用户、商品目录、运费模板、地址和库存，模板与库存按固定 ID 顺序锁定并刷新读取。库存领域承担占用、确认与释放，所有变动递增库存版本并保存独立不可变事件；订单、明细、订单事件、占用和库存事件同事务写入。缺失占用、数量不匹配或非法状态明确拒绝。客户端和管理员没有手工标记支付的 API。

订单状态当前只有 pending_payment、paid 和 cancelled。待付款时限固定 30 分钟，独立的 `scripts.expire_pending_orders` 命令默认 dry-run；显式 `--apply` 且精确确认数据库名后，按持久化到期时间使用 `SKIP LOCKED` 领取并关闭订单。命令未由应用启动或定时任务自动调用。

超时扫描每单独立事务，避免批次间持有不同 SKU 顺序的库存锁。应用数据库连接通过 Settings 的 `DB_LOCK_TIMEOUT` 设置锁等待上限，默认五秒。锁超时必须回滚并明确失败，不自动重做外部副作用。

管理订单列表、订单详情和履约查询要求 `orders:read`；管理退款分页查询要求 `refunds:read`，退款响应包含审核所需 `revision`。Admin 的交易中心消费上述契约，待付款或取消订单只展示订单快照，付款后再查询履约状态。

### 订单快照和后续边界

订单明细固化商品名称、SKU 编码、规格、数量、成交单价、重量和商品版本；订单固化地址、运费分组、规则版本与金额。内部支付确认在渠道确认时间达到订单到期点后明确拒绝。渠道适配、验签参数、关单和结果未知后的恢复策略由 M3 支付领域继续实现。

## 7. M3 支付与售后实际边界

M3 新增支付意图与状态事件、履约与状态事件、退款申请与明细状态事件、公开评价和渠道账单对账记录。支付意图按用户请求号幂等，保存商户参考号、金额、币种和渠道状态。微信和支付宝尚未配置时，服务明确保存 `unavailable` 状态，不提供伪造支付成功 API。

可信支付确认仅为内部应用入口，调用方须在渠道验签、商户与应用、订单、金额、币种核对后传入唯一渠道流水和已脱敏载荷摘要。支付编排在订单与库存之前取得推荐关系图锁，避免与推荐绑定、下单形成循环等待。用户状态校验使用 `FOR NO KEY UPDATE`，继续阻止并发状态修改，同时允许佣金等引用用户的外键检查。确认付款、确认库存占用、创建履约单和支付事件在同一短事务内完成。当前没有公开回调路由、真实渠道适配器、验签密钥或外部资金调用。

实物履约从待发货进入已发货，再由用户确认或发货满七日的持久化扫描进入已交付；虚拟订单由管理员登记交付引用后完成。自动确认命令 `scripts.auto_confirm_fulfillments` 默认 dry-run，并要求精确数据库确认与显式 `--apply`。

退款仅支持已交付订单的订单明细商品金额和数量，不退运费、不自动入库。待审核、已批准、处理中、结果未知和成功退款均占用可退数量与金额；零金额明细不能发起资金退款。确认时再次核对金额、币种、原成功支付流水和订单归属，退款流水按渠道唯一，并记录载荷摘要。未知状态收到可信确认后可恢复为成功。确认入口统一先锁订单再锁支付或退款记录，渠道流水另有事务幂等锁。评价仅对本人已交付订单明细开放，使用不可变明细 DTO 和订单锁避免与退款反向锁定。

对账按渠道流水串行，重放核对金额、币种、发生时间、来源引用和摘要；只记录账单与本地支付事实匹配或差异，不改变订单、支付或退款状态。地址、订单售后、分销提现及相应管理端点的错误请求体不进入请求日志，避免收货资料、退款说明或收款引用泄露。

## 8. M1 实际边界

已提供分类查询与创建更新、商品管理与公开查询、SKU 新增及原位修改、上下架、库存查询调整与流水、本人地址管理、运费模板创建更新查询与试算。商品列表批量读取变体和图片，避免逐商品加载。

分类、商品、SKU、模板通过启停或上下架管理生命周期，Admin 商品中心提供单条编辑、批量操作、图片选择上传、库存调整与流水。商品列表支持名称或 SKU 编码、分类、状态和商品类型筛选，未提供复制或物理删除。地址快照已接入订单，商品可售资格在购物车及订单中统一核对。目标环境仍须经授权执行迁移和权限同步后才能使用新接口。

## 9. M4 会员分销与钱包实际边界

M4 新增会员档案、首次推荐关系、佣金记录与退款追回关联、双轨钱包账户、不可变钱包流水和提现申请六张表。会员初始等级固定为 `standard`，当前不参与计价；开通档案先按用户行锁串行，同时建立双轨钱包。推荐绑定先取得关系图事务锁，再锁用户与档案，拒绝自邀和任意深度循环；读取付款归属使用同一关系图锁，仅纳入可信付款时点已经绑定的关系。邀请码使用 UUID 随机尾部，避免截取时间前缀导致同毫秒低熵碰撞。

可信支付确认在订单、库存、支付事件和履约单完成同一事务后，按订单商品金额创建最多两条佣金快照。一级推荐人使用 10%，二级推荐人使用 5%，运费不参与基数，金额采用两位小数半舍入。履约交付时记录七日后的结算时间；独立命令 `scripts.settle_due_commissions` 默认 dry-run，只有精确确认数据库并显式 `--apply` 才结算佣金钱包。

退款成功确认按累计成功退款商品金额计算应追回总额，减去已有追回金额后写本次关联与流水，避免多次小额退款舍入遗漏或提前多追；全额退款最终追回全部佣金。结算和追佣先按固定顺序锁定全部相关佣金钱包。可用余额不足形成欠款，后续结算及提现拒绝解冻均先抵消欠款；有欠款时不能批准新提现。佣金钱包只接收已结算佣金并允许提现；消费钱包尚未开放充值或消费扣款，不能提现；两条轨道没有互转入口。

提现按用户和请求号幂等，申请时将佣金钱包可用余额转为冻结余额并写入不可变流水。管理员审核通过只表示进入后续渠道执行，审核拒绝在同一审计事务内解冻；真实打款、渠道确认、结果未知查询和追佣已提现后的外部追偿尚未实现。

## 10. 迁移、验证和交付

每阶段新增不可变 Alembic revision；不执行共享数据库变更或导入参考数据。权限目录通过独立受控命令同步，应用启动不自动改权限表。

边界修复使用后继 `20260917_05`，新增库存占用事件、库存总容量约束、退款渠道与退款事件摘要，并扩展订单支付引用长度以容纳完整渠道前缀。历史库存事件不伪造；历史退款渠道只从唯一成功支付事实回填，存在歧义时迁移明确终止。新增列和事件表必须先经授权升级数据库，再切换对应代码；历史追佣差额及库存审计缺口须按真实数据单独核验，不能把代码修复当作历史资金修复。迁移不提供删除审计数据的降级，恢复使用前向修复或已授权备份恢复。

默认执行后端轻量门禁、契约生成及受影响治理检查。测试源码应覆盖领域不变量、拒绝、回滚、幂等和状态冲突；实际 pytest、真实 PostgreSQL 并发及迁移、渠道联调仅在当前任务明确点名授权后运行。未运行的验证不得记为通过。

## 11. Admin 电商运营查询

`app/services/commerce_reporting.py` 是只读运营查询模型，直接读取 PostgreSQL 已提交事实，每次刷新重新查询，不维护第二份余额或状态。查询不进入资金写决策；审核、发货和库存操作仍由对应应用服务在事务内核对权威状态。分页按创建时间和主键稳定排序，计数及页面读取采用数据库读已提交隔离，期间有并发新增时可通过刷新重新读取。

| 页面 | 查询权限 | 主要筛选 | 操作 |
| --- | --- | --- | --- |
| 订单履约 | `orders:read` | 订单、用户、状态、类型 | 快照详情、发货、虚拟交付、选中导出 |
| 退款审核 | `refunds:read` | 申请、订单、用户、状态 | 单条审核与选中导出 |
| 支付记录 | `payments:read` | 支付记录、订单、用户、渠道、状态 | 只读查询与选中导出 |
| 支付对账 | `reconciliation:read` | 记录、渠道、状态 | 既有对账录入与选中导出 |
| 会员与推荐关系 | `members:read` | 用户、直接推荐人 | 档案、推荐链逐层查询与选中导出 |
| 佣金记录 | `commissions:read` | 记录、订单、受益人、状态 | 冻结、结算、追回查询与选中导出 |
| 双轨钱包 | `wallets:read` | 钱包、用户、轨道 | 余额、不可变流水与选中账户导出 |
| 提现审核 | `withdrawals:read` | 申请、用户、全部状态 | 单条审核与选中导出 |

查询条件必须属于当前资源支持的字段，不支持的条件明确返回 422。普通业务列表通过独立的 `资源:export` 权限导出，每次提交 1 至 100 个唯一选中标识，会员使用 `user_id`。导出端点同时要求读取权限和 CSRF，按响应 Schema 白名单输出，缺失任一目标时整体返回冲突；不导出原始请求摘要、密钥或任意数据库字段。Admin 使用服务端返回的金额字符串生成 CSV，对引号和公式前缀进行转义，失败保留选择，成功清空选择并刷新。

菜单和控件由 `routes.ts`、`access.ts` 及当前管理员权限控制，所有查询在服务端再次校验准确资源权限。权限目录显式同步，不自动给普通角色增加权限。财务查询、导出、对账和相关错误请求体均纳入敏感路径保护。支付、退款和提现渠道仍未接入，页面明确区分审核与实际资金成功，不提供手工伪造成功或余额修改。
