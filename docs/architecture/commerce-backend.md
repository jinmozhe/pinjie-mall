# 商城后端领域与实施设计

## 1. 定位

本文描述后端目标模型与当前业务实现边界。业务验收唯一来源为[产品需求基线](../PROJECT_REQUIREMENTS.md)，当前源码、历史动态验证和最新修复的证据边界统一见[数据库字典第 13 章](database-schema-guide.md#131-当前源码及迁移盘点)；商品首期和此前建设分别保留于[商品首期计划](../../plans/2026-09-22_后端目标模型与商品首期实施计划.md)与[四阶段计划](../../plans/2026-09-17_商城后端四阶段建设计划.md)。

目标迁移边界：2026-09-22 起，后续开发以[终极全域数据库字典](database-schema-guide.md)及更新后的产品基线为目标，采用平台统一运费、零元内部成交、整单含原运费退款和三级预算分佣。商品首期已实施品牌、属性、采用快照、SKU 组合身份与库存归档联动；阶段 2 已实现会员等级、会员价格规则、平台运费配置和统一报价；阶段 3 已实现可发布分佣政策、来源规则、三级矩阵、分佣总开关、钱包版本账链和持久任务基础；阶段 4 已实现购物车、结算预览、订单快照、库存和限购预占、取消或到期释放、可信成交、零元内部成交、履约创建及佣金冻结；阶段 5 已实现整单售后申请、独立退款执行事实、库存回补、限购退款标记、佣金结算与追回以及三类对账匹配；阶段 6 已实现显式单轮持久任务 Worker，处理内部过期订单、自动确认履约和佣金结算任务。外部支付和提现渠道、小程序会话、常驻调度、告警及渠道任务处理器仍未实现；旧运费模板试算入口继续返回 `503 / COMMERCE_UPGRADE_REQUIRED`，新订单不得按旧模板计价。

## 2. 所有权与依赖

| 领域 | 拥有数据 | 对外职责 |
| --- | --- | --- |
| products | 分类、商品、稳定 SKU、商品图片关联 | 商品管理、可售状态与商品快照 |
| inventory | SKU 库存账户、人工流水、占用及占用事件 | 初始化、调整、占用确认释放 |
| addresses | 用户收货地址 | 本人管理、默认地址和快照 |
| shipping | 存量运费模板、地区规则 | 仅保留管理与历史资料；新商品不关联模板，试算及新交易报价已阻断 |
| cart | 购物车条目 | 购物意图，不保存权威成交金额 |
| orders | 订单、订单明细、状态历史 | 状态转换、快照与交易身份 |
| lifecycle | 支付意图、履约、退款、评价、对账及对应事件 | 支付售后事实和状态查询 |
| membership | 会员等级、价格规则、资格条件、资格与等级事件 | 统一报价、平台运费配置与资格重算 |
| points | 积分账户、积分账本 | 人工授予与冲销，并提交积分资格贡献 |
| commissioning | 分佣政策、来源规则、三级矩阵与分佣总开关 | 草稿配置、政策发布与控制 |
| distribution | 会员推荐档案、佣金、双轨账户、追回关联、钱包流水、提现 | 推荐关系、三级权益冻结、结算、追回和人工提现 |
| purchases | 累计限购账户与订单限购事实 | 预占、成交确认、取消释放和退款标记 |
| durable_tasks | 持久任务、租约和失败状态 | 为支付、退款、佣金与提现恢复保存业务意图 |

Model 沿用项目 db/models 路径，路径集中不授予跨领域写权限。各领域公开入口输出 DTO 或提供明确命令。购物车、订单和支付售后的跨领域编排分别位于 `app/services/cart.py`、`app/services/orders.py`、`app/services/payment_lifecycle.py`；商品可售快照、地址快照、会员与平台运费报价、库存变更和订单查询通过所属领域的公开 Service 协作。生命周期仓储不读取或写入订单表，订单仓储不读取商品、地址、模板或库存表。

## 3. M1 数据与接口设计

### 商品首期

- 分类为父子树，最多三级；结构写入使用数据库事务内固定锁，防止并发改父级构造环。
- SPU 保存名称、说明、类型、分类、可选品牌、累计限购配置及草稿/上架/下架状态。商品已不保存运费模板引用。
- 每个 SPU 拥有稳定 SKU；无规格商品保留 `sku_no=0` 默认 SKU，多规格只经营明确提交的组合。SKU 保存服务端生成的 `specification_key`、展示 JSON、成本价、市场价、批发阶梯、可选重量和归档时间。
- 公共属性、标准值、分类直接模板、商品采用版本和候选值均受版本与归属校验。公共字典改名不会覆盖采用快照；自建维度以采用记录 ID 参与组合身份，禁止以文字推断货品身份。
- 规格转换原子归档旧 SKU、清退旧可用库存并保留预占；后续释放预占会再次清退，旧 SKU 不会恢复可售。
- 商品图片按轮播与独立详情两组关联统一资产 ID，绑定时锁定并验证图片资产，资产删除时检查引用。仍被引用时明确拒绝删除。
- 商品公开 DTO 与管理 DTO 分开，不输出成本、内部备注或权限信息。

### 商品详情内容

商品说明保持纯文本和 20,000 字符上限。详情切片通过 `product_detail_images` 有序引用统一资产，与轮播独立；绑定预算和解码机制见[文件资产架构](file-asset-storage.md#8-商品详情图片与历史元数据)。商品保存沿用权限、审计、revision 和同一事务，合并两组资产并按 UUID 顺序锁定；单条及批量上架复核详情预算，空详情不阻断既有商品。

管理 GET 详情返回 `ProductDetailRead`，含两组展示元数据；公开 GET 详情返回 `PublicProductDetailRead`，详情图片仅含 URL 和宽高。列表和写入响应继续沿用原模型。创建可省略详情集合，更新必须显式提交完整 `detail_image_asset_ids`，空数组解除全部详情关联；Admin 同批完成迁移，禁止旧请求缺字段时默认为清空。

迁移源码 head 为 `20260926_01`。2026-09-26 本机开发库 `pinjie_mall_dev` 已在验证可读的迁移前备份后升级至该版本，2 条历史商品图片元数据已回填并复核无待处理项。迁移的重复升级、降级保护及隔离测试库验证仍未执行。启用顺序见[操作说明](../operations/product-detail-images.md)。

### 库存

- 库存账户以 SKU 唯一，available 与 reserved 均非负，revision 用于拒绝陈旧写入。
- 人工调整只修改 available；每次调整保存 request_id、SKU、变动数量、前后数量、原因和操作者。
- 人工调整校验可用与占用库存合计不超过数据库整数容量，保证后续释放占用不会溢出。
- 同一请求号只能代表同一内容；重复相同请求返回已完成结果，不重复调整。相同请求号不同内容返回冲突。
- 下单占用、支付确认和取消释放进入 M2，M1 不开放伪造订单状态的库存端点。
- SKU 创建及库存初始化通过同一应用事务完成；商品编辑不直接更新库存表。

### 地址

- 地址写入以用户为粒度串行，写入前核对当前用户有效状态。
- 地址保存收件人、手机、行政区编码与名称、详细地址和默认标记。
- 数据库使用条件唯一索引限制每用户至多一个默认地址；删除默认地址后按创建时间和 ID 选择替补。
- 本阶段复用现有用户认证依赖，不宣称小程序登录已完成。未来 Public Client Profile 适配相同用户 ID。

### 存量运费

- 模板包含名称、计费方式、状态、版本、包邮门槛和排除省份。
- 地区规则包含省份列表、首单位/首费、续单位/续费。默认规则唯一，显式省份不能重复归属。
- 按件计费使用整数件数，按重计费使用整数克；金额保留两位，单位进位使用 Decimal 的 ROUND_CEILING。
- 商品迁移后不再允许新绑定运费模板，运费试算明确拒绝。模板管理接口仅保留存量资料处理，不构成新订单报价能力。
- 运费超过 Numeric(15,2) 上限时明确拒绝。后续结算须重新校验模板状态与规则版本；未来若开放删除，须补齐锁定和引用检查。

### 接口形态

管理 API 使用 /api/v1/admin 下的 products、inventory、shipping 等领域路径；消费者 API 按 products、addresses 等领域组织。具体机器契约只由后端导出至根 openapi.json，不维护另一份字段契约。列表有界分页，写操作使用明确请求 Schema，版本冲突不静默覆盖。

## 4. 应用事务与安全

管理写操作经过管理员会话、精确 PermissionCode、CSRF、事务内权威校验和 AuditCoordinator。外层编排拥有事务，领域内部命令与 Repository 不提交；Repository 返回权威数据，应用服务决定授权。Admin 提供分类和运费模板批量启停、商品批量上下架及同一商品内 SKU 批量启停，限制 1 至 100 个唯一目标、核对 revision、固定顺序锁定并全有或全无。SKU 批量命令核对共享商品版本。

商品、库存、地址和运费按领域定义稳定错误码，统一 AppException 和 ResponseModel。未知错误明确传播，数据库约束冲突只在能识别业务约束时映射为业务冲突。

## 5. 当前交易链路与外部边界

1. 商品和地址提供快照 DTO；订单已保存快照，不保留对可变商品资料的强依赖。
2. 结算预览与创建订单共用服务端会员价格和平台运费；创建时重新计价并校验报价指纹，客户端金额不作为成交依据。
3. 库存占用与限购预占使用订单事实；取消或到期先裁决支付，已成功支付入队成交恢复，未决支付入队渠道查询并保留预占，无未决支付时在同一事务释放。可信成交确认预占，显式单轮 Worker 处理内部恢复任务，常驻调度仍待部署。
4. 外部资金调用仍须采用持久意图、事务外调用、结果确认与短事务落库。超时保留结果未知。
5. 售后只允许已成交且实物未发货或虚拟未交付订单整单申请；系统全量展开原明细及原运费。未接单自动审核，已接单由管理员审核；正额退款创建独立 `refund_attempts` 和持久任务，零额售后不伪造渠道退款。
6. 可信退款确认先保存资金成功事实并入队补偿；独立补偿事务完成原 SKU 回补、限购 refunded 标记、佣金撤销或追回、原消费资格冲销及履约取消。归档 SKU 的回补立即再次清退可用库存。佣金按交付时间和原政策 settle_delay_days 计算结算时间，新增入账和提现释放先抵销欠款。
7. 双轨账户的每次变动与账户 revision、唯一幂等流水及结果余额快照同事务保存。默认人工提现流程开放申请、审核和线下转账确认：审核通过只保留冻结余额，具备 `withdrawals:complete-manual` 权限的管理员必须填写线下凭证引用后才能确认到账并结清冻结余额。当前没有第三方自动转账、渠道回调或未知状态查询能力。
8. 微信身份映射及无密码账户边界已有模型；可信换码与小程序 Bearer 会话仍待接入，当前不可用适配器明确返回错误，不把存量 Cookie 会话作为小程序登录。

## 6. M2 交易实际边界

`POST /api/v1/commerce/quotes` 按当前登录用户计算会员价格与平台运费，并返回报价指纹；它不创建订单、不占用库存或限购额度。购物车条目、`POST /api/v1/checkout/preview`、订单创建、本人订单读取与待付款取消均已恢复。旧运费模板试算仍在应用层返回 `503 / COMMERCE_UPGRADE_REQUIRED`。

预览和创建订单共用服务端计价：同一 SKU 先合并数量，实物和虚拟商品拒绝混单；实物订单必须使用本人地址，虚拟订单没有地址快照。平台运费按整单优惠后商品金额与省级配置计算一次；报价指纹覆盖商品、价格、规格、地址及运费规则快照；下单在事务内重新计算，指纹不一致明确拒绝。

订单按用户和请求号幂等，保存规范请求摘要；重放比较合并后的 SKU 数量和地址 ID 摘要，同意图返回原单，不重新检查当前报价。首次创建重新计价并校验报价指纹，锁定用户并读取可售商品、地址、库存与限购账户；订单、明细、订单事件、库存占用、限购预占、冻结分佣来源与 `expire_order` 持久任务在同一事务写入。库存领域承担占用、确认与释放，所有变动递增库存版本并保存独立不可变事件；缺失占用、数量不匹配或非法状态明确拒绝。客户端和管理员没有手工标记支付的 API。

订单状态当前只有 pending_payment、paid 和 cancelled。待付款时限固定 30 分钟，到期任务以 `expire_order` 写入 `durable_tasks`；服务也提供按到期订单逐单释放的命令入口。`scripts.run_durable_tasks` 提供精确数据库确认和显式 `--apply` 的单轮 Worker，领取、业务执行与完成各使用短事务，应用启动不自动执行任务；常驻调度、告警和部署尚未实施。

单轮 Worker 的 expire_scheduled 每单独立事务；OrderService.expire_due 批量入口仍在同一事务处理有界批次，不能将两者事务范围混同。应用数据库连接通过 Settings 的 `DB_LOCK_TIMEOUT` 设置锁等待上限，默认五秒。锁超时必须回滚并明确失败，不自动重做外部副作用。

管理订单详情要求 `orders:read`，接单使用独立 `orders:accept` 权限、版本校验与事务审计。退款申请查询使用 `refunds:read` 权限，响应包含整单金额、审核模式和完成状态；真实退款执行仅由内部可信确认入口接收。Admin 已接入订单详情、接单、退款审核、退款执行记录查询及对账处置等操作，列表筛选只开放当前后端契约声明的字段。

### 订单快照和后续边界

订单明细固化商品名称、SKU 编码、规格、数量、成交单价、分类、品牌、重量、价格和佣金来源快照；订单固化地址、会员、运费、报价和金额。内部零元确认使用唯一确认号；可信支付确认核对支付意图、订单金额、币种、渠道和流水并保存资金事实。后续成交恢复区分正常、重复和迟到收款，重复或迟到收款创建关联原支付的异常退款执行，不丢弃真实收款事实。渠道适配、验签参数、查询和关单仍待后续支付专项实现。

## 7. 支付、履约与售后实际边界

支付意图、履约、退款申请、评价和对账的存量模型仍存在。支付意图按用户请求号幂等，保存商户参考号、金额、币种和渠道状态。微信和支付宝尚未配置时，服务明确保存 `unavailable` 状态，不提供伪造支付成功 API。

可信支付确认仅为内部应用入口，调用方须在渠道验签、商户与应用、订单、金额、币种核对后传入唯一渠道流水和已脱敏载荷摘要。资金确认事务保存支付成功、资金事件及 confirm_order 持久任务；独立成交事务先取得推荐关系图锁，再核对订单与支付，确认库存和限购、创建履约、消费资格贡献及佣金权益。用户状态校验使用 `FOR NO KEY UPDATE`，阻止并发状态修改并允许外键引用检查。业务恢复失败不会回滚已经提交的资金事实。当前没有公开回调路由、真实渠道适配器、验签密钥或外部资金调用。

管理员先接单，实物履约再从待发货进入已发货，由用户确认或发货满七日的持久任务进入已交付；发货事务同时写入 `auto_confirm_fulfillment`。虚拟订单接单后由管理员登记交付引用完成。接单和履约操作均先锁订单，未结束或已完成退款阻断新履约。自动确认命令 `scripts.auto_confirm_fulfillments` 默认 dry-run，并要求精确数据库确认与显式 `--apply`。

退款申请与实际退款已拆分：申请只表达审核和整单完成，正额渠道执行由 `refund_attempts` 保存商户退款号、原支付、金额、渠道状态和可信确认。可信退款成功先提交执行事实、资金事件及有关联申请时的 refund_followup 任务，申请保持 approved；补偿事务再完成库存回补、限购标记、佣金追回、消费资格冲销、履约取消和申请 completed。申请 completed_at 在此时写入原渠道确认时间；补偿失败回滚本轮业务变更，已保存的资金成功事实保留。状态与时间语义统一见[数据库字典第 8.6 节](database-schema-guide.md#86-整单售后渠道退款与补偿)。渠道退款调用、结果未知查询处理器和真实账单联调尚未完成。

地址、订单售后、分销提现及相应管理端点的错误请求体不进入请求日志，避免收货资料、退款说明或收款引用泄露。

## 8. 当前开放边界

已提供分类查询与创建更新、品牌及公共属性字典维护、商品管理与公开查询、SKU 增加及不改变规格身份的原位修改、明确规格转换、上下架、库存查询调整与流水。商品列表批量读取变体、属性采用和图片，避免逐商品加载。

## 9. 阶段 3 分佣政策、钱包与任务实际边界

阶段 3 新增可版本化的分佣政策、商品或 SKU 来源规则、买家等级和受益人等级精确矩阵，以及 `commission_control` 固定设置行。草稿可维护，发布时锁定总开关配置行、归档此前 active 政策并冻结内容；同一时间只有一个 active 政策。全局开关初始化为关闭，缺失或损坏的配置拒绝新分佣决策。

来源规则显式区分通用或等级买家、商品或 SKU 目标及固定、比例或禁佣模式。下单按 SKU 等级专属、SKU 通用、商品等级专属、商品通用、政策默认的顺序选择并冻结来源、政策和矩阵；禁佣规则终止回退。可信成交消费冻结快照并核对全局开关与受益资格。三级矩阵仅匹配真实推荐距离，不补位，按行来源预算 S 从一级到三级截断；一级有效受益人无矩阵时使用来源预算兜底，显式零不兜底。交付后按冻结政策 settle_delay_days 安排结算，实际结算复核订单、履约和售后并写钱包版本账链；整单退款撤销冻结权益或追回已结算金额，不足部分形成欠款。

钱包账户与账本使用连续 revision 和 `balance_after` 快照，结算和退款追回在单一事务内同时更新账户、唯一幂等流水和结果余额。提现默认使用人工流程：申请冻结佣金余额，审核通过不代表到账，管理员以独立权限填写线下付款凭证和说明后才能将 `approved` 变为 `succeeded`，并写入 `withdrawal_paid` 流水。不得直接改钱包余额或以该入口伪造第三方回调。第三方提现执行、可信渠道回调和未知状态查询保留为渠道适配专项。

`durable_tasks` 以 `(task_type, business_key)` 去重，保存版本化载荷、可用时间、失败阈值和租约 token。内部服务提供事务内入队、`SKIP LOCKED` 领取、过期租约计失败、成功完成与受控重试；完成和重试以数据库 `clock_timestamp()` 复核当前租约。`scripts.run_durable_tasks` 单轮执行订单过期、成交恢复、自动确认履约、退款补偿和佣金结算；渠道相关任务明确重试并在达到阈值后进入 attention。支付、退款和提现适配器、常驻调度、告警和部署仍留待后续专项。

## 10. 迁移、验证和交付

会员资格和积分领域已新增等级条件、可冲销资格事件、等级变更历史、积分账户与不可变积分账本。资格事件按当前有效条件评估最高达标活跃等级，并与会员档案版本和历史事件同事务更新。阶段 F 将成交商品金额写为消费贡献，整单退款只冲销原贡献，历史没有原事实时不补造。积分人工授予或冲销使用独立权限、CSRF、审计和完整意图幂等核对，按幂等键与用户账户串行化，积分变动同步资格贡献。有效邀请触发规则尚未定义，积分兑换、到期、消费抵扣和自动订单积分政策未启用。

每阶段新增不可变 Alembic revision；不执行共享数据库变更或导入参考数据。权限目录通过独立受控命令同步，应用启动不自动改权限表。

## 11. Admin 电商运营查询

`app/services/commerce_reporting.py` 是只读运营查询模型，直接读取 PostgreSQL 已提交事实，每次刷新重新查询，不维护第二份余额或状态。查询不进入资金写决策；审核、发货和库存操作仍由对应应用服务在事务内核对权威状态。分页按创建时间和主键稳定排序，计数及页面读取采用数据库读已提交隔离，期间有并发新增时可通过刷新重新读取。

| 页面 | 查询权限 | 主要筛选 | 操作 |
| --- | --- | --- | --- |
| 订单履约 | `orders:read` | 订单、用户、状态、类型 | 快照详情、接单、发货、虚拟交付、选中导出 |
| 退款审核 | `refunds:read` | 申请、订单、用户、状态 | 单条审核与选中导出 |
| 支付记录 | `payments:read` | 支付记录、订单、用户、渠道、状态 | 只读查询与选中导出 |
| 支付对账 | `reconciliation:read` | 记录、渠道、状态 | 对账录入、版本化人工处置与选中导出 |
| 会员与推荐关系 | `members:read` | 用户、直接推荐人 | 档案、推荐链逐层查询与选中导出 |
| 佣金记录 | `commissions:read` | 记录、订单、受益人、状态 | 冻结、结算、追回查询与选中导出 |
| 双轨钱包 | `wallets:read` | 钱包、用户、轨道 | 余额、不可变流水与选中账户导出 |
| 提现审核 | `withdrawals:read` | 申请、用户、全部状态 | 单条审核、线下付款确认与选中导出 |

查询条件必须属于当前资源支持的字段，不支持的条件明确返回 422。普通业务列表通过独立的 `资源:export` 权限导出，每次提交 1 至 100 个唯一选中标识，会员使用 `user_id`。导出端点同时要求读取权限和 CSRF，按响应 Schema 白名单输出，缺失任一目标时整体返回冲突；不导出原始请求摘要、密钥或任意数据库字段。Admin 使用服务端返回的金额字符串生成 CSV，对引号和公式前缀进行转义，失败保留选择，成功清空选择并刷新。

菜单和控件由 `routes.ts`、`access.ts` 及当前管理员权限控制，所有查询在服务端再次校验准确资源权限。权限目录显式同步，不自动给普通角色增加权限。财务查询、导出、对账和相关错误请求体均纳入敏感路径保护。支付和退款渠道仍未接入；提现默认允许经权限保护的线下付款确认，页面必须区分审核和实际到账，不能提供任意状态跳转或余额修改。
