# 可观测性与可靠性基线

## 1. 可靠性定义

可靠性衡量用户期望的结果是否正确、及时完成，只检测进程在线不足以证明可靠。本文提供设置方法和工程边界，具体 SLI、SLO、错误预算、RTO 和 RPO 由本商城结合业务损失确认。

## 2. 部署等级

| 等级 | 适用范围 | 能力边界 |
| --- | --- | --- |
| 单机可恢复模式 | 当前 1Panel 默认路径 | 允许短时中断，依靠不可变版本、健康检查、备份、恢复验证和回滚 |
| 多实例高可用模式 | 对连续性有明确要求的商城部署 | 多实例、负载均衡、数据层高可用、故障转移、滚动发布和容量冗余 |

单机进程自动重启不能消除主机、磁盘、网络、数据库和机房单点，因此不得宣称高可用。

## 3. 健康探针

| 探针 | 回答的问题 | 失败后动作 |
| --- | --- | --- |
| Startup | 应用是否完成启动和必要初始化 | 继续等待或终止启动 |
| Liveness | 进程是否卡死且需要重启 | 重启实例 |
| Readiness | 实例现在能否接收流量 | 从负载均衡摘除，不必立即重启 |

Liveness 不应依赖可短时故障的外部系统，避免依赖抖动导致重启风暴。Readiness 只检查无法服务关键请求的必要依赖，并设置严格超时。

## 4. 可观测信号

应用必须能够关联：

- 结构化日志。
- 请求和业务结果指标。
- 分布式 Trace。
- `request_id`、`trace_id`、主体标识的脱敏形式和 `release.version`。

日志用于事件细节，指标用于趋势和告警，Trace 用于跨组件路径。三者职责不同，不能互相替代。

Backend 使用统一的 Loguru 入口同时支持标准错误流和可选本地文件 Sink。文件 Sink 使用 UTF-8 JSON Lines，绑定的白名单字段位于每条记录的 `record.extra`，默认启用异步队列，按 50 MB 轮转、保留 10 天并压缩为 ZIP；文件路径、开关和生命周期策略由 Backend `Settings` 读取的环境变量控制。只读容器或仅允许 stdout/stderr 的部署必须设置 `LOG_FILE_ENABLED=false`。日志目录和具体日志文件不进入 Git。

### 4.1 阶段 C 安全与请求信号

- 普通请求由 Middleware 输出结构化白名单字段，文件日志的 `record.extra` 包含 `method`、`route`、`status_code`、`duration_ms`、`request_id` 和 `trace_id`；2xx/3xx 请求不记录请求体。错误 JSON 请求仅在非敏感路由捕获，敏感字段递归脱敏并限制为 4096 个字符，响应体、Cookie、Authorization 和 Token 不进入请求日志。
- 登录安全事件写入 PostgreSQL，属于认证结果的一部分。写入失败时登录、刷新或凭据变更失败关闭。
- 高风险管理操作使用审计意图、结果与 `request_id` 关联。成功业务变更与审计结果在同一事务提交；拒绝或异常由独立终结器记录，终结失败输出 critical 信号。
- `REQUEST_LOG_MODE=metadata` 只持久化请求白名单元数据。Middleware 发布到 Redis Stream，独立 Consumer Group Worker 负责 pending reclaim、幂等入库、ACK 和 DLQ；队列故障不改变普通请求结果，但必须输出 critical 日志。
- 登录安全事件和审计事件默认保留 180 天，请求元数据默认保留 30 天。保留清理由显式 dry-run/`--apply` 工具执行。

Readiness 当前检查 PostgreSQL 与认证必需的 Redis。请求元数据功能关闭时不要求 Worker 存活；启用后必须单独监控 Stream backlog、pending 数、DLQ 增长和消费者心跳。

### 4.2 Admin 系统概览

- `GET /api/v1/admin/system/overview` 是面向运维人员的辅助观测页面接口，读取权限为
  `system:overview:read`。它不能替代容器、负载均衡器和部署平台使用的 `/health/ready`，依赖可用性的
  权威判断继续以 Readiness 为准。
- 数据库与 Redis 每次请求执行实时探针。Redis 处于 `required` 模式且探针失败时，系统综合状态为
  `unavailable`，与 Readiness 语义一致。
- 业务遥测使用 `<project>:<environment>:system:telemetry:v1:overview` Key，TTL 为 120 秒。缓存值记录
  `sampled_at`，响应通过 `source` 区分数据库采样、Redis 缓存和不可用，缓存故障会记录结构化日志并回退到
  有超时限制的数据库采样。
- 当前默认单 Backend 实例通过进程内锁合并同一实例的缓存未命中请求。本商城启用多 Backend 实例且需要
  高频轮询时，应增加跨实例分布式刷新锁或独立遥测采集任务，不能把进程内锁表述为跨实例防击穿能力。
- 普通用户数只统计未进入回收站的用户；管理员和角色只统计启用记录；文件资产统计现存记录；审计事件只统计
  `SECURITY_EVENT_RETENTION_DAYS` 保留期内的现存记录。精确统计只降低执行频率，不承诺消除大表统计成本。
- 响应只公开运行时版本、公开文件访问路径和 CORS 信任源数量，不返回本地文件系统路径、完整 CORS 来源、
  密钥或其他内部配置。存储与安全信息属于配置摘要，不能作为可用性探针或无条件健康结论。

**`REQUEST_LOG_MODE=metadata` 启用决策指引**：以下场景适合启用该模式：（1）需要按 `request_id` 关联后台日志与前端错误的排障场景；（2）有合规要求需要保存 API 访问记录但不需要完整请求体的系统；（3）管理端运维人员需要查看错误请求入参的系统。以下场景不建议启用：系统流量极低或 Redis 资源受限的个人项目；对 Redis Stream 背压、Worker 进程和 DLQ 缺乏运维能力的场景。关闭时（默认），Middleware 仍输出结构化访问日志到 stdout/文件 Sink，只是不做 PostgreSQL 持久化和 Admin 抽屉展示。

**多实例部署 Redis 共享要求**：当 Backend 以多实例方式运行时，以下能力**必须**共享同一 Redis 实例或 Redis Cluster，不得各实例独立使用独立 Redis：限流计数器（`rate_limit`）、登录安全事件并发锁、CSRF 比较摘要、Session 缓存、请求元数据 Stream（`REQUEST_LOG_MODE=metadata`）。使用独立 Redis 会导致同一用户的限流计数分散、CSRF 校验跨实例不一致。单机可恢复模式部署只有一个 Backend 实例，不存在此约束。本商城选择多实例部署时，必须在架构文档中明确 Redis 拓扑（单节点 / 哨兵 / Cluster）及其对 Readiness 检查和故障转移的影响。

## 5. SLI 与 SLO

本商城优先从用户可观察结果定义 SLI，例如：

- 成功完成的关键请求数除以有效请求总数。
- 在目标延迟内完成的关键请求比例。
- 数据正确且新鲜的用户操作比例。

SLO 必须低于 100%，由业务和技术负责人共同确认。错误预算需要实际影响发布节奏：预算快速消耗时暂停高风险功能变更，优先处理可靠性问题。

## 6. 容量与故障控制

- HTTP、数据库、Redis 和外部请求设置独立超时预算。
- 连接池、并发任务、队列和批处理设置硬上限。
- 优雅停机停止接收新请求，等待有界时间完成进行中的工作。
- 重试采用有限次数、退避和抖动，不能放大副作用。
- 结果未知的写操作进入查询、对账或人工处理流程。
- 缓存不能成为权威数据源，失效和一致性策略必须明确。

## 7. RTO、RPO 与演练

生产发布前，本商城必须定义：

- RTO：故障后恢复关键能力的最长时间。
- RPO：可接受的数据丢失时间窗口。
- 备份频率、保留期、异地边界和加密要求。
- 恢复步骤、负责人和验证查询。

备份任务成功不等于可恢复。必须定期在隔离环境执行恢复演练并记录耗时、数据校验和改进项。

## 8. 告警与事故

告警面向可行动问题，优先使用错误预算消耗、用户错误率、延迟和容量饱和度。没有负责人、没有处理动作或长期无人响应的告警必须整改。

事故处理步骤见 [事故响应手册](../operations/incident-response.md)，发布与回滚见 [发布与回滚手册](../operations/release-and-rollback.md)。
