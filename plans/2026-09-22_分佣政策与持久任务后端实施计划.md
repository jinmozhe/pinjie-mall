# 分佣政策与持久任务后端实施计划

## 1. 当前状态和结果

- 状态：已结束
- 结果：已完成；阶段 3 后端模型、迁移、接口、契约和文档已交付，适用轻量门禁通过

## 2. 关联需求

- `BASE-COM-303`：佣金生命周期。

## 3. 背景

阶段 2 已提供会员等级、报价和平台运费。现有分销实现仍使用固定两级费率，钱包流水没有账户版本和结果余额，支付、退款和提现也没有统一的持久任务恢复基础，不能满足当前数据库字典定义的三级预算分佣模型。

## 4. 目标

- 新增可版本化的分佣政策、佣金来源规则和精确三级分配矩阵，并通过 `commission_control` 提供全局熔断。
- 将佣金、追回、钱包和提现的数据模型升级为目标账链结构，保留推荐关系和已存在的查询边界。
- 提供管理端政策和总开关接口，采用权限、CSRF、revision 与审计。
- 新增 `durable_tasks` 模型、事务内入队和租约领取基础，为后续支付、退款、结算和提现恢复使用。
- 阻断旧固定两级发佣入口，避免交易恢复前继续产生不符合目标模型的佣金。

## 5. 非目标

- 小程序、Admin 页面、真实支付、退款、提现渠道及任务 Worker 部署。
- 购物车、订单、支付、履约、售后、限购和真实佣金生成流程恢复。
- 实际数据库升级、权限同步到数据库、pytest、测试数据库迁移或 PostgreSQL 并发动态验证。

## 6. 现状分析

`member_profiles` 已保存首次推荐关系，阶段 2 已提供会员等级。旧 `commission_records` 以订单和固定两层费率建模，不能表达订单明细来源预算、三级政策快照或矩阵截断。`wallet_ledgers` 缺少连续账户版本和结余快照，`durable_tasks` 尚不存在。

## 7. 方案设计

- `commission_policies` 使用草稿、激活、归档状态与不可变内容版本；发布时锁定 `commission_control` 稳定设置行，保证最多一个 active 政策。
- 来源规则严格区分 SKU 或商品、通用或指定买家等级，并以 disabled 作为终止回退的显式规则。矩阵按买家等级、真实距离和受益人等级唯一匹配，层数受政策限制。
- 新分佣计算服务仅供后续可信成交调用，按来源预算、候选额和一级到三级的剩余预算截断生成冻结事实。未配置、全局关闭或禁用来源产生零佣金。
- 钱包每次变动都递增账户 revision，同时写入唯一幂等流水和 JSON 结余快照。未接入真实提现渠道时，提现申请和伪造成功入口保持不可用。
- 持久任务仅保存业务意图、错误摘要、失败计数和租约；领取、成功、重试和关注状态使用 revision 与租约 token 防止重复执行。

## 15. 实施结果

- 新增 `commission_policies`、`commission_amount_rules`、`commission_distribution_rules` 和 `durable_tasks`，并在 `system_settings` 增加初始化关闭的 `commission_control` 稳定行。
- 新增政策草稿、来源规则、三级矩阵、发布归档和分佣总开关的管理接口；写入接口均声明精确权限、CSRF、revision 与审计。发布锁定 `commission_control`，保证空 active 政策和政策切换使用同一控制对象。
- 升级佣金权益、追回、钱包账本和提现模型为阶段 3 目标字段。新增通用钱包账链服务，确保账户 revision、唯一幂等流水与结果余额快照同事务更新。
- 新增持久任务入队、租约领取、过期租约失败累计、完成和重试服务；未创建任务 Worker，也未使支付、退款或提现产生外部副作用。
- 旧固定两级发佣、佣金结算和追回入口返回 `503 / COMMERCE_UPGRADE_REQUIRED`；提现渠道未接入时，申请与审核返回 `503 / WITHDRAWAL_CHANNEL_UNAVAILABLE`。
- 根 OpenAPI 已重新导出，`packages/api-client/src/` 已生成。为保持契约消费者可编译，Admin 会员列表改用 `level_id`。
- 通过 Backend Ruff、格式、Mypy、导入边界、编译、应用导入和 Alembic 头部检查，Admin typecheck/lint、工作区、边界、OpenAPI 例外、文档治理及本轮 Markdown 定向检查。
