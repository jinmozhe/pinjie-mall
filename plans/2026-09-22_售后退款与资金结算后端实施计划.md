# 售后退款与资金结算后端实施计划

## 1. 当前状态和结果

- 状态：已结束
- 结果：已完成；阶段 5 后端、迁移、契约与适用轻量门禁已同步

## 2. 关联需求

- `BASE-COM-201` 至 `BASE-COM-205`：支付、可信确认、履约、整单售后与对账。
- `BASE-COM-303` 至 `BASE-COM-305`：佣金生命周期、双轨钱包与提现。
- `BASE-ADMIN-005`、`BASE-ADMIN-006`：交易履约售后和会员分销财务的服务端能力。

## 3. 背景

阶段 4 已完成下单、可信成交、履约创建和佣金冻结的后端本地实现，但退款仍复用旧申请模型，未有独立执行事实、整单原运费退款、库存回补和佣金追回。佣金结算、提现执行和收款、退款、提现三类对账也尚未接入目标模型。

## 4. 目标

- 新增独立 `refund_attempts` 资金执行事实，完成未发货或未交付订单的整单退款申请、审核、可信确认和结果未知恢复边界。
- 可信退款确认后同一事务回补原 SKU 库存、保留累计限购历史，并撤销冻结佣金或追回已结算金额。
- 按交付后延迟规则结算佣金，维持钱包版本账链和幂等性。
- 建立提现申请、审核、执行意图、可信打款确认和结果未知恢复边界；未接入渠道明确不可用。
- 将对账扩展为收款、退款和提现三类事实匹配与差异记录。

## 5. 非目标

- 小程序工程、Admin 页面适配、真实微信/支付宝或提现渠道联调。
- 实际数据库升级、数据回填、测试数据库迁移、pytest 和 PostgreSQL 并发动态验证。
- 已发货或已交付后的退货、验货、期限与物流逆向流程。
- 会员资格、积分、自动任务 Worker 的部署和生产调度。

## 6. 现状分析

现有 `refund_requests` 同时承载审核和渠道事实，无法表达目标模型的独立退款执行及恢复。`commission_records`、钱包和提现已有版本与流水字段，但结算、追回及渠道执行入口受控阻断。现有对账只覆盖支付渠道流水。阶段 5 需以前向迁移分离资金事实，并让退款、库存、限购、佣金和钱包变更由应用服务在短事务内协调。

## 7. 方案设计

- `refund_requests` 表达整单售后申请和审核，`refund_attempts` 表达一次渠道退款执行、商户退款号、渠道事实、未知状态与载荷摘要；申请与执行均有请求内容校验和唯一业务键。
- 仅已付款且未发货实物或未交付虚拟订单可申请。退款金额由原订单商品实付和原运费重算，零金额订单只完成业务退款，不伪造渠道资金事实。
- 可信退款确认在锁定订单后确认退款执行、回补原 SKU、将限购事实标记为 refunded，并取消冻结佣金或创建追回事实和钱包扣减；重复确认不重复写账。
- 佣金结算只处理已交付且到达 `settle_after` 的冻结权益，使用 `durable_tasks` 记录恢复意图。提现按审核、执行和可信确认分离，真实渠道未接入时返回明确不可用。
- 对账记录增加类型、关联退款或提现和人工处置事实，匹配不改变渠道真实状态。

## 9. 实施顺序

1. 复读退款、履约、佣金、钱包、提现和对账的当前模型、服务、路由与迁移。
2. 新增 `refund_attempts` 和必要前向字段，定义退款、佣金、提现和对账事实约束。
3. 实现整单售后、可信退款确认、库存回补、限购流转与佣金撤销或追回。
4. 实现佣金结算、提现执行恢复边界和三类对账。
5. 导出 OpenAPI、生成 API Client，处理受影响消费者的静态检查问题。
6. 同步文档并运行授权范围内的轻量门禁。

## 15. 实施结果

已实现独立 `refund_attempts`，将退款申请迁为整单审核事实，并将渠道退款、商户退款号和可信确认独立保存。未发货实物和未交付虚拟订单可申请整单退款，系统全量展开订单明细与原运费；未接单自动审核，已接单由管理员审核。正额退款建立持久执行意图，可信确认同一事务完成原 SKU 回补、归档 SKU 清退、限购 refunded 标记、佣金冻结撤销或已结算佣金追回、钱包欠款及履约取消；零额售后不创建渠道退款执行。

佣金交付七日后建立结算任务并写入版本账链，退款追回按唯一追回关联防重并写完整结果余额快照。对账记录已支持 payment、refund、withdrawal 三类渠道流水匹配。提现渠道尚未接入，现有申请和审核端点继续明确返回 `503 / WITHDRAWAL_CHANNEL_UNAVAILABLE`，不冻结余额或伪造资金成功。

已重新导出根 OpenAPI 并生成 API Client。Backend Ruff、格式、Mypy、导入边界、编译、应用导入和 Alembic head 均通过；Admin typecheck 与 lint 通过。治理检查结果见剩余问题。

## 16. 剩余问题

- 实际数据库升级、权限同步、真实支付和提现渠道、任务 Worker、pytest、测试数据库迁移和 PostgreSQL 并发动态验证未执行。
- 历史部分退款和旧对账记录不能被无依据迁为整单事实；`20260922_05` 检测到旧退款或对账数据会明确失败，需经授权的历史数据方案或已核实的本项目本地开发库重置。
- Admin 交易和资金页面尚未消费阶段 5 新契约，本轮仅验证其 typecheck 与 lint。
