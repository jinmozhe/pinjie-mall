## 4. 目标

1. 补齐四阶段需求、共同不变量和验收条件。
2. 第一阶段实现商品分类、SPU/SKU、独立库存基础、地址与运费模板。

## 7. 方案设计

业务规则唯一来源为产品需求基线，领域机制进入 commerce-backend 架构文档。

### M1 详细方案

- 商品与库存分域，采用稳定 SKU 标识；无规格商品建立默认 SKU，编辑不删除重建 SKU。
- 分类最多三级，结构修改串行，拒绝循环和超深结构。
- 商品支持实物/虚拟、草稿/上架/下架、规格、分类和图片资产；SKU 独立价格、重量和启停。
- 库存账户以 SKU 唯一，数量非负；人工调整要求请求号、原因、版本和持久流水。
- 地址写入按用户串行，每用户至多一条默认地址；只允许本人操作。
- 运费支持按件/克、指定与默认地区、包邮门槛和排除地区；全程 Decimal 计算。
- 管理写入口沿用准确权限、Cookie/CSRF、权威状态校验及 AuditCoordinator。
- 新增 Alembic revision、metadata、OpenAPI 和生成客户端，不执行数据库升级。

### M2 详细方案

- 关联 BASE-COM-101 至 BASE-COM-105；仅改 Backend、迁移文件、生成契约和关联文档，不开发页面。
- 购物车以用户和稳定 SKU 唯一；每用户最多 100 条，每条数量 1 至 999，版本冲突明确拒绝；购物车不持有库存。
- 结算预览和下单调用同一计价用例，从商品、地址、运费领域的公开 DTO 读取当前事实。服务端计算金额并返回报价指纹；下单必须携带该指纹，资料或价格变化时拒绝成交并要求重算。
- 订单按用户与请求号唯一，保存规范化请求摘要；原请求重放读取已创建订单，相同请求号不同内容返回冲突。
- 订单、明细、事件和库存占用由一个应用事务完成；分类/商品快照沿用目录事务锁，模板、SKU 库存按 ID 固定顺序锁定。
- 库存新增订单占用记录和独立事件流水，保存可用/占用数量前后值；预留、确认扣减和释放分别幂等，所有余额受数据库约束。
- 订单状态先支持待付款、已付款、已取消。用户只读本人订单并取消本人待付款订单；管理端提供准确 orders:read 权限的只读查询。支付事实确认仅为内部应用入口，不开放客户端或管理员伪造付款接口。
- 订单固化商品名称、规格、SKU 编码、数量、价格、商品版本、地址和运费规则版本。历史数据不因商品或地址编辑变化。
- 超时扫描以持久化订单期限和待付款状态为依据；独立命令默认 dry-run，显式 apply 后每单短事务使用 SKIP LOCKED 领取，失败回滚并非零退出，重跑依赖持久状态恢复，不启动定时服务。
- 并发写统一使用有界锁等待。用户写按用户锁定；已有订单状态改变先锁订单，再固定顺序锁库存，不持有数据库事务调用外部渠道。
- 用户已确认：待付款 30 分钟关闭，实物虚拟分单，同模板合并件数/重量与组内金额计费，不同模板运费相加。订单保存独立期限，预览指纹覆盖价格、资料、地址和规则版本。
- 新增后继 Alembic revision，不改 M1 revision；补充领域、API 拒绝与 PostgreSQL 并发回归源码。按现有授权仅运行轻量门禁及静态迁移核对，任何 pytest 和真实迁移未授权。

### M3 详细方案

- 关联 BASE-COM-201 至 BASE-COM-205；仅改 Backend、迁移文件、生成契约和关联文档，不开发 Admin 或小程序页面。
- 支付意图按用户和请求号幂等，保存渠道、金额、币种、请求摘要及不可变事件。微信和支付宝未配置时记录不可用事实，不产生伪造付款成功。
- 已验签的渠道回调只通过内部应用入口进入；在短事务内锁定支付意图和订单，核对渠道、商户、应用、订单、金额、币种与唯一渠道流水，再确认付款、创建履约单并保存支付事件。
- 实物履约状态为待发货、已发货和已交付；管理员发货后写入物流快照和七日自动确认期限，用户确认或超时扫描完成交付。虚拟订单由管理员写入交付引用后完成交付。
- 退款按用户选择的订单明细数量和商品金额创建幂等申请，不退运费、不自动入库；累计已成功、待审核、已审核和处理中金额不得超过订单商品金额。管理员审核或拒绝，退款成功只由后续渠道事实内部确认。
- 评价限定本人已交付订单明细，每个订单明细只允许一条公开评价。对账导入只能记录渠道账单和本地支付事实的匹配或差异，不改变订单状态。
- 新增后继 Alembic revision、精确管理权限、内部支付确认 Port、用户与管理 API、领域不变量测试源码和默认 dry-run 自动收货命令。真实渠道适配、验签密钥、数据库升级、权限同步与重型验证不执行。

### M4 详细方案

- 关联 BASE-COM-301 至 BASE-COM-305；仅改 Backend、迁移文件、生成契约和关联文档，不开发 Admin 或小程序页面。
- 会员档案固定初始等级为 `standard`，当前不参与商品折扣或其他计价；推荐码绑定仅允许一次，拒绝自邀与循环。
- 可信支付确认后，按订单商品实付金额不含运费创建最多两条佣金快照：一级 10%、二级 5%，均按两位小数半舍入并冻结。交付满七日后结算；规则、受益人、基数、比例和时间均保留。
- 退款成功按退款商品金额比例撤销冻结佣金或追回已结算佣金；追回时优先扣减佣金钱包可用余额，余额不足形成可追溯欠款。退款渠道事实仍由后续支付适配器进入内部确认入口。
- 双轨钱包固定为佣金钱包与消费钱包。佣金钱包仅接收已结算佣金，可提现、不可购物；消费钱包仅允许后续购物抵扣、不可提现；两条轨道禁止互转。本阶段不提供消费钱包充值或购物扣款，避免制造无来源资金。
- 提现申请按用户和请求号幂等，冻结佣金钱包余额；管理员审核通过只记录待渠道执行，审核拒绝解冻。真实打款与结果未知恢复待后续渠道适配，不提供伪造成功入口。
- 新增后继 Alembic revision、精确管理权限、用户与管理 API、默认 dry-run 佣金结算命令和领域不变量测试源码。真实渠道、数据库升级、权限同步与重型验证不执行。

## 15. 实施结果

### M0 与 M1 本地交付

- 统一产品需求、四阶段路线和首阶段设计已落地；各阶段继续维护同一计划。
- 实现四个领域、八张表、管理与消费者共 25 个 HTTP 操作及 11 项管理权限。涵盖稳定 SKU、商品上下架、图片引用保护、幂等库存调整、本人地址和运费试算。
- 管理写操作在审计事务内重新校验管理员与精确权限；商品目录修改串行，库存行锁与版本校验，地址按用户串行，仓储不承担权限决策。
- 交付新增 Alembic revision，静态核对八张表的 78 条 DDL 与模型一致，没有访问数据库。
- 根 OpenAPI 与客户端已生成并再次生成核对内容一致；原有路径与 Schema 无语义修改，新增 18 个路径、43 个 Schema。
- 补充运费边界、分类环、规格冲突、库存幂等、地址归属和默认切换、事务内权限失效、商品图片删除保护的测试源码，以及真实 PostgreSQL 库存并发与回滚用例。上述测试均未运行。

### M2 本地交付

- 实现购物车、服务端结算预览、报价指纹、幂等待付款订单、订单明细和状态事件；订单快照固化商品、地址、运费规则与金额。
- 实现实物与虚拟商品分单、本人地址校验、同模板合并件数或重量计费、不同模板运费累计，以及预览报价变更后的明确拒绝。
- 下单在同一事务内按用户、目录、SKU、运费模板和库存账户保护并发，创建库存占用；取消、30 分钟到期扫描和内部支付确认分别释放或确认占用。达到订单到期点的支付确认明确拒绝。
- 新增购物车、订单、订单明细、订单事件和库存占用五张表的 Alembic revision，静态 DDL 核对通过且没有连接数据库。
- 同步 OpenAPI 与生成客户端，新增 6 个消费者交易 API。超时处理命令默认 dry-run，只有显式确认数据库名并传入 `--apply` 才会写入。

### M3 本地交付

- 实现实物待发货、发货、用户确认或七日自动确认收货，以及虚拟订单管理员交付；履约状态事件完整记录操作者和版本。
