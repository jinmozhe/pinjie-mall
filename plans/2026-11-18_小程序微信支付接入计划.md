## 背景

用户准备配置小程序微信支付，需要明确后台应配置什么、回调地址如何确定，以及当前代码距离真实收款还缺哪些环节。现有商城已经具备支付意图、可信确认、售后与恢复任务基础，但真实渠道没有接通，单独填写环境变量无法形成收款能力。

### 对原有说明的核验

| 原有说法 | 核验结论 | 本项目处理 |
| --- | --- | --- |
| 支付通知地址由后端下单时传入 `notify_url` | 正确，普通商户 JSAPI/小程序下单接口必填此参数 | 从服务端受控配置读取，禁止消费者请求指定或覆盖 |
| 原代码还没有微信支付通知接口 | 与实施前源码一致；现已新增 | 专用渠道通知入口，不能把内部可信确认方法直接开放 |
| 已有 AppID、AppSecret，可继续补支付配置 | 方向正确但信息不完整 | 增加商户签名材料、微信验签材料、APIv3 密钥、通知地址及开关 |
| 小程序遇到 JSAPI 支付授权目录必填时，填写 API 域名 | 不正确 | 官方明确小程序无需配置该目录；先核实操作的产品场景和页面，不能随意填 API 域名 |
| 商户后台的回调输入框通常用于 Native 或分账 | 不能这样概括 | 退款支持商户后台配置通知地址，申请退款请求中的 `notify_url` 优先 |
| 两个拟定的 HTTPS 地址就是当前线上回调地址 | 只能作为设计值 | 路由已有源码，域名部署、证书及公网路由未核实 |

“由后端传入”表示请求中的地址由服务端控制，不代表每笔交易随机生成地址。推荐各环境使用固定配置，不从请求 Host、前端参数或用户输入拼接。

## 目标

1. 完成普通商户直连的小程序微信支付：创建支付意图、下单、调起收银台、通知、查单和订单成交。
2. 接通整单退款及重复付款、迟到付款的异常退款，复用原有资金确认与业务补偿。
3. 支持通知重复、乱序、丢失、接口超时、进程重启及任务重试，资金事实可查询、可恢复、可核对。
4. 保留用户身份、手机号交易前置、零元内部成交、库存、佣金与现有后台权限规则。
5. 将本地实现完成、真实渠道验收和生产启用分别记录。

## 非目标

- 不自动执行未点名的 pytest、Vitest、构建、浏览器、数据库或真实平台验证。
- 不接支付宝、服务商子商户、多商户、H5、Native、分账、钱包充值或自动提现。
- 不改部分退款、发货后售后政策，不新增人工强制支付成功入口。
- 不启用 Web，不启动或暴露 3000 端口。
- 不在 Admin 保存或展示商户私钥、APIv3 密钥，不把秘密写入仓库或小程序。
- 生产开通、密钥设置、数据库实际升级、真实资金操作、镜像发布和部署分别授权。

## 方案设计

### 商户后台与上线前准备

1. 核实当前为普通商户直连。若实际属于服务商/子商户，先调整本计划的商户字段、接口与验签上下文。
2. 核实小程序已认证、商户已获得相应 JSAPI/小程序支付权限。商户后台发起 AppID 绑定，公众平台确认授权，核对双方最终状态。
3. 获取商户号、商户 API 证书序列号及对应私钥；设置 APIv3 密钥；获取微信支付验签公钥与公钥 ID，或确认商户当前平台证书模式。
4. 本项目优先采用明确的微信支付公钥模式。已有商户处于平台证书模式或切换灰度期时，先核对共用该商户号的其他系统；禁止擅自切换，也不靠自动猜测密钥形成永久双轨。
5. 核实小程序后台请求合法域名覆盖实际 Backend HTTPS 域名。该配置、支付通知 URL 与 JSAPI 支付授权目录是独立事项。
6. 交易类小程序上线前核实公众平台运营规范和订单发货管理要求。商城现有发货记录不能证明已经上报微信；若缺少平台接入，补充本计划实施范围和验收后再开放正式支付。
7. 核实 HTTPS 证书、公网可达性、反向代理和防火墙。通知路径不能出现登录跳转、验证码或重写原始报文；本机 localhost 无法直接接收微信公网通知。

只需要登记配置项及其就绪状态，不要求用户在聊天中粘贴私钥、密钥、证书包或真实环境文件。

### 服务端配置

下列配置现已由 Settings 校验和应用生命周期加载。实际材料预留，完整运行步骤见[微信支付手册](../docs/operations/wechat-pay.md)。

| 配置 | 用途 | 保护与校验 |
| --- | --- | --- |
| `WECHAT_PAY_ENABLED` | 控制新支付发起 | 默认关闭；启用但材料不完整时明确失败 |
| `WECHAT_PAY_RECOVERY_ENABLED` | 停收后继续通知和资金恢复 | 默认关闭；存在在途资金时保留开启 |
| `WECHAT_SHIPPING_ENABLED`、`WECHAT_SHIPPING_CARRIERS` | 平台发货及运力映射 | 默认关闭，启用须正确 AppSecret 及支付恢复 |
| 现有 `WECHAT_APP_ID` | 下单及调起使用的小程序 | 与运行小程序、已绑定商户及服务端身份记录一致 |
| `WECHAT_PAY_MCH_ID` | 商户号 | 必填、固定环境归属 |
| `WECHAT_PAY_MERCHANT_SERIAL_NO` | 商户 API 证书序列号 | 与请求签名私钥配对 |
| `WECHAT_PAY_PRIVATE_KEY_PATH` | 商户 API 私钥挂载路径 | 仅服务端可读，不写入镜像或代码 |
| `WECHAT_PAY_API_V3_KEY` | 通知资源解密 | 使用受控秘密注入、隐藏日志输出 |
| `WECHAT_PAY_PUBLIC_KEY_ID`、`WECHAT_PAY_PUBLIC_KEY_PATH` | 微信支付应答及通知验签 | 按明确 ID 选择受信公钥，未知 ID 拒绝并告警 |
| `WECHAT_PAY_NOTIFY_URL` | 支付通知地址 | HTTPS 完整地址，无查询串，使用部署白名单 |
| `WECHAT_PAY_REFUND_NOTIFY_URL` | 退款通知地址 | 每笔退款显式传入，不依赖后台兜底 |
| `WECHAT_PAY_CONFIG_VERSION` | 非秘密配置版本 | 与商户号、AppID 一起快照，支持历史交易恢复 |

`WECHAT_APP_SECRET` 用于微信身份相关调用，不能替代商户请求签名私钥或 APIv3 密钥。商户私钥负责我方向微信证明身份；微信支付公钥负责核验微信应答和通知；APIv3 密钥负责解密通知资源。

关闭新支付不能关闭历史通知、查单和退款能力。历史未结清交易引用的商户配置和验签材料必须保留到完成恢复；旧密钥退役需要明确期限、观测及移除条件。

### 回调与公开契约

已实现以下路由，域名沿用用户给出的候选值；均未部署、未验证：

```text
POST https://api.guizhouzhongying.com/api/v1/payments/wechat/notify
POST https://api.guizhouzhongying.com/api/v1/refunds/wechat/notify
```

- 通知入口不要求消费者 Bearer 或管理员 Cookie/CSRF，独立以微信签名验证身份；其余业务端点权限不变。
- 通知返回微信协议规定的 HTTP 状态和失败体。实施时在 Backend 规则及错误模型中登记这两个第三方协议入口的窄范围例外，不能套用商城 `ResponseModel`，不能全局放松响应规则。
- 保留创建支付意图路径和 `request_id` 幂等语义。新增可空且状态受约束的调起参数对象，字段为 `timeStamp`、`nonceStr`、`package`、`signType`、`paySign`；只在已取得合法预支付信息时返回。
- 按本人请求号找回意图使用 `/orders/{order_id}/payment-attempts/by-request/{request_id}`，按本人订单查有效意图使用 `/orders/{order_id}/payment-status`，请求号由 `/payments/intent` 提供。均已进入 OpenAPI；不接受客户端提供 OpenID、金额、商户号或通知地址。
- `unknown`、渠道关闭、支付成功与订单成交分别表达，避免“支付成功但成交任务尚未完成”被前端展示为可再次付款。

### 下单、签名与状态恢复

1. 短事务校验本人订单、手机号前置、应付金额、币种、截止时间及活动支付意图，保存支付意图、幂等请求摘要和非秘密配置快照。
2. 新微信支付单号使用统一 UUID v7 生成器产生的 32 位十六进制表示，不增加超长前缀；保留既有历史单号，不批量改写已存在记录。历史 `unavailable` 意图不得未经核验直接发送给微信。
3. 以当前用户在该 AppID 下的可信身份记录获取 OpenID，禁止接受客户端自报身份。金额由服务端 Decimal 精确转换为整数分，校验上下界；零元订单继续使用内部成交。
4. 事务外通过共享异步 HTTP 客户端调用 `/v3/pay/transactions/jsapi`。采用规范 RSA 签名、完整超时预算、微信应答验签及错误分类；优先复用 `httpx`，密码学采用经过维护的库，依赖准入和锁文件另行核实后确定。
5. 微信 `time_expire` 与本地订单截止时间一致，遵守官方最短下单剩余时长要求；不足时拒绝新下单，不延长商城订单。短事务保存 `prepay_id` 和有效期，再生成调起参数。
6. 同键同内容返回同一意图；重复点击和不同请求号不能制造多个同时可付的渠道订单。旧意图仅在渠道状态明确后才能复用或关闭并创建新意图。
7. 超时、断连或验签失败进入明确错误及待核对状态；按原商户单号查单，禁止换号盲目重下。查无订单后的重提必须使用确定规则和相同业务身份。
8. 接入已有持久任务，处理查单、关单和取消/到期竞态。只有权威渠道结果允许时才释放预占；迟到或重复付款沿用异常退款，不能丢弃资金事实。

### 通知安全与持久处理

- 验证 `Wechatpay-Serial`、时间戳、随机串、签名与原始请求字节，限制请求大小，检查时钟偏差与重放；不能先反序列化再重新序列化后验签。
- 验签后使用 APIv3 密钥解密，核对事件类型、商户、AppID、商户单号、微信流水、整数金额、币种及支付者归属。退款通知按实际字段核对商户、原交易和退款单，不能要求其不存在的 AppID 字段。
- 支付比对订单 `amount.total`，不能把优惠后的 `payer_total` 误当订单应付金额；退款核对退款额与原支付额。非成功事件不得走可信成功方法。
- 新增持久通知接收记录，唯一约束覆盖渠道、商户及通知 ID，记录载荷摘要、验签配置版本、处理状态和必要的最小业务数据；不记录私钥或完整解密敏感报文。
- 在官方 5 秒应答预算内完成验签和可靠落库，再返回 200 或 204；后台任务完成业务核验和状态变更。持久接收失败返回失败，不能先答成功后仅放内存队列。
- 重复相同事件幂等成功；同通知 ID 内容冲突、未知密钥、解密失败及商户/金额不符进入拒绝或隔离告警。已可靠接收但业务匹配失败的事件必须可恢复、可查，禁止直接丢弃。
- 成功支付统一调用 `confirm_verified_payment`，后续成交沿用 `confirm_order`；数据库唯一约束和事务保证重复通知、主动查单与并行 Worker 不重复记账。

### 退款、核对与后台

- 接入 `refund_submit`、`refund_query`、退款通知和现有 `refund_followup`。整单退款含原运费，限制沿用现有未发货/未交付政策。
- 退款商户单号稳定且满足官方长度及字符要求；超时继续按原退款号查询，受理或 `PROCESSING` 不能标为资金已退回。
- 处理 `SUCCESS`、`ABNORMAL`、`CLOSED`。只有核验后的成功才调用 `confirm_verified_refund`，业务补偿另行幂等执行。
- Admin 复用现有支付、退款、对账、持久任务页面，只补必要状态和诊断字段；保留原有权限、CSRF、审计和只读资金历史。
- 复用现有对账记录模型，规划微信交易账单获取与核对任务，将漏通知、金额差异、孤立流水和退款差异送入已有处理流程；人工备注不能伪造渠道资金事实。
- 明确 Worker 的常驻运行、租约、超时重试、最长恢复窗口及人工接管条件。配置支付前必须确认这些能力可运行，不能只部署 HTTP 回调接口。

### 小程序与发货管理边界

- 订单页按后端渠道能力展示付款入口，复用现有请求层、认证恢复和 Query；调用 `Taro.requestPayment`。

## 风险与回滚

- 商户模式或绑定错误：在真实调用前拒绝启用，不自动猜测服务商字段。

- 重复收款及超时：稳定商户单号、活动意图约束、先查后重试、取消关单裁决、异常退款和日账单核对。
- 回调丢失及 Worker 停止：可靠接收后应答，持续查询恢复，记录积压和最老任务时间，超出窗口报警。

- 未接微信发货管理：作为正式启用前置缺口，不能用商城内部发货功能代替平台接入证据。
