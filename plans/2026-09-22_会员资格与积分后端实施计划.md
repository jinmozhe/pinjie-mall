# 会员资格与积分后端实施计划

## 1. 当前状态和结果

- 状态：已结束
- 结果：已完成；会员资格评估、等级历史和积分账本五表的本地后端实现、迁移、管理接口和生成契约已交付

## 2. 关联需求

- `BASE-COM-301`：会员等级、资格和价格规则使用可追溯的服务端事实。
- `BASE-BE-004`：商城领域按数据所有权实现。
- `BASE-DB-001`：关系结构通过 Alembic 演进。
- `BASE-API-001` 至 `BASE-API-002`：公开契约和生成客户端保持唯一来源。

## 3. 背景

数据库字典的 `member_level_conditions`、`membership_qualification_events`、`member_level_events`、`points_accounts` 与 `points_ledgers` 仅为后续规划，未进入当前 62 张 ORM 表和 Alembic 图。用户已授权先实现这五张表对应的后端领域。

## 4. 目标

- 建立会员等级条件、资格贡献事件、自动评估和等级变更历史。
- 建立积分账户和不可变积分账本，支持明确幂等的授予、冲销与人工调整。
- 提供精确权限、CSRF、revision、审计和事务保护的管理 API；同步根 OpenAPI 与生成 API Client。

## 5. 非目标

- 不实现积分兑换、积分抵扣、到期批次、商城支付积分入金或小程序页面。
- 不执行实际数据库升级、pytest、测试数据库迁移、PostgreSQL 并发验证或真实渠道联调。
- 不改造 Admin 页面；现有 Admin 消费者不适配时明确保留为后续工作。

## 6. 现状分析

现有 `member_levels` 和 `member_profiles` 已支持稳定等级、可空当前等级和版本。字典规定条件按等级、指标和聚合维度唯一，资格事件与积分流水必须幂等、仅追加并能关联冲销原事实；积分账户不属于人民币钱包。字典未定义积分兑换、到期、消费抵扣和自动积分发放政策，因此这些能力不在本轮启用。

## 7. 方案设计

- 新增五个 SQLAlchemy Model 和前向 Alembic revision，落实字典中 FK、唯一键、值域、非负余额、增量互斥和冲销归属约束。
- 在 `membership` 领域管理等级条件、资格事件、资格快照和档案等级转换；最高满足全部有效条件的活跃等级成为当前等级，未满足任一等级时清空等级。每次实际变化与 `member_profiles.revision`、不可变等级事件同一事务提交。
- 将资格事件限定为服务端内部命令，按消费、邀请或积分指标写入，冲销只可作用于同用户同指标的原事件，且累计冲销不超过原正向贡献。
- 在独立 `points` 领域维护积分账户与账本。所有余额修改经单一服务、条件更新和唯一幂等键完成；人工授予或冲销需要专门权限、CSRF 和审计。积分变动同步形成可选的资格贡献事件，但不启用任何积分兑换或订单抵扣。
- 管理端提供等级条件 CRUD、资格与等级历史只读、积分账户和账本只读、人工积分调整接口。路由只处理协议和权限，领域服务拥有事务。

## 11. 风险与回滚

- 自动降级只基于已持久化资格事件和当前有效条件，条件或事件缺失不猜测达标结果。
- 余额、等级和历史事件在同一事务内更新；失败整体回滚。冲销追加新事实，不覆盖旧流水。
- 迁移不在应用启动时执行；无法安全迁移既有生产数据时只允许前向修复或经授权恢复。

## 15. 实施结果

新增 `20260922_06`，实现五张表的 Model、迁移与静态核对。会员条件按等级、指标和聚合维度版本化管理；资格事件以幂等键、来源唯一约束和原事件冲销上限保存，事件写入后自动重新评估当前有效条件，变更会员等级时同事务保存档案版本和不可变快照历史。积分账户与流水支持独立权限、CSRF、审计和幂等的人工授予或冲销，冲销只可关联同账户原授予且不超额，积分变动同步资格贡献。根 OpenAPI 与 API Client 已重新生成。Backend Ruff、格式、Mypy、导入边界、编译、应用导入、模型核对与 Alembic head 均已通过，其中静态模型结果为 67 张 ORM 表和 23 张目标新增运行表，迁移 head 为 `20260922_06`；文本、Markdown、文档、工作区、依赖、边界、生产配置、OpenAPI 例外及治理守卫检查均已通过。
