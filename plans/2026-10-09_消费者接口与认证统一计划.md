# 消费者接口与认证统一计划

## 1. 当前状态和结果

- 状态：已结束。
- 结果：已完成；统一消费者接口与微信 Bearer 的本地实现、契约迁移和轻量验证完成，2026-10-10 复核修正会员调用并清理旧认证不可达代码；原系统临时目录清理剩余项保留。
- 日期：2026-10-09。

## 2. 关联需求

BASE-BE-003、BASE-BE-004、BASE-MP-001、BASE-MP-002、BASE-COM-301、BASE-API-001、BASE-API-002、BASE-GEN-004、BASE-QUAL-001。

## 3. 背景

消费者业务已经共用领域服务，但独立客户端路由重复声明地址、购物车、报价、订单及履约动作。项目仅交付微信小程序，用户确认退役消费者浏览器认证，将消费者能力并入原后端业务模块。

## 4. 目标

- 移除全部 `/api/v1/miniapp` 路由，不保留重定向或兼容别名。
- 消费者统一使用微信登录和 Bearer 会话；Admin 继续使用独立 Cookie、CSRF、权限与审计。
- 合并重复业务端点，保留新增查询、字段白名单、本人会话明确集合撤销、未知结果查询和只读注销核对。
- 后端模块按认证、账户、交易、资金及推荐积分职责组织，移除以客户端命名的业务分支与包装。
- 同步小程序、唯一 OpenAPI、生成客户端、相关测试源码及权威文档。

## 5. 非目标

不启动或修改冻结 Web 应用；不启用实际注销、新提现、真实支付或微信登录配置；不变更 Admin 产品功能；不执行数据库迁移、重型测试、提交、推送、发布或部署。

## 6. 现状分析

两种消费者凭据共用 User/UserSession 数据模型。旧 Cookie 写入口关联密码、CSRF 与 Cookie 轮换，不能只替换全局身份依赖。独立消费者查询包含真实新增能力，合并时必须保留。历史数据库 Profile、audience、配置键及迁移文件继续保留其既有存储语义，避免无需求的数据迁移。

## 7. 方案设计

- 原消费者认证模块承接微信换码、刷新、退出及能力查询；旧密码登录、注册、改密和直接注销入口退役。
- 统一 `get_current_user` 只验证消费者 Bearer，拒绝消费者 Cookie 凭据；管理员身份不能替代消费者身份。
- 业务 Router 仅声明统一身份依赖，移除消费者 CSRF；Admin 的全部 Cookie、CSRF 与准确权限继续生效。
- 地址、购物车、结算、订单、履约、资金、推荐积分和账户接口按已有领域路径收敛，消费者查询保留安全响应模型和已有恢复语义。
- 不将历史 Cookie 会话转换为 Bearer；旧凭据不可再访问消费者受保护接口。保留历史数据用于审计。
- 契约按后端实现、导出 OpenAPI、生成 API Client、小程序适配的顺序更新。认证及私有业务的 no-store 和日志保护随能力迁移。

## 9. 实施顺序

1. 登记计划、记录原文与缓存基线，盘点消费者调用与 API 映射。
2. 合并消费者认证依赖与认证服务，移除旧浏览器消费者入口。
3. 按业务合并路由与查询模型，迁移消费者调用及测试源码。
4. 导出 OpenAPI 并生成客户端，运行轻量门禁，修复本次差异。
5. 更新文档、复读差异、清理本次临时产物并结束计划。
