# 交易订单与支付履约后端实施计划

## 1. 当前状态和结果

- 状态：已结束
- 结果：已完成；阶段 4 后端、迁移、OpenAPI 和 API Client 已同步，适用轻量门禁与治理检查见实施结果。

## 2. 关联需求

- `BASE-COM-005`：收货地址。
- `BASE-COM-006`：平台统一运费。
- `BASE-COM-101` 至 `BASE-COM-105`：购物车、订单、快照、限购和状态机。
- `BASE-COM-201` 至 `BASE-COM-203`：支付、可信确认和履约。
- `BASE-COM-303`：成交时冻结三级预算佣金。

## 3. 背景

阶段 1 至 3 已提供商品、库存、统一报价、平台运费、分佣政策和持久任务基础，但购物车、结算和订单入口仍返回升级中错误。阶段 4 恢复本地交易闭环，所有成交必须使用同一服务端报价、订单快照、库存和限购事实。

## 4. 目标

- 恢复购物车、结算预览、原子下单、取消和到期释放。
- 新增累计限购配置与用户商品交易记录，订单、库存预占和限购预占在同一事务中完成。
- 固化商品、规格、价格、会员、地址、运费和佣金来源快照。
- 建立支付意图、可信确认、零元内部成交及持久任务恢复边界，未接入渠道保持明确不可用。
- 支持实物发货、虚拟交付、用户确认和自动确认，并在可信成交时冻结佣金权益。

## 5. 非目标

- 小程序工程、Admin 页面适配、真实微信或支付宝渠道联调。
- 整单售后、退款执行、库存回补、佣金结算与追回、提现和对账。
- 会员资格、积分和自动任务 Worker 部署。
- 实际数据库升级、数据重置、测试数据库迁移、pytest 与 PostgreSQL 并发动态验证。

## 6. 现状分析

现有订单、支付、履约和购物车实现仍基于旧商品运费模板和固定佣金模型，已在阶段 1 至 3 受控阻断。阶段 2 已提供只读统一报价和平台运费配置，阶段 3 已提供佣金政策、钱包账链与 `durable_tasks`。本阶段需要前向迁移旧表并将跨领域动作置于 Application Service 的单一事务中。

## 7. 方案设计

- 订单预览与创建都调用统一报价服务；创建重算并校验报价指纹，不接受客户端金额。
- 按实物或虚拟商品拆单，实物使用本人地址快照，虚拟订单地址为 SQL NULL；运费按整单优惠后商品金额计算一次。
- 新增限购记录，锁定顺序固定为用户、商品限购行、SKU 库存账户；待付款占用在取消或过期时释放，成交后转换为累计已购事实。
- 支付适配器按意图与可信确认分离，零额订单使用唯一内部确认号；所有可信成交复用同一成交入口，创建履约和冻结佣金。
- 支付、关单、过期订单和自动确认均通过持久任务记录恢复意图；未注册的外部渠道直接返回可识别的不可用错误。

## 15. 实施结果

- 新增 `product_purchase_limits` 与 `product_purchase_records` 模型，以及前向 Alembic revision `20260922_04`；订单、订单明细、支付、履约和库存相关字段按阶段 4 目标模型扩展。
