## 当前实施方案

### 已确认的账户与认证模型

- 用户确认微信静默识别为主要认证方式。满足身份处理告知同意且未主动退出时恢复会话，首次可信 AppID/OpenID 无绑定且注册开放时自动创建 user_id、独立 wx_ 用户名和外部绑定；password_hash 为空。
- username 与手机号独立，不使用 OpenID 或手机号作为用户名。手机号授权只补全当前 user_id，不创建第二个账户，不切换账户，不合并资产。
- users 新增可空 phone_e164、phone_verified_at、phone_verification_source，三项全空或全有效，非空手机号全局唯一。历史账号保持原 user_id，不从收货地址或用户名回填。
- 复用现有 user_external_identities，补充可空 union_scope_id 和服务端配置，用于可信 UnionID 范围记录；本期不启用跨 AppID 自动认人，未来先落实联合身份唯一映射再开放第二应用。
- 未识别、已识别未绑定手机号、已识别已绑定手机号三个状态明确。手机号状态通过后端权威记录返回，不能仅依赖 Token 内声明或前端判断。

### 接口、页面和恢复

- 保留 POST /auth/login 的 code 输入及自动建号，ConsumerUserRead 增加 phone_bound 和 phone_masked 安全投影。
- 新增 POST /users/me/phone，以当前 Bearer 身份和一次性手机号 code 绑定。服务端取当前用户在已登记 AppID 下的 OpenID，调用官方 stable_token 和 getuserphonenumber，校验 OpenID 归属、水印及号码结构。
- 手机号换码按 AppID 缓存应用凭据、有限刷新锁、请求限流和 code 摘要单次消费保护。失败明确传播；未知结果通过读取本人资料确认，禁止重放旧 code。
- 绑定事务保持当前 user_id、用户名及资产不变，验证用户、会话、凭据版本和停用状态。已绑定同号幂等，不同号或他人占号拒绝，不提供本期换绑入口。
- 本人资料、手机号绑定、退出、隐私与安全管理使用基础身份；购物车、地址、交易、会员、推荐、积分和资金端点使用已验证手机号身份。拒绝手机号返回独立 403 错误码，避免触发登录刷新循环。
- 公开页面和个人中心外壳不受 AuthGate 整页拦截。私有模块按需引导；公开帮助、隐私、安全说明保持可访问。
- 统一认证页保存白名单返回目标和 15 分钟内存上下文，支持页面栈与 TabBar。商品恢复规格、数量和动作，由用户确认后执行；无目标进入个人中心，取消回来源或首页。
- 官方 chooseAvatar、nickname 表单组件用于资料填写；保留头像上传、绑定、移除及未知结果查询。资料引导允许跳过，不撤销已建立身份或手机号。
- 静默恢复不改变当前页面；主动退出阻止后台自动重登。首次无同意时仍提供公开浏览，主动认证取得必要同意；手机号由用户主动点击官方组件授权。

## 背景

商城需要保持游客公开浏览，在用户主动进入私有模块或发起加购、购买时按需登录。既有微信身份可用于恢复老账户；需要手机号时由用户通过微信组件授权，Backend 使用可信手机号统一完成已有账户登录或首次建号，前端只处理认证步骤。

用户希望手机号成为主要账户识别字段，用户名可以与手机号一致，同时保留未来接入不同小程序及微信开放平台应用的能力。必须区分不变的商城用户主键、可变手机号、应用内 OpenID 和开放平台范围内的 UnionID，避免身份扩展改变订单、会员、钱包和推荐关系归属。

## 目标

1. 经服务端验证的手机号作为手机号账户的主要匹配标识；这类账户的 username 与规范化手机号一致，内部主键继续使用 UUID v7 的 user_id。
2. 前端只提供统一“登录/注册”入口，不查询手机号是否已注册，不自行选择注册或登录 API。
3. 已有有效微信绑定且手机号完整的用户可通过微信凭据恢复登录；新用户及缺手机号的历史微信账户进入手机号授权步骤。
4. 后端统一裁决可信手机号查找、首次建号、绑定、冲突及会话签发；手机号授权成功本身不等于商城登录成功。
5. 首页、分类、商品详情及个人中心公开外壳支持游客态；私有模块与业务写入保持服务端鉴权。
6. 登录后按需引导官方昵称头像填写，允许跳过；恢复原目标和商品上下文，无有效目标时进入个人中心。
7. 复用现有第三方身份表，明确多 AppID 与 UnionID 的扩展边界，不建立重复账户体系。
8. 形成迁移、并发、失败恢复、隐私、版本与真机验收清单，区分本地实现和实际开放条件。

## 非目标

- 本次不实现或执行数据库迁移，不读取生产数据和真实秘密，不直接启用微信登录。
- 不创建 C 端 Web/H5，不实现网站扫码登录、原生 App 微信登录、公众号登录或其他 OAuth 提供方；这些仅保留可扩展的数据边界。
- 不提供客户端自报手机号登录、仅凭 OpenID 字符串登录、公共密码、密码登录或短信登录兜底。
- 不自动合并两个 user_id，不搬迁订单、钱包、积分、佣金和推荐关系，不自动解绑或替换已有微信身份。
- 不实现自助换绑手机号、手机号回收后的账户找回或实际注销；相关异常明确阻断并进入运营核实流程。
- 不改变 Admin Cookie、CSRF、权限及管理员用户名规则，不重设计无关页面。
- 不因“保持最新”升级全部依赖或采用预发布版本，不将计划中的测试清单当作执行授权。

当前外部身份表已经具备以下两个唯一约束：

- UNIQUE(provider, app_id, subject_id)：同一应用中的一个外部身份只属于一个商城账户。
- UNIQUE(user_id, provider, app_id)：同一商城账户在同一微信应用中只绑定一个微信身份。

这两个约束允许一个 user_id 关联多个不同 AppID 下的 OpenID，已经具备跨应用映射基础。模型存在不能证明目标环境已完成迁移，本次未查询数据库。

| [Taro 发布元数据](https://registry.npmjs.org/@tarojs%2Ftaro) | 稳定 latest 为 4.3.0，项目核心 Taro 包声明、锁定与本机安装同版 | 保持当前稳定组合，实施前再核对，不采用 alpha |

手机号能力当前针对符合资格且已认证的非个人主体开放；标准计费说明为成功回调按次计费，并有体验额度及部分免费主体规则，最终以实际账号权益为准。本计划不推定本项目已经取得资格或额度。

官方规范未将“首页点击进去的一切页面”定义成免登录范围。按内容与操作判断，订单详情、钱包等本人数据仍须鉴权。手机号主账户是商城目标策略，不能表述为微信要求所有小程序必须如此注册。

## 方案设计

### 7.1 身份模型和是否新增表

本期推荐新增持久业务表数量为零：扩展 users，复用 user_external_identities，复用 user_sessions、user_refresh_tokens 和既有审计设施。短期认证挑战使用带 TTL 的 Redis，不能承载最终账户和绑定事实。

| 标识 | 定位 | 唯一范围与使用方式 |
| --- | --- | --- |
| user_id | 商城账户不变主键 | 所有订单、会员和资金继续引用该值 |
| phone_e164 | 经服务端核验的主要账户匹配标识 | 一个号码最多属于一个保留中的商城账户；换号不改变 user_id |
| username | 手机号账户的系统用户名 | 与 phone_e164 完全一致；不作为显示昵称或业务外键 |
| OpenID / subject_id | 微信应用内用户身份 | provider + app_id + subject_id 联合唯一 |
| UnionID / union_id | 同一开放平台账号范围内的微信身份关联信息 | 必须同时知道可信的 union_scope_id；本期记录，不用于独立自动归并 |
| display_name / avatar | 可修改的公开展示资料 | 不参与账户匹配，不承担认证证明 |

“开放平台 OpenID”和“小程序 OpenID”都按所属应用的 AppID 分别保存，不能各放一个固定列，也不能当成同一个值。微信网站应用、移动应用、小程序、公众号可能得到不同 OpenID；UnionID 才承担同一开放平台账号下的跨应用关联语义。

本期只登记当前小程序的实际 AppID；未来应用必须先在服务端显式登记应用类型、所属开放平台命名空间、凭据来源与允许的登录方式，再开放对应换码适配。客户端不能自报 app_id 或 provider 来切换可信提供方，未知来源直接拒绝。保留现有 provider='wechat' 约束，其他提供方实际接入时再迁移。

未来若启用“仅凭可信 UnionID 自动识别跨应用账户”，应先增加独立的外部联合身份映射表，以 UNIQUE(provider, union_scope_id, union_id) 约束到唯一 user_id，再建立 OpenID 与该主体的可校验归属。该表属于后续明确触发的扩展，本期不提前建空表。不能直接对现有身份行的 union_id 加唯一约束，因为同一用户在多个应用下会重复出现相同 UnionID。

### 7.2 users 的目标字段与用户名规则

| 字段 | 建议类型 | 约束与用途 |
| --- | --- | --- |
| phone_e164 | VARCHAR(16)，可空 | 国家码在内的 E.164 号码；非空时全局唯一，包含被软删除账户的占用 |
| phone_verified_at | TIMESTAMPTZ，可空 | 服务端成功核验时间，不代表运营商实时持号验证时间 |
| phone_verification_source | VARCHAR(32)，可空 | 本期固定受控值 wechat_phone_quick，后续验证方式须显式扩展 |
| username | 沿用 VARCHAR(50)，非空唯一 | phone_e164 非空时必须与其一致；历史未补全账户保留旧值 |

实施要求：

1. 三个手机号字段要么全部为空，要么全部有效；用数据库 CheckConstraint、唯一约束及 Schema 校验共同保证。
2. 使用国家码与号码正规化为完整 E.164 值，用户名保存同一值；展示时可按地区格式化或脱敏。不得把国家码丢掉，也不假设微信始终返回中国大陆 11 位号码。
3. phone_e164 是可信手机号唯一来源，username 是同步的登录标识，不反向将 username 中看似手机号的内容当成已验证号码。
4. 保留 user_id、原订单等外键、创建时间、会员和资金事实。无密码账户 password_hash 继续为空。
5. 为手机号账户增加 username = phone_e164 的数据库条件约束。正规化、设置手机号和更新用户名在同一事务执行，任何唯一性冲突都不覆盖旧用户。
6. 当前 normalize_username 不允许加号。实施时分离消费者手机号用户名的系统赋值规则与管理员账户校验，不为 C 端修改放宽 Admin 登录规则。
7. Admin 既有人工创建用户入口保留；人工填写的数字用户名不构成手机号验证。首次可信补全遇到用户名占用时返回冲突，不能抢占或猜测归属。
8. 本期不新增换号入口。后续换号需重新验证、原身份确认、冲突检查、会话撤销和安全审计，并同步 username；手机号回收与换号不允许把原账户资产交给新持有人。

允许空值是为了表达未补全的历史或运营预置账户。新手机号注册必须填全；历史缺手机号账户只取得补全凭证，不能依靠永久旧登录分支获得新的完整业务会话。

### 7.3 user_external_identities 的扩展

| 项目 | 本期设计 |
| --- | --- |
| 表与主键 | 保留现表和 UUID v7 主键，不复制到另一张授权表 |
| user_id | 指向 users.id，保持不可任意改绑；不同 user_id 之间不移动记录 |
| provider / app_id / subject_id | 保留现有字段和两个唯一约束；OpenID 按大小写敏感的原始可信值比较 |
| union_id | 保留可信响应，缺失保持空值，不把缺失解释为换了用户 |
| union_scope_id | 建议新增 VARCHAR(64) 可空字段；服务端登记的开放平台账号命名空间，不能使用当前小程序 AppID 冒充 |
| 索引 | 增加非唯一(provider, union_scope_id, union_id)查询索引；不依靠该索引自动合并 |
| 旧 UnionID | 无法核实开放平台归属时保留原值且 scope 为空，不参与跨应用身份判断；有受控平台绑定证据后才能回填 |
| 秘密 | 不存 session_key、微信 access_token、一次性 code 或其他提供方秘密 |

本期通过同一可信手机号及明确绑定规则即可把未来不同 AppID 的 OpenID 关联到同一个 user_id；这不等于本期已经开放其他应用登录。UnionID 只用于已核实范围内的一致性检查及未来迁移依据。

### 7.4 统一登录流程

前端只识别 authenticated、need_phone、处理中、失败等步骤，不识别“已注册手机号”与“未注册手机号”，不提供手机号查重接口。

1. 用户主动点击登录或受保护模块时，先保存合法返回目标、必要操作上下文及本次流程标识。
2. 首次身份处理前完成必要告知和主动同意；已有有效同意且未主动退出的用户可后台恢复。公开页面不等待认证结果。
3. 前端调用 Taro.login，向现有认证领域提交微信登录 code。后端使用登记的 AppID/AppSecret 调用 code2Session。
4. 后端找到有效微信绑定且对应账户具备可信手机号时，校验账户、凭据和访问状态后签发会话，返回 authenticated。
5. 无绑定或历史账户未补全手机号时，不直接创建新用户、不签发完整 Bearer；返回 need_phone 和 5 分钟有效的不可猜测短期凭证。
6. 前端展示统一“手机号快捷登录”入口，说明首次使用将创建商城账户；由用户点击微信手机号组件。手机号授权页面同时提供取消和继续浏览。
7. 前端提交短期凭证与手机号 code。后端校验凭证、向微信换取号码，并传入当前可信 OpenID 验证 code 的身份归属，再执行下节裁决。
8. 成功时在数据库事务内完成必要的用户创建/补全、绑定、会话和审计，统一返回用户及会话。前端无需调用独立注册接口。
9. 根据资料缺失和本次是否已经跳过资料引导，展示昵称头像填写；保存或跳过均进入统一返回流程。

手机号授权不能自动触发，也不能通过页面初始加载反复调用。拒绝后保留游客公开服务，不自动另建一个无手机号账户作为绕过；此前讨论中的“暂不绑定即注册”不作为本计划默认注册分支。手机号必要性按第 13 节在实施及开放前确认，不能用统一注册页面掩盖与当前动作无关的信息索取。

### 7.5 后端账户裁决矩阵

“手机号命中”只指 phone_e164 的可信记录，不包含收货地址、未验证历史字段或数字用户名。

| 微信身份与手机号状态 | Backend 行为 |
| --- | --- |
| 当前 AppID/OpenID 已绑定，账户有效且手机号完整 | 直接恢复该账户，不反复索取手机号 |
| 无当前绑定，可信手机号不存在，也无用户名或 UnionID 冲突 | 注册开关允许时创建用户，username 同手机号，绑定当前微信身份并签发会话 |
| 无当前绑定，手机号命中有效账户，该账户不存在不同微信主体归属问题 | 使用已有 user_id；经下述归属校验后绑定当前应用身份并签发会话，不重复建号 |
| 当前身份已绑定历史无手机号账户，授权号码未被占用 | 补全原 user_id 的手机号与 username，保留全部业务关系 |
| 当前身份指向 A，手机号指向 B，且 A != B | 明确身份冲突；不静默切到 B，不合并、不转移资产 |
| 同一 AppID 下该手机号账户已绑定另一个 OpenID | 明确绑定冲突，不自动替换；进入独立身份核实流程 |
| 同一开放平台命名空间下可信 UnionID 指向不同用户 | 拒绝新增绑定并审计，不把手机号作为覆盖依据 |
| 号码命中已停用、软删除或限制中的账户 | 拒绝登录和重复创建，不释放号码来绕过限制 |
| 无绑定且注册开关关闭 | 不创建用户；已有手机号账户的安全登录/绑定按其权限独立裁决 |
| 微信、数据库或 Redis 不可用 | 明确失败，不降级成新用户或未注册状态 |

已有手机号账户的归属校验：

- 原账户没有微信绑定且手机号来源可信时，可按该可信手机号完成首次微信绑定；数字用户名相同不满足此前提。
- 原账户在其他微信应用已有绑定时，可信的同命名空间 UnionID 一致可作为同一微信主体的佐证，并联合本次手机号证明完成绑定。
- 其他应用已有绑定但 UnionID 缺失、命名空间不同或无法确认同一主体时，要求已有可信账户会话的独立绑定确认；本期未提供该恢复入口时明确阻断，不退回仅凭号码占有迁移资金账户。
- 不对外泄露冲突账户的完整手机号、用户 ID、昵称或资产信息，统一提供安全的核实提示和请求编号。

手机号快速验证不保证实时持号，且手机号存在二次放号；普通成功登录不能替代未来提现、换绑和账户找回需要的专项身份验证。

### 7.6 手机号接口、凭证与外部失败

- 复用现有共享 httpx.AsyncClient 和固定官方 HTTPS 地址，明确连接、读取及总超时，不继承未知代理或跟随重定向。
- 调用官方服务端手机号接口需要微信应用 access_token；它与商城 Bearer、Refresh Token、session_key 分开命名和存放。应用凭证按 AppID 缓存在 Redis，设置依据 expires_in 的提前刷新及有限并发锁，不返回客户端。
- 优先使用官方稳定版接口调用凭据能力；实施时复核当前文档、有效期、刷新限制与错误语义，禁止把旧 Token 失败静默解释为未注册。
- 校验手机号响应结构、countryCode、purePhoneNumber 与规范化结果，校验 watermark.appid 和时间有效性，并要求微信核验 phone_code 与当前 OpenID 的绑定关系。
- 登录 code 与手机号 code 各自一次性消费。手机号换码超时或结果未知不自动重发同一 code；Token 失效等错误也不得未经证明安全就重放。
- 短期凭证绑定 provider、AppID、OpenID、可用的 UnionID/命名空间、已有历史 user_id、流程随机标识及截止时间；Redis Key 只含凭证摘要，不使用手机号或 OpenID 明文。
- 短期凭证只允许完成当前手机号认证步骤，不能调用私有业务接口、换取任意账户、接受客户端指定 user_id 或修改绑定对象。
- 同一凭证原子推进 ready、processing、committed、unknown 等状态；并发只允许一方消费手机号 code。过期后重新获取微信凭据，不能无限续期。
- 验证结果可以在未过期的同一挑战中短暂保留，保护访问并按 TTL 删除；Redis 丢失后重新授权，不将其作为已注册或已绑定的唯一事实。
- 已提交事务但响应丢失时，客户端以新的微信 code 重新走身份识别，查询现有绑定并签发新会话；禁止重用旧 code 再注册。处理中和结果未知给出有限等待/重新发起提示，避免产生无限轮询。
- 商城注册与登录受 IP、主体摘要、挑战和接口维度限流；日志、Trace、错误及审计不记录完整手机号、code、票据、OpenID、UnionID、Token 或微信原始响应。

### 7.7 事务、并发与数据库约束

1. 微信换码和号码验证在数据库业务事务之外完成；不能持有用户行锁等待微信响应。
2. 事务内先按统一排序取得涉及的手机号摘要锁、微信主体锁及需要的同命名空间 UnionID 锁，再按固定 user_id 顺序锁用户与绑定记录并重新查询权威状态。
3. 新账户创建继续受 miniapp_registration 共享配置锁约束，关闭注册与建号有确定先后顺序；登录已有账户不误用注册开关。
4. users 手机号唯一、username 唯一及外部身份两个唯一约束共同兜底。唯一冲突必须回滚后重新核对归属，只接受完全一致的幂等结果，其他情况返回冲突。
5. 用户、手机号补全、外部绑定、会话、Refresh 摘要和成功审计由同一个最外层 Application Service 事务提交。
6. 失败不遗留半个用户、孤立绑定或假会话。停用、删除、撤销和凭据版本必须在签发前重新验证。
7. 保持既有 UserSession profile、client_id、audience、内存凭据和身份代次边界；不把手机号变为 Token 主体，Token 主体仍为 user_id。
8. 此处为目标锁协议，实施时逐项核对现有用户管理和会话撤销锁顺序，编写真实 PostgreSQL 交叉并发用例，不能只验证顺序登录。

### 7.8 API 与前端状态契约

沿用 /api/v1/auth 领域，不新建另一套 miniapp 专属业务路径。建议扩展 POST /auth/login 为明确鉴别的两种操作：wechat 提交登录 code；phone 提交短期凭证和手机号 code。输入严格禁止额外 OpenID、手机号字符串和目标 user_id。

成功信封中的数据使用可生成的鉴别联合：

- authenticated：原有用户、Access/Refresh、会话期限及明确的资料引导信息。
- need_phone：短期凭证及到期信息，不含业务 Token、OpenID、UnionID 或可枚举的账户信息。

异常使用现有 AppException 与标准错误码体系，区分能力未开放、凭证失效、号码授权未完成、身份冲突、账户停用、限流、依赖不可用和结果未知。前端不把 503 当成 need_phone，不用手机号查重控制界面。

保留 /auth/refresh、/auth/logout 和 /auth/capabilities 的职责。能力查询可明确手机号能力是否就绪，但不得披露秘密和平台身份数据。头像与昵称继续使用 /users/me 既有业务接口，按需要扩展安全投影，生成客户端后消费。

该变化会改变现有登录请求和成功结构，属于需要联合迁移消费者的契约变化。后端实现、根 openapi.json 导出、pnpm generate-api、Miniapp/Admin 适配按顺序执行。默认登录关闭期间协调切换；若届时已有正式客户端在用，须依 ADR 0007 登记负责人、准确删除日期、观测和删除测试后才能建立短期兼容，不能无限接收两套请求。

### 7.9 游客页面、资料引导与登录返回

| 场景 | 游客状态 | 已登录状态 |
| --- | --- | --- |
| 首页、分类、列表、详情、公开评价 | 正常浏览，不提前发起手机号授权 | 保持公开浏览，可追加已授权的本人信息 |
| 个人中心首页 | 默认头像、登录入口、功能菜单；私有数值隐藏，不伪造零余额 | 读取本人资料与有权限的业务摘要 |
| 购物车 Tab | 游客说明、登录和继续逛逛 | 本人购物车 |
| 订单、地址、钱包、积分等私有模块 | 点击具体模块才发起认证 | 服务端鉴权后进入 |
| 商品加购、立即购买 | 保存 SKU、数量和动作再认证 | 重新核验业务条件 |
| 隐私、协议、公开帮助与联系渠道 | 直接访问 | 直接访问 |

采用同一页面组件的不同状态，复用现有 NutUI、设计 tokens 和 Feature 公共入口，不复制两套页面或另建视觉体系。全局只维护一个认证流程，重复点击共用该流程；认证、处理中、取消、失败、已登录状态明确。

昵称使用 type=nickname 与表单最终提交值；头像使用 openType=chooseAvatar，取得临时路径后校验大小、上传并绑定本人资产。平台组件审核不能替代后端文件安全及归属校验。保留原有头像上传、删除绑定和未知结果查询能力，淘汰本场景停止维护的 chooseImage 调用。

资料页提供“保存并继续”和“暂时跳过”；跳过不取消已注册账户、不清除登录态、不阻断购物。按用户和引导版本保存非秘密跳过偏好，避免每次登录强弹；已有资料的用户不重复填写。

返回上下文包括受控路由、白名单参数、来源页面、商品/SKU/数量、动作类型、流程 ID 和 15 分钟有效期，不含手机号、认证票据和 Token。默认保存在内存，若小程序进程丢失则丢弃本次返回意图并落到个人中心，不盲目恢复持久化的旧写动作。

恢复规则：

1. 本人模块：回到原目标并保留合法筛选条件，服务端仍复核资源归属。
2. 加购：恢复原商品规格确认界面，由用户再次确认，不自动增加数量。
3. 立即购买：恢复已选商品，重新校验可售性、库存与价格后进入结算确认，不创建订单或付款。
4. 普通页面按页面栈返回或重定向，TabBar 使用 switchTab；TabBar 不能携带的参数经本次流程上下文传递并消费一次。
5. 无目标、目标非法、过期或指向登录流程本身时，统一进入个人中心；取消认证回来源，无来源回首页。
6. 目标已删除或无权限时显示明确提示并提供个人中心入口，不无限跳转登录。
7. 后台静默恢复不改变用户当前页面；主动退出后禁用自动恢复，直至用户再次点击登录。
8. 成功消费、取消、退出和切换身份时清除对应待执行意图，旧异步结果不得回填新会话。

### 7.10 Admin、隐私与观测

- 保留 Admin 既有用户创建、编辑、启停、回收站、恢复及会话管理功能；不把运营人员填写手机号等同微信验证，不增加未经授权的手工微信改绑入口。
- username 含手机号后，逐项检查列表、详情、选择器、抽屉标题、操作文案、导出、搜索、审计及异常。默认使用 display_name、脱敏账号展示字段与 user_id；消费端不下发完整 username 或手机号。
- 不把同一个公开字段混用于真实用户名和掩码。需要调整 Admin 响应时提供命名明确的安全投影并同步生成契约；现有权限下确需读取完整号码的用途须单独评估，默认不新增完整号码展示。
- 平台隐私指引须覆盖账号身份、手机号、昵称、用户选择头像及实际上传用途，保留公开说明入口。使用官方隐私授权机制，应用内勾选不伪造微信侧同意。
- 手机号快速注册只是账户策略，首次游客不应因纯浏览收到授权弹窗。加购等仅需账户身份的行为如何说明手机号必要性，列为开放前的产品与平台核实项。
- 使用既有安全事件设施记录动作、结果、用户主键和请求号，展示手机号掩码仍按权限控制。指标覆盖换码失败、需手机号比例、授权拒绝、绑定冲突、首次建号、未知结果与恢复，不增加秘密或完整个人信息标签。

### 7.11 历史账户迁移与开放顺序

1. 实施前只读盘点实际目标库 revision、用户和外部绑定数量、无手机号账户、数字用户名占用、UnionID 命名空间和敏感投影。输出聚合结果及受控问题清单，不将真实个人数据写入仓库。
2. 追加 Alembic revision 增加手机号字段、条件约束和 union_scope_id，保留现有主键及约束。真实升级单独授权，不修改已交付 migration。
3. 不从地址簿、订单联系方式、昵称、旧用户名或推测的 UnionID 回填可信手机号；没有可靠证明的数据继续为空。
4. 已绑定无手机号用户首次进入新流程时取得仅限手机号补全的短期凭证，验证成功后在原 user_id 上更新；若号码已指向其他 user_id，阻断并核实。
5. 上线切换时撤销受影响的历史小程序会话或通过统一凭据/会话策略使其重新认证，确保不能用切换前会话绕过手机号完整性要求；Admin 和冻结的历史 Browser 会话不转为小程序身份。
6. 未补全账户可长期保留业务历史，但不保留旧版自动建号和完整登录入口。这是明确的账户完整性状态，不设无期限旧协议分支。
7. 若运行环境始终未启用登录且无外部绑定，可在证据核实后缩小回填范围；不能仅根据仓库默认开关推定数据库没有用户。
8. 开放前确认真实 AppID、AppSecret、平台命名空间、服务端出口及接口凭证要求、request/uploadFile 合法域名、HTTPS、主体资格、手机号额度和隐私指引。
9. 使用实施时核验的稳定基础库进行微信工具和真机验收，同时验证设定的最低支持版本；开发工具 libVersion 不代表全部用户微信运行时都已升级。低于能力要求时明确提示升级，保留公开浏览，不接回旧式手机号解密流程。

## 风险与回滚

| 风险 | 控制与回滚边界 |
| --- | --- |
| 手机号回收或身份冲突导致账户接管 | 保持已验证微信归属、禁止自动覆盖；冲突阻断，资产不迁移 |
| username 与手机号相同扩大隐私暴露 | 一并核对所有消费者、检索和审计，输出安全投影；不能只改小程序页面 |
| 并发首次注册重复建号 | 固定锁顺序、数据库唯一约束、冲突后重新核实；同一主体只产生一个归属 |
| 一次性 code 已消费但响应丢失 | 标记未知并重新取得新凭证；依赖数据库绑定事实恢复，不无限重试 |
| 注册开关关闭与登录混淆 | 区分创建新 user_id 和登录/安全绑定已有账户，事务内复核 |
| 历史用户无法完成补全 | 保留原 user_id 与全部业务事实，提供明确支持路径；禁止清库或伪造手机号 |
| 新旧登录契约混用 | 默认关闭期间协调切换；实际存在旧消费者时登记有期限迁移，不隐式兼容 |
| 手机号收集用途不符合平台要求 | 开放前解决用途与触发边界；验证失败保持能力关闭和公开浏览 |
| 数据库升级后直接退旧代码 | 手机号账户已有写入后，旧代码可能继续创建无手机号用户；禁止直接降级并开放登录 |

本次纯文档可通过逐文件反向补丁调整，计划资产继续保留，不能删除新计划来回退。未来实现出错时优先关闭认证写入或登录总开关、保留公开服务和数据，再采用前向修复。真实迁移先按项目手册完成可恢复备份；存在手机号和新绑定数据时，downgrade 必须拒绝破坏性丢列或删除记录。回滚、恢复和生产动作分别授权。
